# Подготовка и создание коммита

Следуй [правилам проекта](../../../AGENTS.md) и вложенным `AGENTS.md` затронутых модулей. Перед подготовкой сообщения прочитай [правила именования коммитов](references/commit-naming.md). Применимые проверки выбирай по разделу «Проверки Outgate» ниже. Эти документы — источник требований; не заменяй их собственными соглашениями.

## Определить состав изменений

- Прочитай запрос и контекст текущей задачи. Просмотри `git status --short`, `git diff`, `git diff --cached`; изучи содержимое относящихся к задаче новых файлов, поскольку обычный diff их не показывает.
- Выдели одну логическую задачу и её сопутствующие тесты и документацию. Не считай все изменения рабочего дерева автоматически разрешёнными для коммита.
- Сохраняй посторонние правки и существующее частичное индексирование. При смешанных изменениях выбирай только нужные фрагменты; не добавляй целиком частично индексированный файл без проверки состава. Не используй безусловные `git add .`, `git add -A` или `git commit -a`.
- Если посторонние изменения уже находятся в индексе или границы задачи неясны, уточни состав до изменения индекса и создания коммита. Не снимай чужие изменения с индекса самостоятельно.
- Если подходящих изменений нет, сообщи об этом; не создавай пустой коммит.

## Подготовить сообщение

Составь сообщение по фактическому diff и правилам из `references/commit-naming.md`: выбери тип и при необходимости область, напиши конкретное русское описание с глаголом в неопределённой форме. Учитывай требования к несовместимым изменениям и отмене коммитов.

Если пользователь просит только сообщение, верни готовый текст. Не меняй индекс и не создавай коммит. При наличии staged-изменений ориентируйся на них, если пользователь не указал другой состав; иначе используй относящиеся к запросу изменения рабочего дерева.

## Создать коммит

1. Выполни применимые проверки из раздела «Проверки Outgate», учитывая уже выполненные проверки актуального состава изменений. При ошибке останови создание коммита и сообщи причину; недоступные обязательные проверки также укажи пользователю до коммита.
2. Добавь в индекс только выбранные пути или фрагменты, сохраняя существующие границы частичного индексирования. Проверь `git diff --cached`, `git diff --cached --check` и статус: сообщение должно описывать именно итоговый staged diff.
3. Создай обычный коммит. Для многострочного сообщения используй файл и `git commit --file`, сохраняя настоящие переводы строк и избегая shell-подстановок в тексте.
4. Не отключай hooks и не обходи их ошибки. Если Git или hook завершился ошибкой, сообщи её и проверь состояние перед дальнейшими действиями; не повторяй коммит вслепую. Если hook изменил файлы, заново просмотри diff и повтори затронутые проверки перед новой попыткой.
5. Проверь созданный коммит через `git log -1` и итоговый `git status --short`. Сообщи хеш, сообщение, результаты выполненных проверок и оставшиеся незакоммиченные изменения.

Создание коммита не разрешает `push`, `amend` или переписывание истории. Выполняй такие действия только по отдельному запросу пользователя.


## Проверки Outgate

Перед исправлениями прочитай относящиеся к задаче разделы [ТЗ](../../../docs/requirements.md), [протокола](../../../docs/protocol.md) и [schema](../../../docs/protocol.schema.json). Production-требования имеют приоритет над development-упрощениями.

- При изменении wire-контракта проверь согласованность ТЗ, protocol/schema, golden fixtures, тестов и compatibility matrix. Не меняй нормативные fixtures только ради прохождения реализации. Для protocol/parser изменений нужны негативные и граничные тесты, сверка существующих golden bytes и при необходимости fuzz targets. Reference verifier не заменяет JSON Schema validation и semantic/state-machine проверки.
- Сверь изменение реализации с этапами ТЗ §7 и локальным общим статусом `../project-notes/implementation-status.md` (путь от корня checkout); обновляй статус при изменении выполненного объёма и оставшихся проверок. Файл находится вне репозиториев компонентов и не входит в коммиты. Если он отсутствует, сообщи об этом и восстанови контекст по коду и Git; не создавай статус внутри компонента. Каркас, codecs и unit tests не означают готовность adapter или завершённую приёмку. Для QUIC adapter требуется предшествующий сквозной quic-go spike по ТЗ §2.3.
- Проверь границы затронутых модулей: SDK не импортирует gateway, `protocol/v1` содержит только wire types/codecs/чистые helpers; reverst не входит в код, зависимости или обязательные инструменты. Для новых dependencies нужны фиксированные версии, compatibility/security/license проверка и SBOM по правилам проекта. Не добавляй обязательный `go.work` или локальные `replace` в публикуемые модули.

Команды выполняй из указанных каталогов, не из корня как единого Go-модуля:

| Затронутая часть | Проверки |
| --- | --- |
| Protocol/schema, fixtures, verifier или SDK | Из корня: `python3 tests/fixtures/protocol/v1/verify.py` |
| SDK, его зависимости или настройки сборки | Из отдельного SDK checkout (например `../outgate-sdk/`): `GOWORK=off go test -race ./...` и `GOWORK=off go vet ./...` |
| Go-код SDK или его сборка | Отдельно Windows compile из отдельного SDK checkout (например `../outgate-sdk/`): `GOWORK=off GOOS=windows GOARCH=amd64 go build ./...`; при изменении тестов также compile затронутых тестовых пакетов через `go test -c` с теми же переменными окружения и выводом в временный каталог |

Для изменений только документации или скиллов проверь ссылки, формат и согласованность инструкций; Go-проверки нужны, если изменяются описанные команды сборки или поведение SDK. Для новых модулей выбирай проверки по их собственным инструкциям и CI.

Windows cross-compile не является native Windows runtime-проверкой. Не объявляй CI выполненным по наличию workflow. Недоступные обязательные проверки сообщи до коммита; не обходи их без явного решения пользователя и не объявляй успешными. Фиксируй только фактически выполненные проверки и их ограничения.
