# Deployment grant и ротация credentials

Контракт этапа 1 для ТЗ 3.25, 5.5.1 и 6.5. Схема привязки grant используется Admin API и логической записью control state. Манифест файлового источника описывает один способ передать пару приложению, которое вызывает `WithCredentialProvider`. Сетевой обмен остаётся определён протоколом туннеля. [Схема grant](deployment-grant.schema.json), [схема манифеста](credential-provider.schema.json), [Admin API](admin-openapi.yaml), [протокол туннеля](protocol.md).

## Выдача и проверка grant

1. Deployment principal запрашивает grant через Admin API после проверки подписи и digest сборки. Запрос связывает `service_id`, `instance_id`, `version`, `paths`, `mounts`, `path_mode`, `rewrite_mount_headers`, digest и SPKI. SHA-256 SPKI вычисляется над DER SubjectPublicKeyInfo leaf certificate и записывается в lowercase hex. `expires_at` задаётся в RFC 3339. Срок от подтверждённой выдачи до истечения больше нуля и не превышает 1 часа. Для атомарной ротации запрос содержит `credential_generation`. У static credentials и grant-only provider поле опускается.
2. Gateway выдаёт `grant_id.secret`. Первая часть кодирует минимум 16 случайных байт, вторая минимум 32. Обе используют канонический base64url без padding. Длины закодированных частей ограничены схемой. Gateway сохраняет `grant_id`, SHA-256 декодированных байт secret и binding. Проверка digest выполняется сравнением с постоянным временем. Полный credential возвращается в первом успешном ответе и передаётся экземпляру по защищённому каналу. Повтор по operation key и поиск операции возвращают безопасные метаданные. Secret и его digest исключаются из списков, аудита, operation records и логов.
3. До `register_ack` gateway проверяет TLS client certificate, срок и отзывы, grant и точную привязку к регистрации. URI SAN имеет форму `spiffe://<trust_domain>/service/<service_id>/instance/<instance_id>`. Trust domain берётся из конфигурации gateway. Множество `paths` сравнивается без учёта порядка, по точным строкам. Путь и дубли дополнительно проверяются после нормализации по правилам routing, регистрация `/` требует назначения frontend. Значения `mounts` должны быть точными элементами `paths`. Пустой `mounts` в grant соответствует отсутствию поля в register.
4. Для атомарной пары в register и согласованном ack требуется capability `credential_generation`. Положительное uint64 передаётся десятичной строкой, совпадающей с поколением grant. При смене пары поколение увеличивается. Старые поколения отклоняются; реконнект той же пары возможен после очистки прежней сессии при действующих credentials. `credential_expires_at` в ack равен более раннему из `certificate.NotAfter` и `grant.expires_at`. SDK использует подтверждённый срок из ack для планирования обновления.

## Источник атомарной пары

Callback возвращает Go `CredentialSnapshot` с одним `tls.Certificate`, одним opaque deployment grant и одним поколением. Provider проверяет полную пару перед возвратом и не меняет её после публикации. SDK проверяет сертификат, соответствие ключа, SAN, срок и поколение. Разрешения и привязку opaque grant независимо проверяет gateway. Параметры проверки TLS-сертификата gateway задаются приложением отдельно от provider. Provider не получает административные credentials и не выдаёт себе grant.

При файловой поставке deployment-процесс записывает цепочку сертификатов, закрытый ключ и grant в защищённые файлы нового поколения. Он публикует один манифест после подготовки всех трёх файлов. Источники, на которые ссылается опубликованный манифест, остаются неизменными на время чтения. Читатель загружает одно поколение целиком и возвращает ошибку при неполной паре. Поля `certificate_file`, `private_key_file` и `deployment_grant_file` содержат ссылки на файлы. Приложение задаёт корень разрешения относительных путей и доступ к этим файлам. Манифест передаётся внутри deployment-процесса. Ссылки с синтетическими путями для Linux и Windows приведены в примерах. [Примеры манифестов и привязки](../tests/fixtures/credentials/v1/rotation.json).

SDK начинает обновление заранее с учётом фактического срока принятой пары. Timeout callback составляет 5 секунд. Получение credentials допускает повтор с jitter в пределах оставшегося срока пары. После локальной проверки новой пары SDK прекращает новые назначения, выполняет bounded drain старого туннеля, закрывает его и только затем регистрирует новое поколение. Истечение или отзыв имеют приоритет над drain. Старые HTTPS-соединения исключаются из новых доставок при переключении.

Проверка схем и примеров выполняется без выпуска credentials и без сети. Верификация X.509, совместимость источников на реальных ОС, контроль активных сессий, проверка отзывов и устойчивое сохранение поколения относятся к запуску gateway и SDK.
