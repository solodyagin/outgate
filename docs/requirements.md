## 1. Общие сведения

### 1.1. Наименование и цель

**Outgate (Reverse API Gateway)** — обратный HTTP-шлюз для подключения микросервисов через исходящие соединения с регистрацией HTTP-префиксов.

Шлюз работает отдельным процессом и обслуживает один публичный домен. API-сервисы регистрируют префиксы `/api/v1`, `/api/v2` и другие разрешённые пути и самостоятельно аутентифицируют пользователей и проверяют прикладные права. Зарегистрированные пути направляются в туннели; неизвестные пути внутри `/api` возвращают `404`. Остальные пути обслуживает отдельный frontend-upstream с SPA в корне `/`. Администратор может разрешить одному специальному frontend-сервису перекрывать этот upstream корневым QUIC/WSS-туннелем. Оба варианта фронтенда обновляются независимо от шлюза. Микросервису за NAT/файрволом не нужен публичный входящий порт.

Целевая аудитория: разработчики Go-сервисов, администраторы шлюза и внешние HTTP-клиенты. Интеграция сервиса выполняется через клиентскую Go-библиотеку и существующий `http.Handler`.

### 1.2. Основные возможности

- В первую тестовую версию включены два транспорта: QUIC/HTTP3 и WSS. Администратор независимо включает слушатели; клиент явно выбирает транспорт.
- Outgate реализуется самостоятельно, без импорта, копирования кода или fork reverst. QUIC/HTTP3-адаптер использует напрямую `quic-go`/`quic-go/http3`, WSS — независимую WebSocket-библиотеку; оба следуют собственному общему контракту Outgate.
- Шлюз отделяет API-пространство `/api` от frontend-upstream, проверяет права на регистрацию префиксов и балансирует запросы независимо от транспорта. Пользовательская аутентификация остаётся в API-сервисах.
- Межсервисные вызовы идут отдельным HTTPS-запросом в шлюз с HMAC-подписью отправителя. Шлюз проверяет права на целевой сервис и передаёт ему подписанный пользовательский контекст либо идентичность фонового сервиса.
- Потоковые тела, SSE, прозрачное WebSocket-проксирование, реконнект и graceful shutdown обязательны для обоих транспортов уже в прототипе. Публичный префикс задаётся конфигурацией развёртывания; опциональный режим strip позволяет обработчикам сервиса работать от `/` независимо от точки монтирования.
- Для реплик доступны round-robin и active-passive: один выбранный экземпляр получает новые запросы, остальные остаются готовым резервом; режим и порядок задаёт администратор для сервиса/версии.
- Версии обнаруживаются по обязательному полю `version` при регистрации запущенных экземпляров. Администратор управляет канареечным распределением, продвижением и откатом через Admin API.
- Нативный запуск Linux amd64 и Windows amd64, включая production: Windows Service/консоль без WSL2 и контейнеров. Для постоянного control/replay/session хранилища поддерживаются встроенная SQLite и PostgreSQL; SQLite по умолчанию, внешний Redis необязателен.
- Целевые показатели производительности проверяются на отдельном нагрузочном этапе. Выбор транспорта сам по себе не подтверждает их достижение или превосходство безопасности.

### 1.3. Термины

| Термин | Определение |
| :--- | :--- |
| Туннель | Одно активное QUIC- или WSS-соединение экземпляра со шлюзом |
| Service ID | Логическое имя сервиса, связанное с учётными данными и разрешёнными путями |
| Instance ID | Глобально уникальный в пределах шлюза идентификатор экземпляра; сохраняется при реконнекте |
| Version | Идентификатор сборки сервиса, например `1.4.2` или git SHA; не версия протокола |
| Префикс | Путь, сопоставляемый по границам сегментов URL |
| Shared path | Префикс, явно разрешённый нескольким сервисам |
| Stable / canary | Версии сервиса, участвующие в текущей политике распределения трафика |
| Кандидат | Обнаруженная версия, не включённая в текущую политику; получает 0% трафика |
| Основное приложение / frontend-upstream | Настроенный HTTP(S)-сервер SPA, используемый, когда корневой tunnel override не действует |
| Frontend override | Выданное администратором одному service_id право обслуживать `/` через туннель вместо SPA-upstream, без перехвата API и более конкретных маршрутов |
| Пользовательский контекст | Проверенные API-сервисом ID, роли и разрешённые дополнительные атрибуты пользователя |
| Межсервисный вызов | HTTPS-запрос с подтверждённой идентичностью вызывающего сервиса и разрешением на целевой сервис/путь/метод |

### 1.4. Границы первой версии

Первая версия включает оба транспорта, режимы монтирования, API-аутентификацию, межсервисный доступ, SPA-upstream/override, ручную канарейку, WebSocket/SSE, Admin API, отдельный административный веб-интерфейс с редактором межсервисного доступа и обязательный профиль безопасного публичного развёртывания. Поддерживается один шлюз; высокая доступность кластера не заявляется.

`deployment.mode` принимает `development` или `production`, по умолчанию `production`. Упрощения, ниже явно отнесённые к прототипу/development (статические tunnel tokens, in-memory состояние, произвольный локальный UserContext), допустимы только в development и не удовлетворяют публичной production-приёмке. Требования п. 5.5 и 8.8 обязательны для production и имеют приоритет над такими упрощениями. Development слушает loopback; в Compose допускается изолированная сеть с публикацией наружу только на 127.0.0.1. Публично публиковать development-порты запрещено.

Публичный production-релиз требует mTLS сервисов, ограниченных deployment grants, отзыва активных сессий, квот/rate limits, устойчивого control/replay-состояния, проверяемых пользовательских утверждений и отрицательных security-тестов. OTLP остаётся необязательным средством наблюдаемости. Автоматическое продвижение/откат по метрикам, полноценная интеграция с CI/CD/registry, multi-region и кластерная HA относятся к расширениям; они не заменяют обязательные защитные меры.

## 2. Архитектура системы

### 2.1. Схема

```text
Внешний клиент ── HTTPS (HTTP/1.1 или HTTP/2) ──► Gateway, один домен
                                                   │
                              зарегистрированный путь: Router
                                                   │
                              Service → Version → Instance
                                                   │
                                  ┌────────────────┴──────────────┐
                                  │ QUIC/HTTP3 adapter            │ WSS adapter
                                  │ UDP + TLS 1.3                │ TCP + TLS 1.3
                                  ▲                              ▲
                            Сервис A + outgateclient           Сервис B + outgateclient
                            исходящее соединение           исходящее соединение

Неизвестный /api/... ──► 404
Другой путь ──► назначенный frontend tunnel / (если зарегистрирован)
             └─► иначе HTTP(S) reverse proxy ──► SPA upstream
Сервис A ── отдельный HTTPS + HMAC ──► Gateway ── туннель ──► Сервис B
Admin browser ── management origin ──► Admin Web/BFF ── mTLS + user JWT ──► Admin API
Admin API / metrics / health ──► отдельные служебные слушатели
```

Внешним клиентам поддержка HTTP/3 не требуется. Транспорт внешнего HTTP-запроса не определяет транспорт выбранного туннеля.

### 2.2. Компоненты

1. **Общий слой шлюза:** аутентификация, разрешения, атомарная регистрация, реестр маршрутов/версий/экземпляров, канареечная политика, балансировка, заголовки, метрики и жизненный цикл запросов.
2. **Транспортные адаптеры:** установка и закрытие соединения, регистрация, передача HTTP, потоков и отмены, обнаружение разрыва и дренирование. Транспортные детали не должны проникать в правила маршрутизации.
3. **Client library:** единый API для `http.Handler`, выбор транспорта, ограничение конкурентности, реконнект, завершение работы, подписывающий HTTPS-клиент и проверка входящего доверенного контекста.
4. **Admin API:** единая серверная точка административных проверок, просмотра и изменения политик/rollout/access.
5. **Admin Web:** отдельная management-консоль с BFF и OIDC/MFA, использующая Admin API, не публичную SPA. Сетевой доступ и credentials отделены от сервисных туннелей.
6. **Upstream proxy:** обработка незарегистрированных путей вне `/api` отдельным SPA-сервером.
7. **Межсервисный доступ:** проверка отправителя, target/paths/methods, права делегирования, HMAC-подписей и nonce; формирование подписанного контекста для получателя. Пользовательская аутентификация не переносится в шлюз.

Общий контракт адаптера должен обеспечивать идентичные результаты регистрации и HTTP-поведение для QUIC и WSS. На уровне Go допускается использование `http.RoundTripper` и потоковых `io.ReadCloser`; буферизация всего тела в общем слое запрещена.

### 2.3. Самостоятельная реализация и границы зависимостей

- Шлюз, SDK, регистрация, маршрутизация, управление версиями/репликами, авторизация, Admin API и адаптеры реализуются собственным кодом Outgate по этому ТЗ и [protocol.md](protocol.md). **Запрещены импорт модулей/пакетов reverst, его транзитивное включение, vendoring, копирование/переработка исходного кода и обязательный fork reverst.** Для сборки, тестирования, установки и работы Outgate не требуется загрузка, сборка или запущенный процесс reverst.
- Reverst остаётся только архитектурным референсом: сведения о рассмотренной ревизии сохранены в [upstream.md](upstream.md). Они не задают production dependencies, Go toolchain, wire compatibility или критерий «сначала адаптировать upstream». Совместимость с немодифицированным протоколом/клиентом reverst не требуется; несовместимый peer отклоняется явно.
- Допускаются независимые транспортные библиотеки: `quic-go` и его HTTP/3 package напрямую для QUIC/HTTP3, `coder/websocket` для WSS, а также выбранные SQL/криптографические/наблюдательные зависимости. Использование библиотеки, которую также использует reverst, не делает её компонентом reverst и не запрещается. Самостоятельная реализация Outgate не означает самостоятельное написание QUIC/TLS/HTTP3 или отказ от всех сторонних пакетов.
- Версии Go/библиотек фиксируются по результатам compatibility/security проверки, независимо от исторического go.mod reverst. Сохраняются лицензии/уведомления реально используемых dependencies и SBOM; лицензия/права собственного кода выбираются отдельно. Архивная копия лицензии архитектурного референса в docs/references не является заявлением о включении reverst в бинарник/SBOM. Без копирования кода не имитируется соблюдение лицензии простым переименованием пакета: происхождение собственного кода и изменения проверяются review.
- До реализации этапа 2 обязателен собственный сквозной spike напрямую на выбранной `quic-go`: обратное HTTP/3 по исходящему соединению сервиса, отдельный control carrier без конфликтов streams/QPACK, streaming/cancel и internal CONNECT WebSocket, native Linux/Windows. Исключение reverst не доказывает работоспособность reverse mapping. Если публичные API выбранной библиотеки не поддерживают контракт, сначала пересматриваются ADR/ТЗ/protocol/schema/fixtures; нельзя скрыто заменить HTTP/3 собственным framing поверх QUIC либо добавить reverst обратно.
- Приёмка проверяет `go.mod`, `go.sum`, resolved module graph, imports/vendor и SBOM на отсутствие reverst; CI не скачивает/не запускает его как обязательный build/test tool. Review проверяет отсутствие перенесённых файлов/фрагментов reverst. Такие проверки не считаются выполненными до появления реализации. Референсные URL/история решений в документации допускаются.

## 3. Функциональные требования

### 3.1. Слушатели и выбор транспорта

- Публичный слушатель **ДОЛЖЕН** принимать HTTPS по HTTP/1.1 и HTTP/2; адрес по умолчанию `:8443`. Открытый HTTP-порт в прототипе не требуется.
- Администратор **ДОЛЖЕН** независимо включать QUIC (`:7171`, UDP) и WSS (`:7172`, TCP, путь `/tunnel`). Допустимы QUIC-only, WSS-only и смешанный режим.
- Если отключены оба транспорта, неверны сертификаты или не удалось запустить любой включённый слушатель, шлюз **ДОЛЖЕН** завершить запуск с диагностируемой ошибкой.
- Клиент явно выбирает `quic` или `wss`; по умолчанию `quic`. Автоматический fallback запрещён. Несовпадение транспорта/порта должно давать ошибку выбранного подключения, а не смену транспорта.
- Оба туннеля используют TLS 1.3 и проверку сертификата шлюза. `InsecureSkipVerify` в поддерживаемой конфигурации запрещён; для стенда используется доверенный тестовый CA.
- Прозрачное WebSocket-проксирование внешних клиентов **ДОЛЖНО** работать через оба туннеля и в fallback основного приложения. Обязательный внешний handshake — HTTP/1.1 Upgrade по RFC 6455 поверх TLS; Extended CONNECT внешних HTTP/2/HTTP/3-клиентов не входит в первую версию. Поддержка WSS как транспорта туннеля и WebSocket приложения — отдельные обязательные возможности.

### 3.2. Аутентификация и регистрация

При подключении клиент передаёт:

| Поле | Требование |
| :--- | :--- |
| `protocol_version` | Обязательное целое число; для этого протокола `1` |
| `service_id` | Обязательное имя сервиса |
| `instance_id` | Обязательный ID экземпляра |
| `version` | Обязательный неизменяемый ID сборки сервиса |
| `paths` | Непустой список публичных префиксов из конфигурации сервиса |
| `mounts` | Необязательная карта логических mount IDs в точные paths; контракт п. 3.22 |
| `protocol_minor`, `capabilities`, `required_capabilities` | Согласование совместимости по п. 4.7 |
| `path_mode` | `preserve` (по умолчанию) либо `strip`; одинаков для всех путей этой сессии |
| `rewrite_mount_headers` | Boolean, по умолчанию `true` в strip и `false` в preserve; правила п. 3.16 |
| `metadata` | Необязательная карта строк: регион, теги и т. п. |
| `deployment_grant` | Обязательный в production credential допуска: передаётся в WSS Authorization/QUIC bootstrap, не отдельным полем register JSON; никогда не передаётся handler или в логи |
| `readiness_check_configured` | Boolean: SDK настроен выполнять локальную проверку готовности; обязателен true для production active-passive |

- В development bearer-токен **ДОЛЖЕН** однозначно связываться с `service_id`; в production используются mTLS identity и ограниченный deployment grant вместо общего статического токена. Проверка учётных данных и разрешений выполняется до публикации маршрутов и допуска HTTP-запросов в туннель.
- Для каждого сервиса задаются разрешённые префиксы. Регистрируемый путь должен совпадать с разрешённым префиксом либо находиться внутри него по границе сегмента. Отсутствие разрешения означает запрет; shared path не отменяет эту проверку. Исключение для allowed_paths `/` у назначенного frontend: это право только на точную регистрацию `/`, а не на любое поддерево; другие пути требуют отдельных явных разрешений.
- Регистрация всех путей **ДОЛЖНА** быть атомарной. Ошибка любого поля/пути отклоняет регистрацию целиком.
- Один `instance_id` соответствует одному активному или дренируемому соединению независимо от транспорта и версии. Повторная регистрация активного ID отклоняется; захват чужого соединения запрещён.
- Несколько экземпляров одного сервиса могут регистрировать одинаковый путь. Другие сервисы могут регистрировать тот же путь только при точном включении префикса в `shared_paths`.
- Более узкий путь другого сервиса допускается только в рамках его собственных разрешений. Вложенность сама по себе не является конфликтом.
- После обнаруженного разрыва экземпляр немедленно исключается из выбора. В development владение маршрутами сохраняется в памяти до перезапуска. В production подтверждённое владение и активированные маршруты сохраняются в постоянном control state; отключение/рестарт не выдаёт путь другому сервису. Незавершённые сессии после рестарта не считаются активными.
- Изменение набора путей, режима монтирования или версии экземпляра требует завершения старой сессии и новой регистрации. Реплики одной пары `(service_id, version)` должны регистрировать одинаковые path_mode и rewrite_mount_headers, иначе регистрация отклоняется как `invalid_register`. Разные версии могут использовать разные режимы при сохранении внешнего контракта.

### 3.3. Пути и маршрутизация

- Префикс начинается с `/`. Завершающий `/` удаляется перед сравнением, кроме самого корня `/`. Регистрация `/` по умолчанию запрещена; исключение — явно назначенный администратором frontend-сервис по п. 3.17. Корневой frontend-маршрут не даёт прав на `/api` и другие зарегистрированные префиксы.
- В регистрации запрещены пробельные/управляющие символы, query, fragment, `%`, обратная косая черта, пустые сегменты и сегменты `.`/`..`. Повторяющиеся префиксы после нормализации отклоняются.
- Для маршрутизации используется декодированный путь URL с однократным декодированием. Запросы с некорректным escaping, закодированными разделителями `/` или `\`, обратной косой чертой, управляющими символами, пустыми сегментами внутри пути или сегментами `.`/`..` возвращают `400`; неоднозначный путь не должен попадать в fallback.
- Longest prefix match выполняется по границам сегментов: `/api` совпадает с `/api` и `/api/users`, но не с `/apix`. Завершающий `/` запроса допустим. Через туннель передаются исходные публичные path/query. В preserve handler получает их без удаления префикса; в strip библиотека после всех проверок удаляет выбранный префикс по п. 3.16. Повторная нормализация или декодирование запрещены.
- Сначала рассматриваются active prefixes и retained retired tombstones по п. 3.26, отличные от `/`; pending-пути в маршрутизации не участвуют. Retired tombstone сохраняет longest-prefix match и возвращает 503, если нет другого active shared owner; он не пропускает запрос к более короткому prefix. Если среди них совпадения нет, `/api` и настроенные зарезервированные API-поддеревья возвращают `404`, даже при зарегистрированном корневом frontend. Для остальных путей применяется корневой override, а при его отсутствии — frontend-upstream. Например, неизвестный `/api/v3/orders` даёт `404`, а `/apix` может обслуживаться SPA. Правило действует и после перезапуска при ещё не восстановленных API-регистрациях. Ответ выбранного frontend, включая `404`, передаётся клиенту без повторного fallback.
- Если маршрут известен, но подходящего активного экземпляра нет, шлюз отвечает `503 Service Unavailable` с `Retry-After: 1`. Переход к более короткому префиксу или основному приложению запрещён.
- При отсутствии доступного upstream основного приложения возвращается `502`; при истечении ожидания его ответа — `504`.

После проверки межсервисной подписи/политики, если она требуется (п. 3.14), порядок выбора следующий:

1. Наиболее длинный active/retired-retained префикс, отличный от `/`; retired обрабатывается до выбора версии по п. 3.26; корневой frontend рассматривается отдельно только после исключения зарезервированных API-путей по п. 3.17.
2. Сервис-владелец; для внешнего shared path — round-robin среди доступных владельцев. Для подписанного межсервисного запроса рассматривается только явно указанный target при том же наиболее длинном совпадении; обход чужого вложенного маршрута через более короткий префикс запрещён.
3. Stable/canary версия по политике выбранного сервиса.
4. Готовый экземпляр выбранной версии по стратегии сервиса: round_robin по умолчанию либо выбранный primary в active_passive (п. 3.18), независимо от QUIC/WSS.

Если после выбора версии её экземпляр исчез до отправки запроса, допускается выбрать готовый резерв той же версии; при отсутствии такового применяется `503`. Нельзя скрыто перенормировать доли или направить запрос в другую версию/сервис. При отсутствии активных владельцев shared path также возвращается `503`.

До начала отправки разрешено выбрать другой активный экземпляр той же версии. После начала передачи запроса автоматический повтор запрещён для всех методов: операция могла уже выполниться. Сбой транспорта до отправки внешних response headers даёт `502` (таймаут — по п. 5.6); после их отправки поток завершается с ошибкой без подмены статуса.

### 3.4. Обнаружение версий

- `version` задаётся клиентом через `WithVersion` и не извлекается из необязательных metadata. Значение — непробельная строка длиной до 128 байт без управляющих символов. Порядок SemVer и понятие «самая новая» автоматически не вычисляются.
- Новая версия обнаруживается только после успешной авторизованной регистрации хотя бы одного экземпляра. Обнаружение образов до запуска или сканирование CI/CD не входит в прототип.
- Шлюз хранит для пары `(service_id, version)` поля `first_seen`, `last_seen` (время последней успешной регистрации), число активных экземпляров и зарегистрированные ими пути/транспорты. После отключения всех экземпляров запись остаётся видимой с нулевым активным числом; в development до перезапуска, в production — в control state с административным сроком хранения.
- Появление новой версии фиксируется структурированным событием `service_version_discovered`. Отклонённая регистрация не создаёт обнаруженную версию.
- Версия, не назначенная stable или canary, получает 0% трафика. Её новые пути резервируются как pending и видны администратору, но не публикуются в таблице активной маршрутизации. Кандидат с новым более длинным префиксом не может перекрыть работающий маршрут stable. Активация новых путей требует отдельной административной операции п. 5.5.3; `503` при отключении относится к уже активированным маршрутам.
- Начальная stable-версия каждого разрешённого сервиса задаётся в YAML. Первое подключение новой версии не меняет stable автоматически.

### 3.5. Канареечное распределение

- Политика действует на весь `service_id`, одинаково для обоих транспортов и всех его путей: `stable_version`, необязательная `canary_version`, целое `canary_percent` от 0 до 100. Доля stable равна `100 - canary_percent`.
- Версии stable/canary должны различаться. Без canary допускается только `canary_percent: 0`. Неуказанные версии получают нулевую долю.
- Версия выбирается независимым взвешенным случайным выбором на каждый HTTP-запрос, затем применяется round-robin либо active-passive среди экземпляров этой версии. Sticky sessions, маршрутизация по cookie/заголовку и гарантия точной доли в малой выборке не входят в прототип.
- Новую политику администратор задаёт через защищённый Admin API. Изменение атомарно; каждый новый запрос использует один согласованный снимок политики. Уже начатые запросы, SSE-потоки и WebSocket-соединения не переключаются.
- Для включения положительной доли новой версии или её продвижения должны существовать активные экземпляры, в совокупности покрывающие все известные маршруты этого сервиса. Проверка выполняется при изменении политики; последующие отказы обрабатываются через `503`, без автоматического отката.
- Администратор должен иметь возможность установить canary 0%, в том числе когда canary недоступна. Дренирование и удаление экземпляров не меняют политику автоматически.
- **Продвижение:** текущая canary становится stable, предыдущее stable сохраняется как `previous_stable_version`, canary очищается, её процент обнуляется. Продвижение без canary возвращает `409`.
- **Откат во время канарейки:** canary очищается, stable сохраняется и получает 100%.
- **Откат после продвижения:** при отсутствии canary восстанавливается `previous_stable_version` с 100%, если она активна и покрывает маршруты; поле previous очищается. Если цели нет — `409`. Переход на иные версии выполняется явным PUT политики.
- Продвижение и откат меняют только распределение новых запросов. Шлюз не запускает и не останавливает процессы/контейнеры сервиса.
- В development политики Admin API и история находятся в памяти и сбрасываются к YAML при перезапуске. В production изменения атомарно сохраняются до успешного ответа API; при рестарте используется последнее подтверждённое состояние, а не более старая начальная политика YAML. Ошибка восстановления состояния не вызывает сброс к defaults: readiness=false, обслуживаемый трафик получает `503`.

### 3.6. Передача HTTP и заголовки

- Оба транспорта **ДОЛЖНЫ** передавать метод, исходный путь/query, Host, многозначные заголовки, тело, статус и end-to-end response headers. Тела передаются потоково с ограниченной памятью; HTTP/1.1 chunked framing не переносится буквально в HTTP/3 или WSS.
- Поддерживаются обычные ответы, SSE с `http.Flusher` и WebSocket handshake со статусом `101 Switching Protocols`. Для обычных HTTP-ответов требуются финальные статусы `200–599`; остальные informational responses `1xx` (включая проксирование `100 Continue`) и HTTP trailers не входят в обязательный контракт. Внешний `Expect: 100-continue` обрабатывается локальным HTTP-сервером шлюза.
- Для обычного HTTP hop-by-hop заголовки, включая указанные в `Connection`, удаляются; CR/LF в значениях не допускаются. Для распознанного WebSocket handshake `Connection: Upgrade` и `Upgrade: websocket` передаются/формируются отдельно по правилам п. 3.11; произвольные hop-by-hop заголовки сохранять запрещено. Redirect upstream не должен автоматически следоваться шлюзом.
- Шлюз формирует `X-Forwarded-For`, `X-Forwarded-Proto`, `X-Forwarded-Host` из фактического внешнего соединения; поступившие от клиента значения по умолчанию заменяются. В production допускаются только явно настроенные trusted proxy CIDR; для них forwarded IP проверяется по доверенной цепочке. Без этой настройки используются фактические socket peer и TLS, а входящие forwarded values заменяются.
- `X-Request-ID` сохраняется, если содержит один безопасный идентификатор до 128 байт, иначе генерируется. Он возвращается клиенту для всех ответов, включая ошибки и fallback.
- При передаче в туннель шлюз заменяет `X-Forwarded-Prefix` выбранным публичным префиксом, а `X-Tunnel-Instance` и `X-Tunnel-Version` — выбранными значениями; `traceparent` передаётся как end-to-end заголовок. `Authorization` и Cookie приложения сохраняются. Внешние `X-User-ID`, `X-User-Roles` и настроенные доверенные атрибуты удаляются до передачи API или SPA; их доверенное межсервисное заполнение определяется п. 3.14–3.15.
- Лимит тела применяется при чтении потока, даже без `Content-Length`, отдельно к запросу и ответу. Превышение тела запроса даёт `413` и отмену обработки; слишком большой ответ до отправки headers — `502`, после них — разрыв потока. Полное буферизование ради проверки размера запрещено.
- Таймаут ожидания response headers отделён от idle timeout тела. Полный deadline запроса по умолчанию отключён; активный SSE не обрывается только из-за общей длительности. Idle timeout сбрасывается при передаче данных.

### 3.7. Жизненный цикл и backpressure

- Клиент автоматически переподключается только выбранным транспортом с exponential backoff и jitter и повторяет регистрацию. Ошибки аутентификации, версии протокола, прав и некорректных полей считаются невосстановимыми; временная недоступность и дубликат ещё не очищенного instance ID — восстанавливаемыми.
- Ограничение конкурентной обработки задаётся через `WithMaxConcurrentRequests`, по умолчанию 100 на клиент. Каждый открытый WebSocket занимает один слот до закрытия соединения, даже если handler завершился после Hijack. При превышении клиент отвечает `429` до Upgrade, не ставя запрос в неограниченную очередь; этот ответ не вызывает повтор или смену версии.
- Отмена внешнего request context и таймауты должны отменять соответствующий обработчик, чтение/запись тела и освобождать ресурсы, не закрывая другие запросы туннеля.
- При graceful shutdown клиента он объявляет `unregister`/drain: шлюз перестаёт выбирать сессию для новых запросов, но позволяет текущим завершиться в пределах deadline `Close`. Отмена контекста `Run` запускает тот же процесс с настроенным ограничением времени. `Close` идемпотентен.
- При graceful shutdown шлюза readiness выключается, новые регистрации и HTTP-запросы не принимаются, сессиям отправляется `reconnect` с признаком drain. Активные запросы завершаются в течение 30s по умолчанию; после этого потоки отменяются и соединения закрываются.
- Клиент не создаёт вторую активную сессию с тем же instance ID: повторное подключение начинается после закрытия старой сессии. После обнаруженного разрыва все её активные запросы завершаются ошибкой и очищаются.

### 3.8. Наблюдаемость

Обязательные Prometheus-метрики прототипа:

- `outgate_tunnels_active{service_id,instance_id,version,transport}`;
- `outgate_requests_total{service_id,version,transport,method,status}`;
- `outgate_request_duration_seconds{service_id,version,transport}` — histogram;
- `outgate_tunnel_reconnects_total{service_id,version,transport}`;
- `outgate_registration_failures_total{reason,transport}`;
- `outgate_websocket_connections_active{service_id,version,transport}`;
- `outgate_websocket_connection_duration_seconds{service_id,version,transport}` — histogram от успешного handshake до закрытия;
- `outgate_instance_role{service_id,version,instance_id,role}` — gauge, role из primary/standby/unavailable для active-passive;
- `outgate_instance_switches_total{service_id,version,reason}` — reason из disconnect/not_ready/drain/revoked/manual/preempt;
- `outgate_service_version_discoveries_total{service_id}`;
- `outgate_rollout_changes_total{service_id,action}` — `action` из `update`, `promote`, `rollback`.

WebSocket handshake учитывается в `outgate_requests_total` со статусом `101` либо HTTP-статусом отказа; `outgate_request_duration_seconds` для него измеряет время до завершения handshake. Длительность открытого соединения и число активных соединений учитываются отдельными WebSocket-метриками.

`transport` ограничен значениями `quic`, `wss`, `upstream`, `none`; последние два применимы к HTTP-метрикам fallback и ошибок до выбора туннеля. Метки не включают request ID, сырой URL или текст ошибки. Неизвестные HTTP-методы агрегируются как `other`; значения service/version ограничиваются реестром и административными лимитами, серии не должны бесконечно накапливаться при смене instance ID.

Структурированные JSON-логи содержат применимые поля `ts`, `level`, `event`, `request_id`, `service_id`, `instance_id`, `version`, `transport`, `path`, `status`, `duration_ms`. Регистрации, отказы, обнаружение версий и изменения политик записываются в аудит; токены и тела не логируются. Аудит изменения политики содержит старое и новое состояние без секретов.

`/healthz`, `/readyz` и `/metrics` расположены на служебном слушателе, не конкурируют с маршрутами сервисов. Readiness означает, что конфигурация загружена, все включённые слушатели работают, обязательные для выбранного режима state/replay/identity-зависимости готовы и shutdown не начат; отсутствие подключённых сервисов само по себе не делает шлюз неготовым. Полный OTLP export опционален; проброс `traceparent` обязателен уже в прототипе.

### 3.9. Admin API

Admin API работает на отдельном адресе. Development использует отдельный bearer-токен и loopback; production требует выделенного admin CA, mTLS и индивидуальных principals/RBAC по п. 5.5.6. На удалённом адресе обязателен HTTPS с TLS 1.3. Без корректного токена возвращается `401`; токен сервиса не даёт административных прав.

| Метод и путь | Назначение |
| :--- | :--- |
| `GET /admin/tunnels` | Активные/дренируемые экземпляры: сервис, версия, пути, транспорт, состояние |
| `GET /admin/routes` | Владельцы известных путей и активные экземпляры, включая недоступные маршруты |
| `GET /admin/services/{service_id}/versions` | Обнаруженные версии, first/last seen, роли и активные экземпляры |
| `GET /admin/services/{service_id}/rollout` | Текущая политика, previous stable, время изменения |
| `PUT /admin/services/{service_id}/rollout` | Атомарная замена stable/canary и процента |
| `POST /admin/services/{service_id}/rollout/promote` | Продвижение canary |
| `POST /admin/services/{service_id}/rollout/rollback` | Откат по правилам п. 3.5 |

Пример PUT и полей политики в успешном ответе:

```json
{
  "stable_version": "1.4.2",
  "canary_version": "1.5.0",
  "canary_percent": 10
}
```

Для отключения canary передаются `canary_version: null` и `canary_percent: 0`. Общие headers/revision/reason/idempotency по п. 3.23 обязательны и не повторяются в сокращённом rollout-примере. Успешные изменения возвращают `200` и итоговый снимок политики; POST-команды promote/rollback не требуют тела, но требуют общие mutating headers по п. 3.23. Весь запрос валидируется до изменения состояния. Административные изменения сериализуются; в production expected_revision предотвращает silent overwrite, последний успешно применённый снимок определяет последующую политику.

Неизвестный сервис даёт `404`, некорректное тело/процент — `400`, необнаруженная или недоступная целевая версия/недостаточное покрытие маршрутов — `409`. Ошибка возвращается как Problem Details с code/reason и безопасным detail по п. 3.23. Начальный YAML может ссылаться на ещё не подключённую stable-версию; требования об активности относятся к административному включению новой цели.

Для production обязательны принудительное отключение экземпляров, отзыв credentials, постоянное control state и ограничения административного доступа по п. 5.5. Admin CLI остаётся необязательным; отдельный Admin Web и редактор access policies обязательны по п. 3.19–3.20. Этот API не управляет пользовательскими сессиями или списком защищённых endpoints API-сервисов; rollout endpoints не выдают межсервисные секреты и не меняют security policies; редактор межсервисных прав использует отдельные endpoints п. 3.20; production расширения отзыва/импорта п. 5.5.6 доступны только соответствующим административным ролям. Межсервисная подпись не предоставляет административных прав.

### 3.10. Публичный API Go-клиента

SDK поставляется отдельным Go module/repository [solodyagin/outgate-sdk](https://github.com/solodyagin/outgate-sdk); планируемый прикладной package — `github.com/solodyagin/outgate-sdk/outgateclient`. Сейчас реализован только `protocol/v1`; прикладной API и versioned release ещё отсутствуют. Прикладные сервисы не импортируют код gateway; выдаваемый самостоятельный boilerplate и правила зависимостей описаны в п. 10.3 и [service-development.md](service-development.md).

```go
package outgateclient

// config — внутренняя конфигурация клиента.
type Option func(*config) error
type Client struct { /* внутренние поля */ }

// gatewayAddr — hostname:port без схемы и пути.
```

### 3.11. Прозрачный WebSocket приложения

- Разработчик **ДОЛЖЕН** иметь возможность передать существующий WebSocket `http.Handler` через `WithHandler` без изменений его handshake и обмена сообщениями и без знания выбранного транспорта. Совместимость проверяется с `gorilla/websocket` и `coder/websocket`. Origin-политика, авторизация пользователя и прикладные ограничения самого сервиса сохраняются; прозрачность не означает их обход.
- Клиентская библиотека предоставляет обработчику HTTP/1.1-окружение с рабочим `http.Hijacker` и двунаправленным `net.Conn`, поддерживающим чтение, запись, закрытие и deadlines. Обычный HTTP/3 ResponseWriter не является достаточным для этой гарантии. Внутреннее виртуальное HTTP/1.1-соединение не требует публичного или дополнительного настроенного порта сервиса; его создаёт библиотека.
- Шлюз передаёт исходные Host, Origin, Cookie, Authorization, query, `Sec-WebSocket-Key`, `Sec-WebSocket-Version`, subprotocols и extensions, а также служебные заголовки п. 3.6. Токен туннеля не заменяет пользовательский Authorization и не попадает в прикладной handler. Выбранный subprotocol, `Sec-WebSocket-Accept`, согласованные extensions и response headers возвращаются от сервиса; шлюз проверяет корректность Upgrade-ответа перед подтверждением внешнему клиенту.
- Шлюз возвращает внешний `101` только после успешного handshake обработчика. Отказ обработчика, например `401`, `403` или `429`, передаётся как обычный HTTP-ответ. Истечение handshake timeout даёт `504`, сбой туннеля — `502`, отсутствие выбранного экземпляра — `503`; после отправки `101` HTTP-статус изменить нельзя.
- После handshake передаются сырые байты RFC 6455 в обоих направлениях с сохранением маскирования, границ/порядка сообщений, фрагментации, text/binary, Ping/Pong и Close с кодом и причиной. Канальные чанки туннеля не обязаны совпадать с WebSocket-фреймами. Сообщения не преобразуются в JSON и не буферизуются целиком; поддерживается согласованный приложением `permessage-deflate` без переписывания payload шлюзом.
- Путь, сервис, версия и экземпляр выбираются один раз при handshake по общей политике. Процент canary применяется к новым соединениям, а не к отдельным сообщениям. Перенос открытого WebSocket, повтор handshake после начала его передачи и автоматическое восстановление WebSocket приложением шлюза запрещены. После разрыва туннеля переподключение браузера выполняет приложение; его новое соединение может попасть в другую версию.
- Для WebSocket действуют отдельные `handshake_timeout` (10s), `idle_timeout` (по умолчанию 0 — отключён) и `write_timeout` (10s ожидания заблокированной записи). HTTP body-size limits, body idle timeout и общий HTTP deadline не ограничивают суммарный объём/длительность уже открытого WebSocket. Прикладной handler отвечает за лимиты сообщений. Ограниченная память обеспечивается чанками, flow control и ограничением числа соединений.
- Закрытие, ошибка или отмена отдельного соединения освобождает его слот, потоки и goroutine, не закрывая исправный туннель. Буферизованные байты после handshake/Hijack не должны теряться. Keepalive туннеля не подменяет Ping/Pong приложения.
- Открытые WebSocket учитываются при drain даже после возврата из handler. При graceful shutdown новые соединения не назначаются дренируемому экземпляру; существующие могут завершиться до shutdown deadline, после которого библиотека/шлюз принудительно закрывает их и освобождает ресурсы. Неограниченно ждать закрытия долгоживущего соединения запрещено.
- Для пути вне конкретных зарегистрированных маршрутов и `/api` WebSocket прозрачно проксируется в выбранный корневой frontend-туннель либо frontend-upstream с сохранением его правил handshake; неизвестный путь внутри `/api` даёт `404`. Политика canary сервисов на frontend fallback не распространяется. Межсервисная идентичность проверяется при handshake, действует на всё соединение и не перепроверяется для каждого сообщения; подпись handshake не проверяется для каждого сообщения. В production отдельно обязателен контроль срока/отзыва пользовательской сессии по п. 5.5.4; новые подключения всегда проходят новую проверку.

### 3.12. Аутентификация и авторизация в API-сервисах

- Регистрация префикса `/api/v1`, `/api/v2` и т. д. не означает, что все его endpoints защищены одинаково. Публичность маршрутов, проверка токена/сессии пользователя, роли и прикладные права определяются middleware и handler самого API-сервиса.
- Шлюз не хранит список пользовательских login/public/private endpoints и не вызывает auth-сервис перед каждым запросом. Автоматическая цепочка «auth → API» не входит в эту версию.
- Различаются три вида полномочий: credential регистрации туннеля; пользовательская аутентификация в API; credential и политика межсервисного доступа. Они не заменяют друг друга и admin token.
- Для обычного внешнего запроса наличие `X-User-ID`/`X-User-Roles` не подтверждает пользователя: шлюз удаляет их и все настроенные доверенные атрибуты, сохраняя пользовательские Authorization/Cookie. API после успешной проверки устанавливает контекст через `WithUserContext`; эти значения не читаются библиотекой из произвольных входящих заголовков.
- Для проверенного межсервисного запроса библиотека получателя предоставляет `UserContextFromContext` и `CallerServiceFromContext`. API самостоятельно решает, достаточно ли этих утверждений для конкретной операции; `WithUserContext` не является автоматическим обходом прикладной авторизации.

### 3.13. Независимое обновление SPA

- Корень `/` обслуживает отдельный frontend-upstream либо назначенный frontend-сервис через QUIC/WSS; сборка SPA не встраивается в бинарник шлюза. Frontend можно обновлять независимо, без пересборки шлюза. Туннельному варианту не нужен входящий порт, доступный шлюзу.
- Шлюз сначала выбирает конкретные активированные маршруты, затем применяет запрет API fallback, затем рассматривает разрешённый корневой tunnel override и, если он не установлен, frontend-upstream. Сам факт разрешения override не отключает upstream до успешной корневой регистрации. Правила владения и отключения приведены в п. 3.17.
- Frontend-сервер предоставляет `index.html` для клиентских маршрутов SPA и `404` для отсутствующих статических ресурсов; frontend fallback не изменяет статусы API. Настройка SPA fallback принадлежит frontend-серверу, шлюз не заменяет любой ответ `404` HTML-файлом.
- Развёртывание сборки атомарное: HTML и соответствующие ресурсы публикуются согласованно. Ресурсы предыдущей сборки сохраняются на период обновления активных клиентов; переключение каталога/версии не оставляет смешанную неполную сборку.
- Для `index.html` frontend задаёт `Cache-Control: no-cache` и валидатор ETag или Last-Modified; ресурсы с хешем содержимого в имени могут получать длительный `max-age` и `immutable`. Шлюз сохраняет эти заголовки, не кеширует API как статику и не включает статический SPA-upstream в canary API-сервисов; корневой frontend-туннель использует собственную rollout-политику назначенного сервиса.

### 3.14. Межсервисные HTTPS-вызовы

- `Client.ServiceHTTPClient(gatewayURL)` создаёт `*http.Client` с подписывающим RoundTripper и отдельным пулом HTTPS-соединений к публичному слушателю шлюза в development либо выделенному service mTLS listener в production. Это не запрос внутри исходящего QUIC/WSS-туннеля вызывающего сервиса. URL не должен содержать userinfo, query или fragment; принимается HTTPS origin без прикладного пути.
- `WithTargetService` задаёт получателя в request context. Request URL содержит этот же HTTPS origin и исходный путь/query получателя. Чужой origin, отсутствие target, некорректный контекст или отсутствие ключа подписи вызывают локальную ошибку без сетевой отправки. Используется проверка сертификата сервера; следование redirect отключено (`http.ErrUseLastResponse`).
- RoundTripper клонирует request/headers, берёт идентичность отправителя из `WithServiceID`, пользовательский контекст — только из context, формирует заголовки и подписывает их. Тело не читается заранее. Исходные запросы, заголовки и UserContext не мутируются; роли/атрибуты копируются при помещении в context.
- В development шлюз отличает межсервисный вызов на публичном HTTPS по зарезервированным Outgate-полям и подписи профиля п. 4.6. В production для этого используется отдельный mTLS listener; публичный browser listener не принимает такие credentials. Если такие поля/подпись предъявлены, ошибка проверки не должна превращать запрос в обычный внешний. Внешние запросы без них обслуживаются как пользовательские по п. 3.12.
- Шлюз проверяет caller credential, target и YAML-политику `caller → target → paths/methods`; отсутствие разрешения означает `403`. Каждое правило отдельно разрешает вызовы с пользовательским контекстом (`allow_user_context`) и без него (`allow_background`). Разрешение делегирования не выдаётся автоматически из права регистрации пути.
- Проверка политики использует нормализованный путь и границы сегментов п. 3.3; подпись покрывает исходные path/query без изменения их байтового представления. Методы сопоставляются явно, без wildcard по умолчанию.
- Целевой сервис должен владеть наиболее длинным зарегистрированным маршрутом. Для shared path выбирается только указанный target; при чужом вложенном маршруте возвращается `403`, при отсутствии целевого зарегистрированного маршрута/активного экземпляра — `503`. В SPA, другого владельца или более короткий префикс межсервисный запрос не попадает. Canary и round-robin целевого сервиса сохраняются.
- После проверки шлюз удаляет входящую Outgate-подпись/служебные поля, заново формирует доверенные заголовки, выбирает версию/экземпляр и подписывает итоговый запрос отдельным ключом получателя. Его библиотека проверяет подпись, target и привязку к собственному instance/version до handler; некорректный доверенный контекст отклоняется, а не становится внешним запросом.
- При фоновой операции остаётся caller identity, но `X-User-ID`, `X-User-Roles` и пользовательские Attributes отсутствуют. Нет фиктивного пользователя «system». Отсутствие пользователя не даёт полномочий автоматически: API проверяет права сервисной операции.
- Следующий вызов B → C может наследовать проверенного пользователя A → B из context, но caller становится B, а разрешения проверяются заново для B → C. Входящие Authorization/Cookie и произвольные заголовки автоматически не копируются; их явная передача остаётся решением приложения.
- HMAC подтверждает отправителя HTTP-запроса, но не истинность заявленных им ролей. Development допускает делегирование локального UserContext доверенным API. В production пользовательские claims выводятся только из подписанного утверждения настроенного issuer (п. 5.5.4), а не из произвольных значений вызывающего сервиса. Шлюз не проверяет пароли и не вызывает auth endpoint перед каждым запросом.
- Просроченная/неверная/повторная подпись возвращает `401`; запрет цели или делегирования — `403`; исчерпание replay-кеша — `503` с `Retry-After: 1`. Ответы не запускают автоматический повтор отправленного запроса; потоковые запросы не воспроизводятся HTTP-клиентом прозрачно.
- Отмена context отменяет HTTPS-запрос и его обработку через туннель; нормальная работа входящей сессии не зависит от отдельного исходящего запроса. Закрытие клиента прекращает новые межсервисные вызовы и закрывает idle HTTPS-соединения; текущие вызовы ограничены shutdown deadline.

### 3.15. Доверенные заголовки и ключи

- Обязательные поля пользовательского контекста: один непустой `X-User-ID` и один `X-User-Roles` с компактным JSON-массивом строк (включая `[]`, если ролей нет). При отсутствии пользователя оба заголовка отсутствуют. Частичный контекст, дубли полей, CR/LF, превышение лимитов или неизвестный дополнительный атрибут отклоняются.
- `Attributes` — карта заранее разрешённых логических имён в заголовки, например `tenant_id → X-User-Tenant-ID`. Значения строковые; имена из allowlist не могут перекрывать Authorization, Cookie, Host, hop-by-hop, Signature, Outgate-метаданные и обязательные поля. ID, роли и атрибуты — UTF-8 строки без управляющих символов; точное допустимое HTTP-кодирование фиксируется профилем п. 4.6.
- По умолчанию user ID ограничен 128 байтами, число ролей — 32, каждая роль — 64 байтами, число дополнительных атрибутов — 16, значение атрибута — 1024 байтами, весь сериализованный пользовательский контекст — 8 KiB. Лимиты проверяются библиотекой, шлюзом и получателем до выделения неограниченных буферов.
- У отправителя есть активный HMAC-ключ исходящей подписи; шлюз принимает его по `(service_id, key_id)`. У шлюза есть отдельный активный ключ подписи для каждого получателя, у библиотеки получателя — принимаемый набор соответствующих ключей. Секреты направлений и сервисов не переиспользуются между собой или как tunnel/admin token.
- Ключ содержит `key_id` и не менее 32 случайных байт секрета. В конфигурации задаётся ровно один источник: `secret_env` либо `secret_file`; содержимое — base64 секрета. Неразрешённый источник, некорректная кодировка, короткий секрет или дубли ключей — ошибка запуска. API/логи показывают только ID, никогда секрет или полную подпись/пользовательские заголовки.
- Для ротации сначала получатели/шлюз получают набор старого и нового ключей, затем отправители переключают активный ключ. Старый ключ удаляется после окончания допустимого окна подписей и обработки ранее принятых запросов; конфигурация ключей прототипа загружается при запуске. Статические ключи не изменяются через rollout Admin API.
- Клиент настраивается через `WithServiceSigningKey` и `WithGatewayVerificationKeys`. Первый нужен для исходящих вызовов, второй — для получения межсервисных запросов; production дополнительно настраивает issuer/replay/revocation verifier и mTLS/grants по п. 5.5; внешние-only сервисы могут не иметь этих опций. Подписанный входящий запрос без принимаемого ключа не должен попасть в handler. Проверка выполняется и для виртуального HTTP/1.1/WebSocket-канала.

### 3.16. Монтирование сервиса под настраиваемым префиксом

- Разработчик сервиса не обязан заранее знать публичный mount point. Deployment передаёт пути в `WithPaths` из env/YAML; `WithStripPrefix(true)` позволяет использовать `mux.HandleFunc("/hello", ...)` при внешнем `/api/v1/hello`, `/api/v2/hello` или другом разрешённом префиксе. Переезд требует изменения конфигурации/регистрации, но не исходного кода handler.
- По умолчанию действует preserve для совместимости обработчиков, уже принимающих `/api/v1/hello`. Strip включается явно; один режим применяется ко всем путям клиента. Несколько префиксов такой сессии — алиасы одного локального корня, а не разные локальные каталоги. Явные отображения нескольких внешних путей в разные внутренние base paths в эту версию не входят.
- Шлюз выбирает маршрут, сервис, версию и экземпляр по исходному публичному пути. Он передаёт выбранный нормализованный префикс в `X-Forwarded-Prefix`, заменяя внешний одноимённый заголовок. Для SPA-upstream fallback заголовок удаляется. Для корневого frontend-туннеля X-Forwarded-Prefix равен `/`; нормализация и strip для такого mount являются тождественными: `/assets/app.js` остаётся `/assets/app.js`, Path/RawPath/RequestURI и cookie Path не получают двойного `/`. Клиент проверяет, что префикс действительно зарегистрирован сессией и совпадает с путём по границе сегмента; вычислять его заново по одному только URL запрещено.
- Библиотека сначала проверяет подпись и пользовательский контекст на исходном URI, затем клонирует request для handler и удаляет ровно выбранный префикс. `/api/v1/hello?q=1` превращается в `/hello?q=1`, `/api/v1` и `/api/v1/` — в `/`. Автоматический redirect ради добавления завершающего `/` не выполняется.
- `URL.Path`, `URL.RawPath` при наличии и `RequestURI` должны согласованно отражать локальный путь; query, его порядок/escaping и признак пустого query сохраняются. Дополнительное декодирование, `path.Clean` и удаление другого, более короткого/длинного префикса запрещены. Невалидный mount metadata отклоняется до handler.
- `MountInfoFromContext` возвращает выбранный префикс и исходный RequestURI в обоих режимах. В strip сервис видит локальный путь, но может получить публичный путь для логирования и генерации адресов; `X-Forwarded-Prefix` также доступен. Копирование входящего context в следующий межсервисный вызов не применяет входящий mount к адресату: его публичный URL задаётся отдельно конфигурацией вызова.
- Локальная маршрутизация, public/private middleware и проверка прав пользователя в handler работают с локальным путём. Разрешения регистрации, межсервисная paths/methods policy, request signatures, выбор canary и gateway-логи используют публичный путь. Строка `/api/v1` в mount-конфигурации по-прежнему не является полем версии сборки.
- В strip по умолчанию включена обработка response headers шлюзом для выбранной сессии. Ссылки `Location` без scheme/authority разрешаются относительно локального URL запроса, затем к локальному результирующему пути добавляется mount-префикс; query/fragment сохраняются. Например, локальный `Location: /login` становится `/api/v1/login`. Относительный `login` на локальном `/` также становится `/api/v1/login`, в том числе при внешнем запросе точно к `/api/v1` без завершающего `/`.
- Абсолютные URL и network-path ссылки `//host/path` в `Location` сохраняются как явно заданные приложением. Значения обрабатываются как локальные: повторно добавлять публичный префикс в handler при включённой обработке нельзя. Ответ с невалидным/небезопасным Location отклоняется до отправки headers. Header `Refresh`, Link и URL внутри HTML/JSON/CSS/JS автоматически не переписываются.
- В отдельных `Set-Cookie` сохраняются все атрибуты и отдельность заголовков, но явно заданный локальный `Path=/` превращается в `<prefix>`, `Path=/session` — в `<prefix>/session`; отсутствие Path и Domain не меняются. Например, Path `/api/v1` подходит точному mount и его дочерним путям, но не `/api/v10`, согласно границам cookie path-match. У cookie `__Host-` обязательный Path=/ сохраняется, такая cookie остаётся общей для хоста; это исключение отражается в документации. Клиентские имена cookie разных сервисов должны исключать коллизии.
- Приложение может отключить обработку заголовков через `WithMountResponseRewrite(false)` и формировать публичные Location/Path самостоятельно с использованием MountInfo. В preserve обработка выключена; явное включение её без strip отклоняется при создании клиента. Структура и содержимое response body и WebSocket-сообщений не меняются.
- В virtual HTTP/1.1 для WebSocket обработчик также получает локальный путь; проверка outgategateway выполняется до strip. Gateway обрабатывает Location отказов и Set-Cookie handshake по тем же правилам; `Sec-WebSocket-*`, Origin и сырой обмен не переписываются. SSE и потоковые тела не буферизуются для преобразования пути/headers.
- Mount-параметры публикуются в Admin API routes/tunnels, чтобы оператор видел публичный префикс и режим. При неизвестном API-маршруте сохраняется `404`, при недоступном зарегистрированном — `503`; strip не создаёт обхода чужого вложенного маршрута или fallback в SPA.

### 3.17. Разрешённое перекрытие SPA-upstream корневым сервисом

- Администратор задаёт `frontend_override.enabled` и ровно один `frontend_override.service_id`. По умолчанию override выключен. Для указанного ID должна существовать конфигурация services с явным `allowed_paths: ["/"]` (или списком с этим точным элементом), начальной rollout-политикой и отдельным tunnel credential.
- Регистрация `/` разрешена только при enabled=true и совпадении подтверждённого credential service_id с назначенным frontend. Одного знания service_id или instance_id недостаточно; в production также требуются соответствующие mTLS identity и deployment grant: чужой токен с заявленным именем frontend отклоняется. У обычного сервиса запрос `/` даёт `path_forbidden`; отказ всего набора путей атомарен.
- `/` не может быть shared path и не выдаётся нескольким service_id. Allowed `/` у frontend не разрешает регистрировать `/api`, `/api/v1`, `/assets` или другие поддеревья: дополнительные пути требуют отдельных разрешений. Корневой маршрут обслуживает остаточный трафик, а не перехватывает зарегистрированные пути других сервисов.
- Корневой frontend подключается любым включённым транспортом. Допускаются несколько его экземпляров и версий: canary выбирает версию, а round-robin либо active-passive — экземпляр внутри назначенного service_id, включая смешанный QUIC/WSS. Текущий статический upstream в это распределение не включается.
- Порядок внешней маршрутизации: конкретный зарегистрированный маршрут → `404` для неизвестного зарезервированного API-пути → известный корневой frontend-туннель → SPA-upstream. Известный конкретный маршрут без доступного экземпляра даёт `503`, не корневой frontend. Если выбранная canary-версия frontend недоступна, возвращается `503`, без изменения её доли или перехода в upstream.
- Пока root override ещё ни разу не активирован, `/` обслуживает SPA-upstream. В development его устанавливает первая успешная регистрация `/`; в production требуется административная активация, а её состояние сохраняется между перезапусками. При отключении/дренировании всех экземпляров право владения `/` сохраняется (в development до перезапуска, в production в control state): новые frontend-запросы получают `503` с `Retry-After: 1`, а не другую сборку из upstream. Возврат к старому SPA при отказе туннеля не выполняется автоматически.
- Для планового возврата к upstream в development администратор устанавливает enabled=false и перезапускает шлюз. В production security_admin выполняет устойчивую операцию PUT /admin/frontend-override с revision; она меняет backend только для новых запросов, не требует сброса состояния и не обрывает уже обслуживаемые соединения. В development после рестарта upstream используется до восстановления корневой регистрации. В production установленный root override восстанавливается из control state и до подключения экземпляров возвращает `503`, без возврата к старой сборке; переход к upstream выполняется только явным административным изменением.
- Запросы/соединения, уже направленные в upstream или туннель, не мигрируют при появлении override. Ответ `404`/ошибка handler не вызывает переключения backend; повтор уже отправленного запроса запрещён. Правила независимого выпуска SPA, cache headers и сохранения assets распространяются на оба варианта. Сборки upstream/override должны иметь согласованную политику доступности старых хешированных ресурсов для открытых вкладок; шлюз не ищет отсутствующий asset в другом backend.
- Корневой frontend не получает доверенный пользовательский контекст или право межсервисных вызовов только из-за регистрации `/`. Для него действуют bearer-auth, allowed_paths, отдельные interservice policies и user-header stripping. Подписанный запрос к другому target не может попасть в frontend как в fallback.
- Admin API routes/tunnels отображает корневой маршрут, service/version/instance/transport и активность. В ответ GET /admin/routes также включается `frontend_override` с enabled, назначенным service_id и состоянием `disabled`, `awaiting_registration`, `active` либо `unavailable`; последнее означает отсутствие положительно взвешенных активных экземпляров. Секреты не раскрываются. Обновления состояния видны в логах регистрации/дренирования/разрыва.
- Конфигурация с неизвестным frontend service_id, отсутствующим явным разрешением `/`, root в shared_paths или allowed `/` у неназначенного сервиса отклоняется при запуске. Отключённый override с сохранённым service_id/allowed `/` допустим, но root-регистрация запрещена до явного включения администратором.

### 3.18. Основной и резервные экземпляры (active-passive)

- Администратор задаёт `services.<id>.instance_routing.strategy`: `round_robin` (default) либо `active_passive`. Настройка сервиса имеет приоритет над общим routing.strategy. В active-passive для каждой обслуживаемой версии задаётся непустой упорядоченный `instance_order`: первый — предпочтительный основной, остальные — резервные в порядке выбора. Для фактического резервирования нужны не менее двух экземпляров; допускается временная работа с одним, что отражается как отсутствие резерва.
- Выбор выполняется отдельно для `(service_id, version)`, после canary, но до назначения экземпляра и подписи outgategateway. Stable и canary не резервируют друг друга. Для положительно взвешенной версии без настроенного order rollout/импорт отклоняется; standby той же версии может использовать любой разрешённый транспорт.
- В active-passive допускаются только instance IDs из order своей версии. Приоритет/роль не задаются клиентским заголовком или metadata; остальные регистрации отклоняются как invalid_register. ID не может повторяться в разных пулах сервиса; global instance uniqueness и production certificate/grant binding сохраняются. Резервные экземпляры имеют те же version, нормализованный набор paths, path_mode и rewrite, что основной этой версии; несовпадение регистрации отклоняется. Публичные маршруты не дублируются как разные владельцы.
- Резерв заранее устанавливает туннель, проходит регистрацию, допуск и readiness; это горячий резерв входящего трафика, а не запуск контейнера по факту отказа. Готовность означает: сессия авторизована/не отозвана, transport жив, экземпляр не в drain, локальная readiness-проверка успешна. HTTP 5xx/429 и медленный отдельный запрос сами по себе не переключают весь пул и не запускают повтор.
- В production active-passive обязателен WithReadinessCheck; отсутствие callback отклоняет регистрацию. В development без callback допускается transport-only готовность, явно обозначаемая диагностикой. Callback проверяет handler и его обязательные зависимости, не публичный пользовательский endpoint; библиотека не открывает для этого входящий порт и не обходит API-аутентификацию HTTP-пробой.
- Шлюз согласует параметры в register_ack: interval=5s, timeout=2s, unhealthy_threshold=3, healthy_threshold=2 по умолчанию. SDK выполняет проверки в фоне; до двух успешных результатов новая сессия not_ready. Три последовательных отказа/timeout делают её not_ready; явный разрыв, отзыв и drain исключают немедленно. Callback обязан учитывать context; SDK не запускает бесконечные goroutine поверх зависшей проверки — одновременно допускается одна, её timeout уже считается отказом.
- SDK передаёт `instance_status` по управляющему каналу QUIC или WSS со state ready/not_ready, монотонным номером в сессии и безопасным reason без секретов. Статус публикуется не реже 5s; отсутствие обновлений 15s делает сессию not_ready, даже если transport Ping/Pong ещё работает. Нарушение sequence/лимитов обрабатывается как protocol error. Transport heartbeat и прикладная readiness решают разные задачи.
- Пока текущий primary готов, все новые запросы выбранной версии направляются только ему. При недоступности/дрейне/отзыве primary шлюз атомарно выбирает первый готовый standby из order; при отсутствии готовых — `503` с Retry-After:1 без очереди неограниченного ожидания. Переключение после обнаружения состояния занимает не более 1s, отдельно от времени его обнаружения. Все одновременно поступающие запросы используют согласованный снимок выбранного primary.
- По умолчанию `preempt=false`: восстановившийся предпочтительный основной остаётся standby, исправный текущий primary не вытесняется. При `preempt=true` более предпочтительный экземпляр может заменить его только после непрерывной готовности `recovery_hold_down` (default 30s); потеря готовности обнуляет выдержку. Это предотвращает постоянные переключения при flapping. Первоначально выбирается лучший из готовых на момент выбора; позднее подключение первого в order при preempt=false не вызывает автоматического возврата.
- До начала передачи запроса допустима повторная выборка экземпляра той же версии; подпись/nonce доставки тогда создаются для окончательно выбранного instance. После начала отправки нет автоматического повтора на standby, включая GET/POST и WebSocket handshake. Уже принятые HTTP/SSE/WebSocket могут завершаться на прежнем экземпляре до его ошибки/срока/отзыва; новые идут новому primary. Миграция соединений/сессий не предоставляется.
- Active-passive управляет только новыми запросами через этот gateway. Он не обеспечивает единственного writer в БД и не останавливает фоновые jobs прежнего primary: возможна одновременная работа уже принятых операций. Для singleton jobs/записи приложение обязано использовать lease/lock с fencing token в своей БД/координаторе. Сервис не начинает фоновые jobs только потому, что получил сетевую роль primary. State, файлы и сессии реплик хранятся во внешнем общем хранилище либо реплицируются средствами приложения; gateway данные не синхронизирует.
- После рестарта шлюза конфигурация пула восстанавливается из control state, но старое соединение не признаётся живым: выбор делается заново среди допущенных/готовых сессий по order. До появления готового primary для активированного маршрута действует `503`. Не гарантируется сохранение последнего runtime primary после рестарта; это не сброс rollout, route ownership или frontend override.
- Production deployer может выполнить `POST /admin/services/{service_id}/versions/{version}/active-instance` с instance_id и expected_revision. Переключение разрешено только в active-passive на зарегистрированный готовый экземпляр своего order с полным покрытием путей; иначе 409. Команда меняет новые назначения, не прерывает старые соединения и не меняет version/проценты. Решение аудируется; для постоянного изменения предпочтения администратор изменяет order через валидированный импорт. Ручное переключение при preempt=true также подчиняется дальнейшей политике возврата.
- GET /admin/tunnels и routes показывают выбранный primary, standby/unavailable, порядок, причину/время последнего переключения и degraded/no_ready_replica. Все живые standby входят в outgate_tunnels_active, но не получают пользовательские запросы до выбора. Counter переключений увеличивается при смене ранее выбранного primary, первоначальный выбор в него не входит. Режим поддерживается для API, root frontend и межсервисных целей; обходы `/api`, caller ACL, canary, quotas и отзывов запрещены.

### 3.19. Отдельный веб-интерфейс администратора

#### 3.19.1. Размещение и границы

- В поставку первой версии входит отдельное приложение `outgate-admin-web`: frontend административной консоли и серверная BFF-часть (backend for frontend). Оно обращается к Admin API шлюза; не читает/не изменяет control/replay state или YAML напрямую. UI не заменяет серверную авторизацию и не становится единственным способом управления: API остаётся доступен разрешённой автоматизации.
- Консоль размещается на отдельном HTTPS origin в management network, например `https://outgate-admin.example.net:9444`, без общих cookies с публичной SPA/API. Её нельзя зарегистрировать как service route `/admin` на публичном домене, отдать через root frontend override или опубликовать обычным service tunnel. Admin API остаётся на изолированном mTLS listener; браузер обращается только к BFF своего origin.
- В production вход выполняется через настроенный административный OIDC provider с Authorization Code + PKCE S256, state и nonce, exact redirect URI и MFA по разрешённому acr/amr профилю. Это отдельный client/audience от пользовательских API assertions. Пароли администраторов приложение не хранит; локальный тестовый вход допустим только в development на loopback.
- Access/refresh tokens, OIDC client secret и mTLS private key BFF хранятся только на сервере; в браузере нет admin bearer tokens, HMAC/service keys или client certificates. Cookie `__Host-outgate-admin` содержит только случайный session ID, имеет Secure/HttpOnly/Path=/ без Domain и SameSite=Strict. Для OIDC callback допускается отдельная короткоживущая Lax-cookie, связанная со state/PKCE и удаляемая после входа. Сессия — не более 8h, idle timeout 15 минут; logout инвалидирует её на сервере.
- BFF соединяется с Admin API своим сертификатом от admin CA, разрешённым только для web delegation, и передаёт проверяемый admin access JWT текущего пользователя. Сам BFF certificate не имеет роли security_admin/deployer. Admin API независимо проверяет issuer, signature, audience `outgate-admin-api`, exp и subject, затем определяет роль по своей административной карте principals. X-User-Roles, роли из JS, cookie публичной SPA и неподтверждённые actor headers не дают административных прав. Headless/CLI principals с индивидуальным сертификатом и токеном продолжают работать отдельно.
- Все операции с изменением состояния требуют synchronizer CSRF token, exact Origin и JSON Content-Type; GET не меняет состояние. CORS для BFF закрыт. CSP без unsafe-inline/unsafe-eval, frame-ancestors 'none', nosniff и Cache-Control:no-store для сессионных/API-ответов обязательны. Тексты service metadata, путей и audit events отображаются как данные с escaping; innerHTML из них недопустим. Service worker консоли отключён.
- Роли viewer/deployer/security_admin проверяются сервером на каждом вызове и не расширяются фронтендом. Security-admin операции требуют свежего MFA-входа не старше 5 минут; при необходимости UI запускает step-up в IdP. Свежесть/assurance проверяет Admin API по подписанным auth_time/acr/amr, а не по отметке времени JS. Удалённая роль/отозванная admin session перестаёт работать не позднее 5s; UI очищает данные и возвращает на вход при 401/403.

#### 3.19.2. Экраны и действия

- **Обзор:** readiness, выбранный режим, transport listeners, ошибки/квоты/state dependencies; показываются недоступность и время актуальности данных, не фиктивное «всё работает» при сбое API. Обновление статусов — по умолчанию раз в 5s с backoff при ошибках.
- **Сервисы и экземпляры:** service/version/instance, transport, mount paths/mode, readiness, primary/standby, drain, сертификат/grant ID и сроки без секретов. Viewer просматривает, deployer активирует разрешённые маршруты и переключает готовый primary, security_admin немедленно отключает/отзывает доступ.
- **Версии и rollout:** stable/canary, проценты, coverage, promotion/rollback и текущая revision. Deployer видит последствия и подтверждает изменение; несогласованная/устаревшая форма получает 409 без потери новой конфигурации.
- **Frontend:** текущий upstream/override, назначенный service_id и состояние root. Только security_admin меняет override через соответствующий API; форма показывает, какой frontend получит новые запросы и что существующие соединения не мигрируют.
- **Межсервисный доступ:** таблица и фильтры caller/target/paths/methods, user delegation/background, internal-only. Viewer/deployer читают, security_admin редактирует по п. 3.20. UI не редактирует пользовательские роли в API, issuer keys, claims пользователя или OAuth permissions самого IdP.
- **Аудит:** кто/когда/что изменил, причина, old/new revision, безопасный diff, результат; доступ по роли. Секреты и полные JWT/подписи не возвращаются браузеру. История изменений позволяет подготовить обратное изменение, но не обойти текущую валидацию.
- Форма не генерирует новые service IDs, trust roots, admin roles или ключи подписи из произвольного текста. Bootstrap identities, источники секретов, CA/IdP endpoints и admin RBAC остаются в защищённой эксплуатационной конфигурации. В первой версии веб-экран grants показывает только метаданные и отзыв; выдача grant secret остаётся CI/защищённому deployment API и не попадает в UI.

### 3.20. Редактирование межсервисных прав через Admin API и UI

- YAML задаёт bootstrap-политики, но в production действующим источником является постоянное control state. Изменение в UI и изменение через автоматизацию идут одним Admin API с одинаковыми RBAC, validation, revision и аудитом. Перезапуск или обычное перечитывание старого YAML не отменяют UI-изменения; config import — отдельная явная security_admin операция.
- Редактор управляет только `policies` (caller/target/paths/methods/allow_user_context/allow_background) и `internal_only`. Правило можно создать, изменить или удалить; неполное/противоречивое правило не применяется. Отсутствие allow rule означает deny; wildcard caller/target/method, корневой path `/` и отключение обязательных issuer/mTLS/HMAC/replay-проверок в редакторе не разрешаются. Доступ к корневому frontend при необходимости задаётся отдельным явным config import, а не случайным «разрешить всем».
- Caller/target выбираются из известных настроенных сервисов, а пути/методы валидируются сервером по публичным путям, не локальному strip view. Новый rule не может выдать регистрацию маршрутов, доступ к Admin API/secret stores или полномочия issuer. Allow_user_context разрешает только проверенное target-specific утверждение; UI не делает доверенными произвольные X-User-*.
- Пользователь сначала редактирует черновик без изменения трафика. Серверная проверка возвращает ошибки, нормализованный diff, добавляемые/удаляемые разрешения, влияние на internal-only и текущие активные потоки. Проверка не вызывает сервисы и не отправляет им тестовые бизнес-запросы.
- Перед применением UI показывает summary, diff, текущую revision, предупреждение о расширении/снятии internal-only, количество потенциально закрываемых потоков и требует явного подтверждения с непустой причиной. Расширение полномочий и ослабление internal-only требуют свежего MFA; в первой версии это правило применяется ко всем изменениям межсервисного доступа. Автоматическое применение при переключении checkbox/закрытии формы запрещено.
- API контракты: `GET /admin/interservice-access` возвращает текущий snapshot и revision; `POST /admin/interservice-access/validate` принимает candidate snapshot и expected_revision, возвращает validation result/diff/preview_id; `PUT /admin/interservice-access` применяет candidate с expected_revision, preview_id и reason; `POST /admin/interservice-access/evaluate` проверяет гипотетические caller/target/path/method и тип контекста без изменения состояния.
- Validate/evaluate доступны viewer для анализа, PUT — только security_admin. Preview связан с hash точного candidate, actor и базовой revision, живёт 10 минут и используется однократно. PUT заново проверяет роль/свежесть MFA, поля и текущую revision: чужой/изменённый/просроченный preview либо новая revision возвращают 409; попытка обхода роли — 403. Проверка не заменяется frontend-only JavaScript validation. Валидация неправильного snapshot — 400 с ошибками полей, неизвестного сервиса — 400; state/audit failure — 503.
- Apply выполняется транзакционно: сохраняет весь набор правил, новую revision и аудит намерения/результата в устойчивую очередь, затем публикует один снимок правил. Частичное обновление не допускается. Успешный ответ 200 содержит итоговый snapshot/revision, но не секреты. Ошибка control/outbox до commit оставляет старую политику без частичной публикации. После commit ответ может потеряться, но изменение уже сохранено: применяется operation lookup/resync по п. 3.23, а не обещание отката. UI не пишет файл YAML и не требует перезапуска gateway.
- Новые запросы после применения проверяются по новой политике. При отзыве/сужении права шлюз переоценивает активные межсервисные WebSocket/SSE и закрывает переставшие быть разрешёнными не позднее 5s. Для текущих обычных запросов выполняется best-effort отмена; это не откатывает уже совершённые бизнес-операции и не инициирует их повтор. Внешние пользовательские соединения не закрываются только из-за изменения interservice allow rules, если не меняется их доступ по internal-only.
- Перевод пути в internal-only запрещает новые внешние запросы и закрывает уже открытые внешние WebSocket/SSE этого пути в пределах 5s. Шлюз хранит необходимые caller/target/public path/method/auth-kind и применённую revision для переоценки; содержимое пользовательских сообщений для этого не логируется. Если endpoint должен стать internal-only, старое внешнее соединение не может сохранить доступ бессрочно.
- Evaluate возвращает allow/deny с причинами и совпавшими правилами для заданного snapshot/revision и явно показывает, что это моделирование policy, а не доказательство наличия credentials/JWT или готовности сервиса. Никакая simulated user identity не становится действительным контекстом запроса. Состав правил, семантика deny-by-default и недопустимость суммирования частичных прав из разных rules совпадают с runtime verifier.
- Восстановление прежнего набора правил создаёт новый candidate из истории, проходит те же validate/preview/confirm/MFA и формирует новую монотонную revision. Старые grants, credentials и уже отозванные user sessions не восстанавливаются такой операцией. UI не предоставляет неконтролируемый «откат всей базы».
- Настройка сертификатов/секретов, смена admin roles, источников issuer и публичных listener addresses не переносится в этот редактор. Ограничение снижает последствия ошибочного клика и не позволяет приложению само выдать себе административную роль.

### 3.21. Состояния и конкурентное использование SDK

- `Client` имеет состояния `created`, `connecting`, `registered`, `ready`, `draining`, `closed`. `New` не открывает соединений и не запускает goroutines. `Run` разрешён ровно один раз за жизнь Client; второй/параллельный вызов возвращает типизированный `already_started`, после Close — `client_closed`. Для нового запуска создаётся новый Client; реконнект внутри единственного Run сохраняется.
- Переходы: `created → connecting → registered → ready`; временный разрыв `registered/ready → connecting`, плановая ротация `ready → draining(credential_rotation) → connecting`, потеря readiness `ready → registered`, штатное завершение `* → draining → closed`. Close во время credential_rotation делает drain окончательным, без нового connect. Невосстановимая ошибка Run прекращает новые назначения, bounded cleanup/drain по классификации security/transport failure завершает Client в closed и возвращает причину; revoke не получает grace сверх security deadline. `registered` означает полученный ack; `ready` дополнительно требует актуальные credentials/revocations, завершённый recovery barrier и успешную локальную readiness. Наличие canary-трафика, route activation или роли primary не является условием готовности экземпляра.
- Добавить `Status() ClientStatus` и `WaitReady(ctx context.Context) error`. Snapshot содержит state, connected/ready_since, transport и безопасный last_error_code без secrets. WaitReady возвращает nil при текущем ready; иначе ждёт, возвращает ctx.Err при отмене ожидания либо terminal error при closed. Он не запускает Run, не обещает, что ready сохранится после возврата, и не блокирует работающий Run. В любом состоянии кроме ready новые ServiceHTTPClient вызовы локально отклоняются с `client_not_ready`/`client_closed`; получать metadata состояния можно до Run.
- Close до Run сразу переводит в closed. Одновременные Close объединяются в одну процедуру; первый Close запускает drain, самый ранний из переданных shutdown deadlines ограничивает общую процедуру, последующие вызовы её не продлевают. Close без deadline использует 30s. Успешный повтор после закрытия возвращает nil. На deadline незавершённые обработчики/потоки отменяются; Close возвращает context.DeadlineExceeded, если потребовалось принудительное завершение. При отмене Run снаружи используется тот же drain, Run при штатном завершении возвращает nil.
- Контексты уже принятых handler не являются прямыми дочерними контекста Run: его отмена прекращает новые назначения, но не отменяет их немедленно до drain deadline. Disconnect, revoke, отмена исходного HTTP request и истечение его собственного deadline продолжают отменять соответствующий handler сразу. WebSocket после Hijack отслеживается до закрытия и также входит в drain.
- Пользовательские handler/callback обязаны учитывать context cancellation и не блокироваться навсегда. SDK держит не более одного незавершённого вызова каждого callback: timeout делает readiness=false, новые вызовы не накапливаются до завершения старого. Go не позволяет безопасно принудительно завершить произвольную goroutine: Close закрывает принадлежащие SDK ресурсы/соединения, но не обещает остановить CPU-loop или сторонний I/O пользовательского кода, игнорирующего context. Это нарушение контракта приложения диагностируется отдельно; тесты отсутствия SDK-утечек используют cooperative callbacks.
- SDK thread-safe для Status/WaitReady/Close и параллельных ServiceHTTPClient запросов. После передачи конфигурации maps/slices копируются; Request/headers/context другого вызова не изменяются. Сетевой код не вызывает пользовательский callback под внутренним mutex. Readiness/credential callbacks имеют отдельный deadline; зависший callback не создаёт неограниченные goroutines. Panic HTTP-handler перехватывается на границе запроса: до headers — безопасный 500, после — закрытие этого потока; stack trace только в защищённом локальном журнале, туннель и другие запросы остаются рабочими.

### 3.22. Логический адрес сервиса и discovery mount points

- Существующий ServiceHTTPClient с публичным path сохраняется. Дополнительно SDK предоставляет NewServiceRequest с параметрами context, gatewayURL, method, target_service, mount_id, local_request_uri и streaming body; результат — `*http.Request` с WithTargetService и выбранным публичным URL. Body не читается при построении. Нет автоматического бизнес-вызова или повтора; запрос отправляется через ServiceHTTPClient отдельно.
- Для логической адресации в регистрации добавляется необязательное `mounts` — map mount_id → один из точных `paths`, опция `WithMounts(map[string]string)`. Mount IDs соответствуют `[a-z][a-z0-9_-]{0,63}`, значения не дают новых прав и включаются в точный grant binding. `/` допустим только для назначенного frontend. Без mounts прежняя регистрация работает, но discovery helper возвращает `mount_not_found`. Один mount_id сервиса имеет один и тот же публичный prefix/path_mode во всех положительно взвешенных версиях; несовместимое включение rollout/маршрута отклоняется с 409. Кандидат не переопределяет опубликованный mount.
- `GET /outgate/discovery/services/{service_id}` на service mTLS listener возвращает service_id, активированные mounts и монотонный `route_revision`. Это служебный read-only endpoint до обычного router, не публичный маршрут. В production проверяются certificate/SPKI, действующий grant ID и наличие хотя бы одного caller → target allow rule; произвольный сертификат без действующего допуска недостаточен. Содержимое не включает instances, секреты, JWT или роли пользователей. Development использует собственный service bearer. Полная проверка конкретного пути/метода/user/background выполняется при последующем outgatecall; discovery не выдаёт разрешение на вызов.
- Например, mount `api → /api/v2` и local URI `/reports?limit=10` дают `/api/v2/reports?limit=10`; `/` даёт `/api/v2/`, root mount `/` не добавляет второй slash. Принимается только origin-form URI от `/`, не absolute URL/authority/fragment; действуют проверки escaping/сегментов п. 3.3. Query и escaped path сохраняются без повторного декодирования; `..`, `//` и encoded separators не позволяют выйти из mount. Mount здесь означает логический публичный адрес, а не изменение handler в preserve.
- Discovery cache SDK: TTL 30s, ограничение 256 target/mount записей; непроверенный/просроченный cache при недоступном discovery не используется. Helper добавляет `X-Outgate-Expected-Route-Revision`, покрываемый outgatecall и outgategateway. Gateway сравнивает его до списания nonce/отправки: несовпадение — 409 `route_revision_conflict`; заголовок не доверяется без подписи. При изменении mounts/владения/активации route_revision увеличивается, при обычном rollout неизменного mount — нет. SDK очищает cache при таком 409, но не повторяет бизнес-запрос; приложение явно строит новый запрос. Нельзя незаметно адресовать старый path после перемонтирования.

### 3.23. Контракт Admin API, ошибки и результат операции

- До реализации UI поставляются `docs/admin-openapi.yaml` (OpenAPI 3.1) и JSON Schema конфигурации. Они описывают все endpoints, authentication/roles/scope, тела/ответы/headers, nullable/defaults, revisions, enum/error codes и примеры. Неизвестные поля mutating JSON отклоняются; duplicate JSON keys запрещены. Все revision/cursor-sequence/64-bit IDs в JSON — decimal strings без ведущих нулей, не float JavaScript; проценты и лимиты — ограниченные integers. API version первой версии — 1 через обязательный `X-Outgate-Admin-API-Version: 1`; неподдерживаемая версия даёт 400 `unsupported_admin_api_version`. Публичные health и прикладные API не требуют этого header.
- Списки tunnels/routes/versions/audit/operations используют `limit` (default 50, 1–200) и opaque `cursor`, стабильный порядок по ID/time+ID, фильтры service_id/version/transport/state в зависимости от ресурса. Cursor связан с фильтрами и actor scope, живёт 10 минут; изменённый фильтр/некорректный cursor — 400, истёкший/устаревший snapshot — 409. Ответ: items, next_cursor|null, snapshot_revision. Один обход не смешивает снимки разных revisions; очень большой snapshot не требует полной загрузки в память. Чужие объекты не появляются даже в counts.
- Собственные HTTP-ошибки gateway/BFF/Admin API до отправки headers имеют `application/problem+json`: type URI, title, status, безопасный detail, instance=`urn:outgate:request:<request_id>`, расширения `code`, `request_id` и при validation `errors` с field/code. Это профиль RFC 9457; сохраняемый `reason` равен code для совместимости первой версии. Не возвращаются stack/SQL/DSN/secret/JWT. WSS/QUIC transport errors имеют тот же code, но не обязаны быть HTTP JSON. Если request headers/URI нельзя сериализовать в согласованный control limit, gateway отклоняет только запрос с 431 до отправки в tunnel; слишком большой response header block даёт 502 до headers либо abort после них, не закрывая исправную session. Прикладные HTTP errors/тела сервисов не переупаковываются; после headers статус не заменяется. Для HEAD тело ошибки не передаётся.
- Все mutating Admin API, включая import, grant/revoke, route activation и команды rollout, требуют `Idempotency-Key` (UUIDv7 по RFC 9562), expected_revision и reason (1–512 UTF-8 bytes). Body-less POST передаёт expected revision в `If-Match: "<revision>"`, reason — `X-Outgate-Change-Reason` (base64url без padding от UTF-8 reason); если одновременно задан JSON и headers, значения обязаны совпадать. UI/BFF создаёт key при явном подтверждении и повторно использует его только для той же операции. Request ID не заменяет operation ID.
- До изменения транзакция проверяет principal/scope/MFA/preview/revision; затем атомарно фиксирует новое состояние/revision, запись operation и outbox event в той же control DB. Operation ID равен Idempotency-Key и уникален в installation; повтор того же key разрешён только тому же actor, с тем же endpoint/нормализованным payload/expected_revision. После повторной проверки текущих прав он возвращает прежний безопасный result без повторного изменения; несовпадение actor/payload — 409 без раскрытия чужой операции. Проверка уже committed key предшествует проверке его старой revision и использованного preview, чтобы потерянный ответ не превращал успешное изменение в новый commit.
- `GET /admin/operations/{operation_id}` возвращает committed result/revision либо `unknown` (404) в разрешённой области actor; admin operation state не может быть доказан одним timeout. При неопределённом commit UI показывает «результат неизвестен» и проверяет этот endpoint/повторяет тот же key, не генерирует новый. Business HTTP-запросы эта идемпотентность не охватывает. Без записи operation в той же транзакции successful commit не публикуется.
- Для preview операций вне policy editor используется `POST /admin/changes/validate` с operation type, candidate, expected_revision и scope_service_ids; ответ — нормализованный diff/последствия/preview_id. Validate не меняет трафик; применяется общий TTL 10 минут, actor/payload/scope/revision binding и однократное использование. Root override, route release и security config import не обходят такой preview прямым API. Уже committed повтор по operation key не требует нового preview.
- Transactional outbox publisher доставляет audit events во внешнее защищённое хранилище at-least-once; event_id обеспечивает дедупликацию. Недоступность внешнего получателя не откатывает committed policy. Заполненная/недоступная локальная outbox запрещает новые изменения до commit. После commit, но до публикации in-memory snapshot процесс снимает readiness до resync; невозможность отправить ответ не означает, что осталась старая политика. Это уточняет все формулировки об «отказе state/audit». Размер outbox по умолчанию 100 000 событий или 256 MiB (первый достигнутый предел), предупреждение при 80%; предел настраивается после оценки нагрузки.
- Grant secret возвращается только в первом успешном ответе и не сохраняется в operation/outbox; повтор выдачи возвращает метаданные с `secret_available:false`. При потере ответа deployer отзывает grant и создаёт новый с другим key. Невозможно «восстановить secret» через GET, UI или аудит. Operation records хранятся 30 дней; старые keys с временем создания старше окна отклоняются, а не исполняются как новые. Для этого Idempotency-Key — UUIDv7 с timestamp, проверяемым по RFC 9562, допуск будущего времени 30s; произвольный UUID без timestamp запрещён.

### 3.24. Области RBAC и безопасный bootstrap администратора

- Principal определяется по admin certificate identity для CLI либо паре OIDC issuer+sub для web. Binding задаёт role и непустой service_ids; `*` доступен только явному глобальному binding в защищённой bootstrap-конфигурации. Viewer/deployer/security_admin независимы, иерархического наследования нет; для просмотра web-страниц с изменениями actor обычно имеет viewer и соответствующую mutating роль. Для одного действия объединяются service scopes всех bindings требуемой роли; разные роли друг друга не заменяют. Отсутствие binding означает deny.
- Viewer видит только разрешённые service IDs; deployer выдаёт grant/активирует маршруты/меняет rollout/order/primary только своего service scope и не создаёт новые service identities. Security_admin отзывает/меняет root/права только в своей области. Межсервисное правило требует scope security_admin одновременно на caller и target. Shared path change требует scope на всех затронутых владельцев; попытка глобального import с объектом вне scope отклоняется целиком. Instance/operation/audit endpoints проверяют scope владельца, а не только имя endpoint.
- Scoped GET/validate/evaluate возвращает только видимые rules/объекты. PUT policy snapshot scoped actor заменяет только явно указанную `scope_service_ids` проекцию, доступную одновременно для чтения и изменения; остальные правила сохраняются сервером без передачи их значений браузеру. Preview связан также с этой областью и полной base revision. Попытка изменить/delete правило, затрагивающее caller/target вне scope, отклоняется; скрытый rule не исчезает из-за его отсутствия в форме. Global actor может явно выбрать полный snapshot.
- Global security_admin нужен для создания/окончательного удаления identity, глобальных security limits/issuer trust и импорта, изменяющего объекты вне service-specific scope. Trust roots/IdP/admin roles по-прежнему не редактируются в web policy editor. Проверка scope/MFA выполняется сервером при каждом изменении и его повторе; frontend hidden button не является контролем.
- Для online security_admin CLI-операции одних статических cert/token недостаточно: разрешённый CLI principal содержит user_subject и дополнительно передаёт свежий admin access JWT в X-Outgate-Admin-User-Assertion. API проверяет pinned issuer/audience/auth_time/acr/amr и exact subject binding к этому certificate principal; эффективные права ограничены его серверными bindings. Этот header — секретный, логирование запрещено. Viewer/deployer machine calls продолжают cert/token профиль; unattended security_admin writes без user MFA не допускаются. CLI получает JWT разрешённым IdP login вне gateway, не принимает произвольный subject от пользователя.
- Первоначальный администратор задаётся до первого запуска защищённым bindings-файлом с конкретными identities; default admin/password нет. Bootstrap создаёт initial DB и audit событие, повторный bootstrap существующей DB отклоняется. Для восстановления при поломке IdP предусмотрен заранее выпущенный индивидуальный CLI recovery principal с admin CA и global security_admin, хранимый offline. Его сетевой доступ остаётся management-only.
- Recovery principal не обходит fresh-MFA для online policy editor/import. При недоступном IdP оператор останавливает BFF и gateway, применяет локальной recovery-командой проверенный bindings/IdP config с ожидаемой revision и обязательным reason, сохраняет подписанный recovery manifest и outbox event, инвалидирует admin sessions и запускает обычный профиль. Команда требует эксклюзивный control lock, OS/DB права отдельной recovery-role; удалённого unauthenticated endpoint и автоматического входа без MFA нет. Ограничения этой исключительной offline-процедуры отражаются в runbook и аудите.

### 3.25. Стабильная instance identity и ротация credentials

- В production WithInstanceID обязателен: ID стабилен при restart одного deployment instance, совпадает с certificate URI SAN и grant. Генерация hostname-pid-rand остаётся только development default; production без явного ID возвращает invalid_config до подключения. Один cert/grant не клонируется между репликами. Service/instance IDs: `[A-Za-z0-9][A-Za-z0-9._-]{0,127}`; case-sensitive, без скрытого lowercasing.
- Добавить atomic credential API `WithCredentialProvider`, возвращающий immutable snapshot {client TLS certificate, deployment grant, generation}; generation увеличивается. Production использует либо его, либо статическую пару WithTLS+WithDeploymentGrant. Старый WithDeploymentGrantProvider допустим только при неизменном SPKI; совместное задание двух providers отклоняется. WithTLS при provider задаёт только server trust/ServerName, статические client Certificates/GetClientCertificate вместе с provider запрещены. Gateway server trust/CA задаётся отдельно и не извлекается из недоверенного provider. Новый provider не получает admin credentials и не выпускает себе grant: он интегрируется с разрешённым deployment-процессом.
- Получить следующий snapshot SDK пытается заранее: не позже чем за min(5m, 20% фактического остаточного срока пары при её принятии) до min(cert.NotAfter, grant.expires), причём SDK использует подтверждённый gateway grant expiry из ack, а не пытается прочитать opaque secret. Callback timeout 5s, retry с jitter 1–30s в пределах оставшегося срока. При ротации сертификата сначала доверенный deployment issuer выдаёт grant под новый SPKI; SDK принимает только согласованную пару. SDK проверяет certificate CA/SAN/сроки/generation и целостность snapshot; opaque grant не декодируется как доверенные claims, его SPKI/service/instance/version/paths/mounts и сроки проверяет gateway до register_ack; некорректный snapshot не заменяет рабочий.
- Одновременно один instance не имеет двух туннельных сессий. SDK прекращает новые назначения, drain старой пары до 30s, закрывает старую сессию и регистрирует новую; краткое отсутствие экземпляра допустимо, реплики/active-passive обеспечивают доступность. Credential renewal не является бесшовной миграцией WebSocket. Старые HTTPS connections не используются для новых вызовов после credential switch; активные ограничены сроком старой пары/revoke. При истечении без успешного обновления новые вызовы запрещены, старые потоки закрываются, readiness=false. Компрометация/revoke прекращают доступ немедленно по прежним срокам, без ожидания drain.

### 3.26. Retire, освобождение маршрутов и хранение данных

- Маршрут имеет administrative state pending/active/retired. `POST /admin/routes/retire` с service_id+path+revision запрещает новые регистрации/назначения этого владельца, сохраняет tombstone и поведение 503 для совпавшего retired API/service префикса; запрос не уходит к более короткому маршруту/SPA. Текущие потоки drain до 30s. Для shared path retired владелец исключается, остальные действуют; tombstone блокирует fallback, когда активных владельцев больше нет.
- `POST /admin/routes/release` security_admin удаляет владение после retire и завершения всех потоков/отзыва grants, допускающих этот path. Нужны explicit reason/preview и scope всех затрагиваемых shared owners. Незавершённый drain/действующий grant — 409. После release путь снова следует общему router: reserved /api даёт 404, прочие могут попасть в SPA; UI явно показывает это последствие. Root освобождается только явным выключением override с теми же controls, не обычным retire. Новый owner активируется отдельной транзакцией, не автоматически от наличия регистрации.
- `POST /admin/services/{id}/versions/{version}/retire` deployer разрешён только при весе 0, отсутствии stable/canary/previous-stable references, активных/дренируемых экземпляров и действующих grants: иначе 409. После retire version не используется в новом rollout, повторная регистрация запрещена до `POST /admin/services/{id}/versions/{version}/restore` (security_admin, scope/revision/reason/operation key). Restore снимает tombstone запрета версии, но не выдаёт grant, не активирует пути и не меняет rollout автоматически. Минимальная metadata tombstone остаётся, подробная история может очищаться. `DELETE /admin/services/{service_id}` глобальным security_admin требует отсутствия routes/mounts/versions references/policies/grants/сессий, заранее устойчиво отозванной identity; service ID не переиспользуется автоматически.
- Retention по умолчанию: operation dedup 30 дней; локально отображаемый audit 90 дней после подтверждённой внешней доставки; подробная retired-version/instance history 30 дней; tombstones и действующий policy snapshot без автоудаления. Ограничение 100 версий относится к одновременно не retired версиям, а не бесконечному архиву; очистка истории не освобождает route ownership. Security revocations хранятся до истечения всех затрагиваемых credentials/claims + clock skew, бессрочный service/key revoke не удаляется по возрасту. Live nonce сохраняются до expires+skew, admin sessions до expiry/logout. Безопасные минимумы retention нельзя уменьшить обычной UI-настройкой.
- Cleanup пакетный, ограниченный по CPU/памяти/lock time; purge/delete не удаляют чужой scope, live nonce, неотправленный outbox и единственный актуальный revocation snapshot. Исчерпание места/лимита даёт диагностируемый fail-closed/503, не скрытую потерю истории безопасности. Метрики числа объектов/диска и `POST /admin/history/purge/validate` (read-only dry-run) и `POST /admin/history/purge` (security_admin, scope/revision/reason/operation key) обязательны; физические backup имеют отдельные retention/access правила оператора.

## 4. Протокол взаимодействия

### 4.1. Общие правила

Версия протокола — `1`. Версия сборки сервиса и версия протокола независимы. Версия передаётся при регистрации, несовместимость отклоняется до включения экземпляра в маршрутизацию.

Семантика сообщений общая, wire encoding определяется адаптером. В WSS используются JSON text messages для управления и binary messages для тел. QUIC использует собственный управляющий обмен Outgate и HTTP/3 для HTTP-данных; JSON/base64-конверты HTTP-тел в QUIC запрещены.

Семантический пример регистрации WSS (учётные данные передаются отдельно):

```json
{
  "type": "register",
  "protocol_version": 1,
  "service_id": "my-service",
  "instance_id": "my-service-01",
  "version": "1.4.2",
  "paths": ["/api/v1"],
  "path_mode": "strip",
  "rewrite_mount_headers": true,
  "metadata": {"region": "eu-west"}
}
```

`register_ack` подтверждает полный набор путей и возвращает версию протокола, согласованные лимиты/таймауты и параметры readiness при её использовании. `register_nack` содержит `code`, `retryable` и безопасный `detail` по wire-контракту. Подтверждение отправляется только после атомарной фиксации регистрации со статусом путей active/pending, указанным в ack; pending не публикуется в production router до активации. При невозможности доставить ack сессия удаляется из активного выбора. Ack также сообщает session_id, negotiated protocol_minor/capabilities, route_revision и проверенные credential expiry timestamps (без grant secret); состояние registered не равно ready по п. 3.21.

Точные структуры, коды, размерности, wire layout и переходы состояний закреплены в [protocol.md](protocol.md) и [protocol.schema.json](protocol.schema.json); дальнейшие изменения перед реализацией адаптеров синхронизируются с ними и golden fixtures. Оба адаптера проверяются общими контрактными тестами.

### 4.2. QUIC/HTTP3

- Клиент устанавливает QUIC-соединение с TLS 1.3 и выполняет собственную регистрацию Outgate поверх напрямую используемой QUIC-библиотеки. Согласование ALPN, формат credential и управляющего потока версионируются в protocol.md; версии самой Outgate-реализации и библиотеки фиксируются отдельно; произвольные управляющие сообщения нельзя отправлять как стандартные HTTP/3-фреймы.
- Bearer credential (development) либо deployment grant (production) передаётся в защищённом начальном управляющем обмене; production дополнительно проверяет mTLS certificate binding. Допускается ограниченное чтение сообщения для проверки credential; до успешной аутентификации реестр не изменяется.
- После регистрации клиент обслуживает HTTP/3-запросы шлюза по этому же обратному соединению. Отдельный HTTP-запрос использует отдельный HTTP/3-поток; тело передаётся нативно с QUIC flow control.
- Отмена запроса использует закрытие/reset его потока, не всего соединения. Управляющий канал поддерживает drain/unregister/reconnect и instance_status; его жизненный цикл не должен конфликтовать с HTTP/3.
- Keepalive по умолчанию 15s, idle timeout 45s. QUIC PING/ACK и idle timeout реализуются транспортом; JSON ping/pong для QUIC не требуется.
- TLS failures и QUIC application errors отображаются клиентом в общие причины ошибок. Числовые QUIC-коды документируются в собственном пространстве и не трактуются как WebSocket close codes.

### 4.3. WSS

- TLS → HTTP WebSocket Upgrade на настроенном пути → регистрация → multiplexing HTTP. В development bearer-токен, а в production deployment grant передаётся в `Authorization` при Upgrade, не в URL; в production сертификат уже проверен до Upgrade и grant повторно сверяется с полями регистрации; неверный токен возвращает HTTP `401` до Upgrade. Origin браузера не является заменой аутентификации.
- Один туннель — одно WSS-соединение. Для записи используется один сериализующий writer с приоритетом управления и справедливым обслуживанием готовых потоков; длительное чтение/запись тела не блокирует reader управления.
- Идентификатор внутреннего запроса уникален в пределах сессии и не равен автоматически внешнему `X-Request-ID`, который может повторяться.

| Сообщение | Направление | Назначение |
| :--- | :--- | :--- |
| `register`, `register_ack`, `register_nack` | client ↔ gateway | Общая регистрация |
| `request_start` | gateway → client | ID, метод, исходный path/query, Host, заголовки |
| `response_start` | client → gateway | ID, финальный статус, заголовки |
| Binary body chunk | bidirectional | ID запроса, направление тела, сырые байты |
| `request_end`, `response_end` | По направлению тела | EOF соответствующего тела, в том числе пустого |
| `window_update` | Получатель → отправитель | Кредит на байты тела конкретного запроса/направления |
| `cancel` | bidirectional | Отмена запроса и освобождение ресурсов |
| `unregister`, `reconnect` | client → gateway / gateway → client | Drain и завершение сессии |
| `instance_status` | client → gateway | Готовность экземпляра и sequence в рамках сессии; п. 3.18 |

- JSON start messages не содержат тела и base64. Каждый бинарный chunk однозначно содержит внутренний ID и направление; размер payload не превышает 32 KiB по умолчанию. Точное бинарное представление и максимальные размеры заголовков фиксируются в protocol.md до реализации.
- Целевое начальное окно каждого направления тела — 64 KiB по умолчанию, согласуется в ack; фактический credit выдаёт получатель. Request body начинает с нулевого credit до первого window_update по [protocol.md](protocol.md). Отправитель не может отправлять сверх кредита; кредит возвращается после потребления байтов downstream, а не после простого накопления в очереди.
- Очереди и число потоков ограничены. Reader не ждёт освобождения очереди обработчика: данные в пределах выданного кредита помещаются в заранее ограниченный буфер; нарушение кредита является protocol error. Отдельные лимиты управления и числа in-flight запросов предотвращают заполнение памяти start messages без тел.
- Когда кредит исчерпан, блокируется только отправитель соответствующего тела; управление, отмена и остальные готовые запросы продолжают обрабатываться. TCP head-of-line blocking при сетевых потерях этим не устраняется.
- `request_start` предшествует request body, `response_start` — response body. Ответ может начаться до окончания запроса. `*_end` закрывает только соответствующее направление; после `cancel` запрещены новые данные этого запроса. Уже отправленные до получения cancel данные безопасно отбрасываются в пределах согласованных лимитов; память освобождается без закрытия исправной сессии.
- Для `429` и раннего ответа клиент не обязан читать всё тело: неиспользованное request body отменяется отдельно, response body завершается штатно. Это правило должно быть явно выражено в wire-протоколе, чтобы отмена загрузки не уничтожала ответ.
- SSE передаётся и flush-ится без ожидания полного ответа. Compression внешнего WSS-туннеля в прототипе отключена; согласованные WebSocket-расширения самого приложения передаются прозрачно по п. 3.11.
- Keepalive использует стандартные WebSocket Ping/Pong control frames: Ping раз в 15s, Pong ожидается в течение 10s, после двух последовательных пропусков соединение закрывается. Таймаут записи и максимальный размер сообщения обязательны.

### 4.4. Ошибки и лимиты

| Общая причина | Значение |
| :--- | :--- |
| `auth_failed` | Неверные учётные данные |
| `invalid_register` | Некорректная регистрация |
| `unsupported_protocol_version` | Неподдерживаемая версия протокола |
| `path_forbidden` | Нет разрешения на префикс |
| `path_conflict` | Путь принадлежит другому сервису и не shared |
| `duplicate_instance` | ID уже имеет активную/дренируемую сессию |
| `quota_exceeded` | Превышен лимит туннелей, путей или версий |
| `protocol_error` | Нарушен порядок сообщений, framing или flow control |
| `server_shutdown` | Шлюз останавливается, допустим реконнект |

Причина доступна в типизированной ошибке Go-клиента и аудит-логе. WSS после Upgrade использует `register_nack` для отказа регистрации, затем закрытие с application code `4002`; нарушение активного протокола — `4004`, остановка — `1013`. До Upgrade действуют HTTP-ошибки: неверный bearer-токен возвращает `401`. При TLS failure приложение не может гарантировать выдачу кода.

По умолчанию: register timeout 10s, максимум управляющего сообщения 64 KiB, 32 пути на экземпляр, 100 обнаруженных версий на сервис, 1000 in-flight запросов на туннель у шлюза. Лимиты проверяются до выделения неограниченных ресурсов; максимумы и единицы задаются конфигурацией и документируются. Очистка запроса должна выполняться при EOF, отмене, deadline, сбое транспорта и shutdown.

### 4.5. Двунаправленный канал WebSocket приложения

Общий контракт адаптеров дополняется открытием ограниченного двунаправленного байтового канала, привязанного к выбранным сессии и внутреннему ID. По нему передаётся исходный HTTP/1.1 WebSocket handshake, затем, при `101`, байты WebSocket до закрытия. На стороне клиента библиотека обслуживает канал виртуальным HTTP/1.1-сервером с переданным `http.Handler`. Шлюз разбирает ограниченные по размеру response headers, передаёт отказ как HTTP либо переключает внешнее соединение на двунаправленный обмен, сохраняя уже прочитанные байты.

- **QUIC:** отдельный HTTP/3 CONNECT-поток на той же аутентифицированной обратной сессии. CONNECT адресует фиксированную внутреннюю функцию байтового канала клиента; произвольный target host/port не допускается. Успешный внутренний `200` означает только готовность канала; внешний `101` определяется вложенным handshake сервиса. CONNECT DATA передаёт байты, QUIC обеспечивает ограничение потока. Заголовки `Connection`/`Upgrade` находятся внутри вложенного HTTP/1.1, а не в HTTP/3 headers. Внешний и внутренний протоколы не смешиваются.
- **WSS:** управляющие `websocket_open` и `websocket_open_ack` создают байтовый канал с уникальным ID. Отказ открыть канал содержит причину и отображается в HTTP-ошибку до внешнего Upgrade. После ack бинарные чанки обоих направлений содержат ID и отдельный признак WebSocket-канала; payload — сырые байты вложенного HTTP/1.1 handshake и последующего WebSocket. Для него действуют те же ограниченные окна, справедливый writer и приоритет управления, что для обычных потоков; блокировка одного канала не останавливает остальные.
- EOF/закрытие направления передаётся явно; reset/cancel закрывает только конкретный канал. Close-фреймы приложения проходят как данные, отдельно от команды закрытия канала и Ping/Pong внешнего WSS. Число каналов входит в лимиты in-flight шлюза и concurrency клиента и учитывается до закрытия, а не только до ответа `101`.
- `docs/protocol.md` закрепляет handshake открытия, таймауты, лимиты, framing бинарных чанков, half-close/reset и переходы из handshake в raw stream. Транспортные кредиты распространяются также на вложенный handshake. Новый канал принимает данные только после подтверждения; невозможность принять соединение возвращает отказ без неограниченной очереди.

Такой контракт сохраняет обычные HTTP/3-запросы для HTTP и SSE, а совместимость существующих WebSocket-обработчиков обеспечивает отдельным каналом; сам по себе HTTP/3 не гарантирует поддержку `http.Hijacker`. Основание этой границы — [контракт Go Hijacker](https://pkg.go.dev/net/http#Hijacker); CONNECT в HTTP/3 описан в [RFC 9114, раздел 4.4](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.4).

### 4.6. Профиль HTTP Message Signatures

Используется [RFC 9421](https://www.rfc-editor.org/rfc/rfc9421.html), алгоритм `hmac-sha256`. Метки подписей различаются: `outgatecall` для сервис → шлюз, `outgategateway` для шлюз → сервис. Подписывается одна Outgate-запись каждого участка; неизвестный алгоритм или попытка использовать ключ другого участка/сервиса отклоняется. Outgate Signature/Signature-Input не заменяют пользовательский Authorization.

- Зарезервированные поля: `X-Outgate-Caller-Service`, `X-Outgate-Target-Service`, `X-Outgate-Context-Headers`. Последнее — упорядоченный JSON-массив имён присутствующих пользовательских заголовков в lower case; без пользователя — `[]`. Они не могут задаваться обработчиком как доверенные утверждения вместо context. Предъявление любого зарезервированного Outgate-поля, метки `outgatecall`/`outgategateway` или неполной Outgate-подписи на публичном входе требует межсервисной проверки; без корректного `outgatecall` возвращается `401`.
- `outgatecall` покрывает `@method`, `@authority`, `@path`, `@query`, caller/target, manifest и все перечисленные в нём user headers. Параметры `keyid`, `alg`, `created`, `expires`, `nonce` обязательны и входят в signature base по RFC. Добавить неподписанный user attribute нельзя: состав должен точно совпасть с manifest и allowlist. Даже при отсутствии пользователя manifest остаётся подписанным. При использовании discovery обязательно покрывается X-Outgate-Expected-Route-Revision. В production обязательно покрываются X-Outgate-Hop-Limit, X-Outgate-Deployment-Grant-ID и, при user delegation, X-Outgate-User-Assertion; удаление/подмена этих полей нарушает профиль и отклоняется.
- `outgategateway` дополнительно покрывает `X-Tunnel-Instance`, `X-Tunnel-Version` и `X-Forwarded-Prefix`, имеет новый nonce и ключ получателя. Подпись создаётся после маршрутизации на публичных path/query и назначения mount-префикса; между подписью и проверкой получателем подписанные поля не меняются. Strip в клиентской библиотеке выполняется строго после проверки подписи/nonce на исходном публичном URI и не меняет wire-запрос до неё. `@authority` при проверке соответствует сохранённому прикладному Host, а не физическому адресу туннеля.
- Получатель доверяет пользовательским заголовкам только после проверки `outgategateway`. Наличие доверенных/Outgate-заголовков без корректной подписи — `401` до handler. Для обычного внешнего запроса их нет; context user/caller не установлен. Шлюз не позволяет внешнему клиенту предъявить `outgategateway` как подтверждение своего запроса.
- Срок действия: `expires = created + 60s`, допуск часов 30s в обе стороны. Проверяются `created <= now + 30s` и `now <= expires + 30s`; nonce — не менее 128 случайных бит. Verifier сам проверяет expires-created=60s; произвольно увеличенный срок из подписанного запроса не принимается. Проверка выполняется при приёме headers/handshake, не повторяется по ходу тела или долгоживущего WebSocket/SSE.
- Replay-хранилище шлюза и получателя атомарно резервирует `(участок, service_id, key_id, nonce)` после успешной криптографической проверки и до вызова handler/доставки. Запись живёт до `expires + 30s`, используется однократно. Development допускает in-memory кеш на 100 000 записей. Production требует устойчивого хранилища, расчёта ёмкости по допущенному RPS и квотам п. 5.5.2. Живые записи не вытесняются; заполнение/недоступность даёт `503`. Получатель проверяет instance binding, поэтому подпись доставки не принимается другой репликой.
- Автоматических повторов подписанного запроса нет. Повтор с тем же nonce отклоняется; новый nonce не делает прикладную операцию идемпотентной. Подпись не включает тело или его digest, поэтому проверка до обработки не требует буферизации. Тело защищается TLS на обоих сетевых участках; end-to-end целостность тела этой подписью не заявляется.
- В prototype используются точные значения исходного escaped path/query; parser и canonicalization соответствуют RFC 9421. Роли сериализуются компактным JSON, manifest сортируется, а header values проверяются на допустимость без неявных преобразований. `docs/protocol.md` до реализации фиксирует порядок компонентов, escaping/кодирование UTF-8 и примеры signature base с тестовыми ключами для user/background, HTTP, HTTP/3 и WebSocket-handshake.
- Потеря replay-защиты при перезапуске допустима только в development. В production хранилище не очищается при старте; потеря или неизвестная целостность состояния переводит соответствующий защищённый тракт в fail-closed до безопасного восстановления по п. 5.5.2.

### 4.7. Фиксация wire-контракта и совместимость версий

- `protocol_version: 1` — major wire version, не версия приложения. До реализации адаптеров результатом этапа 1 являются полный `docs/protocol.md`, JSON Schema каждого сообщения и исполняемые golden fixtures в `tests/fixtures/protocol/v1`. Они нормативны вместе с этим ТЗ; изменение требования синхронно обновляет схемы/fixtures. Наличие заголовка документа без полного каталога сообщений не закрывает этап.
- Register/ack дополнительно содержат protocol_minor (первоначально 0), capabilities и required_capabilities — списки уникальных ASCII feature IDs. Major выбирается явно, другой major отклоняется. При одном major согласуется минимальный minor и пересечение capabilities; отсутствующий required feature даёт unsupported_protocol_version до активации сессии, без fallback/частичной регистрации. Optional расширения передаются только в `extensions`; неизвестные optional extensions игнорируются, неизвестные основные поля/типы и duplicate JSON keys запрещены. Breaking change формата/семантики требует нового major; добавление optional extension — minor. В первой версии обязательные features включают streaming, cancellation, duplex_websocket и bounded_flow_control для обоих адаптеров.
- Text control WSS — один UTF-8 JSON object на одно WebSocket message, максимум 64 KiB после сборки фрагментов; tunnel permessage-deflate отключён. JSON IDs stream/session/cursor/revision передаются decimal strings без знака/ведущих нулей, timestamps — целые Unix seconds. Headers — упорядоченный массив пар name/value, позволяющий повторения Set-Cookie и других полей; недопустимые имена/CRLF отвергаются до handler. Metadata registration: максимум 32 записи, key до 64 bytes, value до 1024 bytes, суммарно 8 KiB; общий control-limit также обязателен. Auth/grant secret передаётся только в защищённом registration credential exchange, не в обычных control extensions.
- Binary WSS message: фиксированный заголовок 16 bytes, big-endian: version uint8 (=1), kind uint8, flags uint16 (=0), stream_id uint64 (>0), payload_length uint32; затем ровно payload_length bytes. Kind 1 — request body, 2 — response body, 3 — WebSocket bytes к handler, 4 — WebSocket bytes от handler. Один message — один chunk; payload не более согласованного max_chunk_bytes (default 32768), пустое завершение выражается control end, не special binary frame. Неверные version/kind/flags/length/ID — protocol_error без выделения памяти по неподтверждённой длине.
- Stream IDs выдаёт gateway монотонно от 1, без повторного использования до конца сессии; один ID описывает один HTTP-запрос либо один WebSocket-channel. Session ID назначает gateway в ack как случайный 128-bit token (base64url без padding); decimal-string правило относится к numeric IDs, не к этому token; после реконнекта старая namespace недействительна, in-flight операции не возобновляются. Wrap ID завершает сессию через drain. HTTP start содержит stream_id, method, raw_request_uri, host, headers; response start — stream_id, status, headers. Content-Length — metadata для проверки фактических байтов, не второй способ framing; несоответствие приводит к request failure/обрыву, не дополнению данных.
- Полный каталог control: register/ack/nack; request_start/response_start; request_end/response_end; cancel/cancel_ack с scope=request_body|response_body|all и code; window_update со stream_id/direction/positive byte credit; websocket_open/open_ack с metadata HTTP handshake; open_ack подтверждает только создание byte channel, не авторизацию/успех handler, внешнее 101 следует лишь после внутреннего HTTP/1.1 101; reject передаётся как обычный response; websocket_end с direction; instance_status с monotonic sequence/readiness; drain/drain_ack, unregister/unregister_ack; reconnect. Каждый имеет обязательный type; точные поля, направления, nullable/границы/допустимые состояния закрепляются JSON Schema этапа 1. Никакие новые implicit служебные сообщения в реализации не вводятся без обновления контракта.
- Обычный stream: start → zero or more chunks → end независимо в обе стороны; response может начаться до request_end. После отказа/раннего ответа request_body cancel не отменяет response. Sender прекращает новые chunks выбранного направления и удаляет их из очереди до cancel_ack; receiver сохраняет остаточный credit/bounded state до ack, отбрасывая только уже отправленные chunks. Ack подтверждает, что новых bytes этого направления не будет; после ack новые bytes — protocol_error. Cancel ack timeout 10s, иначе сессия считается неисправной. Normal end закрывает направление, оба end освобождают stream; unsolicited start/response, повторный start/end и данные до start/после end не маскируются.
- Initial credit 65536 bytes на направление выделяется только при наличии общего бюджета. Ack/start сообщает реально выданное окно, допустимо 0 до window_update. Credit учитывает payload, не 16-byte framing; сумма выданного/непотреблённого не превышает согласованный budget. Window_update не переполняет uint64 и не открывает несуществующий/закрытый stream. Control frames имеют отдельную ограниченную очередь; keepalive и cancel не блокируются заполненными body queues. WebSocket канал следует тем же правилам кредитов, но вложенные RFC 6455 frames остаются необработанными bytes.
- QUIC не использует этот WSS binary layout для HTTP body: запросы идут HTTP/3, app WebSocket — согласованным internal CONNECT. QUIC Draft carrier, ALPN outgate-tunnel/1, stream ownership/type IDs, registration codec и error mapping закреплены в [protocol.md](protocol.md) как самостоятельный контракт Outgate; выбранная quic-go и совместимость подтверждаются собственным spike до начала этапа 2; требуется независимый round-trip fixture/сквозной spike. Нельзя назначить произвольный QUIC stream под управление, конфликтующий с HTTP/3 request/control/QPACK. Пока carrier/совместимость не проверены, QUIC этап не считается начатым/закрытым формальным обещанием.
- Golden corpus включает точные bytes/ожидаемый результат для всех control/binary типов, границ размеров, early response, half-close, cancel race, malformed/unknown messages, unsupported capabilities, invalid UTF-8 и повторных IDs. Для RFC 9421 — фиксированные НЕ production keys, exact signature base/HMAC bytes для escaped UTF-8 path, query, многозначных headers, user/background, instance binding и expected route revision; отдельно негативные варианты. Их обязан воспроизводить каждый адаптер/verifier, не только общий serializer, иначе одинаковая ошибка двух сторон останется незамеченной.
- Gateway/SDK/binary release versions используют SemVer, DB schema — отдельный monotonic integer. Матрица релиза перечисляет поддерживаемые wire/admin/schema versions; обязательна совместимость gateway release N с SDK N и предыдущим опубликованным minor того же major, если он существует. Несовместимый peer получает явный отказ до трафика. Gateway upgrade drain/reconnect не мигрирует старые WS/SSE.
- DB migrations применяются отдельной командой до запуска; manifest содержит source/target schema version, backup requirement и перечень совместимых binary versions. Runtime принимает только явно поддерживаемые версии. Rollback бинарника разрешён лишь если прежний binary поддерживает текущую schema; автоматический downgrade БД запрещён. Иначе требуется restore/migration по runbook с восстановлением security state/barrier, а не запуск старого snapshot с открытым трафиком. В рамках minor используется expand/contract без удаления нужных предыдущему поддерживаемому binary полей; destructive migration — отдельный major/план допуска.

## 5. Нефункциональные требования

### 5.1. Производительность

Цели отдельного нагрузочного этапа: 50 000 RPS на 8 vCPU при теле 4 KiB и p99 < 30 ms; накладные расходы latency относительно прямого HTTP(S)-прокси ≤ 15%; до 10 000 одновременных туннелей при достаточной памяти и настроенных лимитах. Эти показатели не являются доказанными свойствами QUIC или WSS и не блокируют функциональную приёмку прототипа.

Отчёт **ДОЛЖЕН** отдельно описывать QUIC, WSS и смешанный режим при одинаковых условиях: CPU/RAM/OS, Go/зависимости, TLS, число клиентов/туннелей/экземпляров, конкурентность, размеры запросов и ответов, доли версий, длительность/прогрев, RTT/потери, throughput, p50/p95/p99, ошибки, CPU и память. Сравнение с прямым прокси проводится при той же бизнес-логике и сопоставимых сетевых участках; формула overhead и измеряемая latency фиксируются в отчёте.

### 5.2. Надёжность

- В прототипе нет гарантии SLA. Цель production — 99.9% при отдельном проектировании отказоустойчивого развёртывания.
- После восстановления сети и готовности выбранного слушателя клиент должен восстановить регистрацию в пределах `2 * MaxDelay` при штатной доступности сервиса и отсутствии отказов авторизации. Это не гарантия при недоступной сети; время обнаружения разрыва измеряется отдельно.
- Backoff ограничен MaxDelay с учётом jitter; попытка подключения/регистрации имеет timeout 10s по умолчанию.
- Graceful shutdown по умолчанию 30s. По deadline ресурсы освобождаются, незавершённые потоки отменяются.
- Ограниченная память и отсутствие утечек goroutine обязательны для обоих адаптеров, включая медленных потребителей и частые реконнекты.

### 5.3. Безопасность

TLS 1.3 обязателен для публичного HTTPS и обоих туннелей; QUIC не объявляется более безопасным, чем корректно настроенный WSS с TLS 1.3. Оба требуют проверки сертификатов, авторизации путей и защиты секретов. 0-RTT для регистрации и HTTP-запросов в прототипе отключён.

Обязательны ограничения размеров/числа сообщений и соединений, защита от path traversal и header injection, проверка межсервисных HMAC-подписей/nonce и аудит регистрации, rollout и отказов межсервисного доступа. Пользовательские ID, роли, Cookie, Authorization, секреты и подписи не включаются в аудит; допускаются service ID, key ID, reason и request ID. mTLS сервисов и rate limiting обязательны до публичного production-запуска для обоих адаптеров; отсутствие настроек п. 5.5 является ошибкой запуска production, а не предупреждением. Локальный HTTP upstream и loopback Admin API допустимы в стенде; при передаче за пределы доверенного хоста используется HTTPS с проверкой сертификата.

### 5.4. Совместимость и стек

- Go: конкретная поддерживаемая версия фиксируется в `go.mod`/toolchain после проверки совместимости собственных адаптеров и выбранной `quic-go`; обещание совместимости со всеми Go 1.22+ не требуется.
- Поддерживаются **Linux amd64 и Windows amd64**, включая публичный production-профиль. Windows запускает нативные `.exe` без WSL/WSL2, Docker, Hyper-V, Linux VM, POSIX-эмулятора или установленного Go toolchain. Целевые Windows: Windows Server 2022/2025 для production, Windows 11 для разработки и стенда; конкретные сборки фиксируются в матрице релиза.
- Поставляются нативные `outgate-gateway` и `outgate-admin-web` для обеих ОС, Windows-варианты с `.exe`, SDK и запускаемые примеры. На Windows не требуется установка отдельного SQLite-сервера; драйвер SQLite встраивается. Зависимости/нативные библиотеки, если нужны, включаются в поставку с лицензиями; отдельный компилятор на машине оператора не требуется. Docker-образ Linux остаётся дополнительным способом доставки, на базе `gcr.io/distroless/static`, если зависимости позволяют статическую сборку.
- `net/http`, `httputil.ReverseProxy`; напрямую `quic-go`/`quic-go/http3` для QUIC/HTTP3; `coder/websocket` для WSS; YAML + env; `prometheus/client_golang`; `log/slog`; OpenTelemetry на production-этапе.
- Зависимости фиксируются, их обновления сопровождаются контрактными и интеграционными проверками обоих транспортов.

#### 5.4.1. Нативный запуск и эксплуатация Windows

- Одинаковые регистрация, маршрутизация, QUIC/WSS, WebSocket/SSE, канарейка, active-passive, Admin Web и security gates обязательны на обеих платформах. Windows не является упрощённым development-only режимом. Linux-only зависимости изолируются build tags либо заменяются переносимыми реализациями; совместимость собственного QUIC-адаптера/quic-go и SQLite подтверждается нативными тестами, а не одной кросс-компиляцией. Оба SQL adapter включены в нативные бинарники.
- Каждый Windows-процесс работает в консоли и как отдельная Windows Service через SCM. Поставка содержит PowerShell-инструкции установки/удаления, запуска/остановки и восстановления службы. Используются отдельные непривилегированные service accounts, не LocalSystem; установка службы и firewall rules требует прав администратора, штатная работа — нет. Linux поставляется с примером systemd unit.
- Ctrl+C в консоли, SCM Stop/Shutdown на Windows и SIGTERM/SIGINT на Linux вызывают общий bounded graceful shutdown: прекращение новых назначений, drain, закрытие listeners/потоков и flush состояния/аудита. SCM получает корректные pending/status updates; процесс не обещает завершить drain при force kill/отключении питания. Повторный запуск проверяет сохранённое состояние.
- Пути конфигурации задаются явно и не зависят от текущего каталога службы. Относительные пути разрешаются относительно каталога конфигурационного файла. Рекомендуемые Windows-каталоги: бинарники `C:/Program Files/Outgate`, данные/логи `C:/ProgramData/Outgate`, отдельный каталог секретов с NTFS ACL только для соответствующей службы и администратора. Примеры `/run/secrets` и `/var/lib/outgate` ниже — Linux deployment paths; Windows-примеры заменяют их явными путями, не требуют таких каталогов и не выполняют скрытую подстановку.
- При выборе SQLite её постоянные БД находятся на локальной файловой системе с проверенными блокировками/flush (NTFS на Windows); SMB/NFS, сетевые шары и синхронизируемые OneDrive-каталоги запрещены. ACL защищают также WAL/SHM, session DB, backup и audit spool. Лимиты открытых handles/соединений и диска проверяются отдельно для ОС. POSIX chmod/non-root и container hardening заменяются эквивалентными Windows ACL/service isolation, когда контейнер не используется.
- TLS использует явно настроенные PEM cert/key/CA с одинаковой проверкой на обеих ОС; доступ к Windows Certificate Store не обязателен в первой версии. Reload секретов доступен через аутентифицированную административную команду на обеих ОС; SIGHUP — только дополнительный Linux-механизм. Private keys не передаются в аргументах командной строки.
- Firewall-инструкции явно разделяют публичные TCP/UDP listeners и management/service mTLS listeners; инсталлятор не открывает все порты автоматически. На Windows не отключаются certificate/Origin/replay-проверки ради прохождения firewall или запуска службы. Журналы — структурированный JSON в stdout для консоли и в защищённые ротируемые файлы для службы.

### 5.5. Обязательный профиль публичного production-развёртывания

Ниже перечислены требования первой публичной версии, а не рекомендации «на будущее». Пока не пройдены проверки п. 8.8, 8.10–8.13 и применимые сценарии 8.9, допустим только изолированный development-стенд. Безопасность не означает защиту от компрометации самого шлюза, identity issuer или администратора; эти компоненты входят в доверенную вычислительную базу.

#### 5.5.1. Идентичность экземпляров, допуск сборок и отзыв доступа

- QUIC/WSS требуют TLS 1.3 с проверкой клиентского сертификата по выделенному service CA. Сертификат содержит URI SAN с service_id и instance_id; точная схема URI и trust domain заданы конфигурацией и protocol.md. CN и непроверенные строки регистрации не используются вместо SAN. Сертификат живёт не более 24h; соединение не переживает его NotAfter.
- Одного сертификата или статического tunnel bearer недостаточно. До регистрации требуется ограниченный deployment grant, выданный администратором/доверенным deployment-процессом. Opaque grant передаётся как grant_id.secret: ID содержит не менее 128 случайных бит, secret — не менее 256. В control state хранится ID и только SHA-256 секретного токена, не его plaintext. Grant связан с service_id, instance_id, точной version, точным набором paths/mounts, path_mode/rewrite, SHA-256 SPKI клиентского сертификата и сроком не более 1h. Клиент не может объявить другую сборку stable или добавить пути по одному украденному общему токену.
- Создание grant не доказывает происхождение бинарника само по себе: оператор выдаёт его только для разрешённого артефакта с проверенными digest/подписью. Digest артефакта сохраняется в deployment-аудите. Аттестация работающего процесса и защита от полного захвата уже допущенного хоста не заявляются.
- При реконнекте допускается повторное использование неистёкшего grant тем же экземпляром с тем же сертификатом, но одновременно только одна сессия. Атомарная ротация сертификата и grant выполняется по п. 3.25. SDK поддерживает WithDeploymentGrantProvider для обновления credentials до истечения срока; сертификат обновляется через TLS client certificate provider. При невозможности продления туннель закрывается по сроку, а не работает бессрочно. Статический grant также допустим для ограниченного по времени запуска.
- На отдельном mTLS HTTPS-слушателе межсервисных запросов certificate service_id должен совпадать с HMAC caller; клиент не может обходить эту проверку через публичный браузерный слушатель. Каждый signed HTTPS-вызов также покрывает X-Outgate-Deployment-Grant-ID: grant должен быть действующим и связанным с certificate identity/SPKI отправителя. SDK извлекает публичный grant ID из текущего credential; сырой secret не передаётся handler. У service certificate и HMAC key отдельные механизмы ротации/отзыва. Source IP не является идентичностью сервиса.
- Security-admin может отозвать service_id целиком, SPKI/certificate serial, grant ID или HMAC key ID. Отзыв устойчиво фиксируется до успешного ответа. Не позднее 5s после него новые регистрации/вызовы отклоняются, активные затронутые туннели, запросы и WebSocket/SSE прекращаются. Отзыв не является graceful drain. Удаление ключа только из файла без применения отзыва не считается выполненным механизмом.
- Сервисы не принимают входящие вызовы, минующие библиотечный verifier: виртуальный listener остаётся внутренним; дополнительный диагностический HTTP-порт не публикуется. При контейнерном Linux-развёртывании процессы работают non-root, без privileged/host network, с read-only root filesystem и отдельными секретами; нативные Linux/Windows службы используют непривилегированные accounts и OS file ACL по п. 5.4.1. Network policy допускает только необходимые шлюз, issuer, state store и собственные зависимости сервиса.

#### 5.5.2. Устойчивое состояние и replay-защита

- Для одного шлюза control state хранится в SQLite (по умолчанию) либо PostgreSQL. SQLite использует постоянный локальный диск, WAL и synchronous=FULL; PostgreSQL — устойчивые транзакции по п. 5.5.8. Второй процесс-владелец одного control state не допускается на обоих backend. SQLite работает нативно на Linux и Windows без внешнего DB-сервера; PostgreSQL подключается по сети без изменения транспортов шлюза. Транзакционно сохраняются версии/владение, активированные маршруты, rollout/previous stable, установленный frontend override, grants и отзывы. Активные сетевые соединения после рестарта всегда создаются заново.
- Изменения Admin API требуют expected_revision и operation key по п. 3.23; несовпадение даёт `409`, успешная запись повышает revision и публикует один согласованный снимок. YAML используется для bootstrap, изменения затем выполняются через API или явный атомарный импорт конфигурации. Повреждённое/утраченное control state нельзя автоматически заменить пустым и начать обслуживать запросы.
- Базовый production-профиль не требует Redis. Каждый verifier (gateway и каждый принимающий экземпляр SDK) выбирает SQLite или PostgreSQL replay store: устойчивые транзакции, уникальный namespace, persisted epoch и UNIQUE по namespace/проверяемой идентичности отправителя/ключа/nonce. SQLite WAL/FULL — локальное значение по умолчанию; PostgreSQL использует собственную схему/ограниченную роль verifier по п. 5.5.8. Внутри одного экземпляра все входные каналы используют один verifier/store; реплики не делят файл БД. Recipient signature привязана к instance/version; резервирование gateway предотвращает повтор на другом экземпляре, а локальный recipient store — повтор на том же. Независимая проверка получателем сохраняется.
- `storage.replay.driver` выбирается явно: `sqlite` по умолчанию, поддерживаемый `postgres` или опциональный `redis`; автоматического переключения при отказе нет. Redis-адаптер, если поставляется/включён, требует TLS, отдельных ACL/namespace, AOF appendfsync=always, постоянного volume и noeviction. RDB-only/AOF everysec и failover с потерей подтверждённых записей не удовлетворяют контракту. Redis не добавляет HA шлюзу и не требуется только ради TTL либо доставки отзывов. Отсутствие Redis не блокирует приёмку SQLite-профиля; непоставляемый адаптер отклоняется как неподдерживаемый, а не имитируется памятью.
- Атомарная транзакция резервирует nonce до expires+skew, одновременно проверяя глобальную и caller-квоту. SQLite и PostgreSQL используют транзакцию с уникальным ограничением и проверкой квот без гонок; PostgreSQL дополнительно сериализует обновления счётчиков namespace/caller блокировками строк в фиксированном порядке. Один лишь INSERT ON CONFLICT не обеспечивает атомарность квот. Redis использует эквивалентную атомарную операцию. Доставка в handler/туннель разрешена только после успешного устойчивого commit; batching допустим с ограниченной очередью и без раннего подтверждения. Отдельные GET и SET без атомарности запрещены. Живые nonce не удаляются при ошибке downstream и не вытесняются ради нового запроса. Проверка криптографии/issuer и разрешений предшествует расходованию nonce-квоты, но следует после предварительного rate limit.
- Ёмкость считается для каждого проверяющего namespace: `ceil(admitted_signed_rps * (signature_ttl + 2 * clock_skew) * 1.25) + admitted_burst`. При TTL 60s, skew 30s, 1000 RPS и burst 2000 минимум 152 000 записей; пример задаёт 200 000. Для 50 000 RPS без burst требуется минимум 7,5 млн записей только на одном проверяющем участке. Размеры памяти, диска/WAL и стоимость fsync измеряются с реальными индексами выбранного backend, не предполагаются равными размеру одного nonce. Expired записи удаляются ограниченными пакетами; cleanup/checkpoint не вытесняют живые nonce и не держат неограниченные очереди. Производительность SQLite с FULL или PostgreSQL с durable commit не объявляется достаточной для 1000 или 50 000 RPS без измерений: фиксируются достигнутые пределы, при необходимости снижаются admission limits с согласованным пересчётом capacity.
- Пределы caller разбиваются на независимые квоты в рамках глобальной ёмкости: один допущенный сервис не может занять весь namespace. При превышении собственной квоты — `429`; при недоступности/исчерпании общего state — `503`, без fallback в память и без fail-open. Параметры RPS, burst и capacity валидируются совместно до запуска; увеличение RPS без увеличения replay capacity запрещено.
- Gateway/SDK не очищают state при старте. Отсутствующая контрольная epoch, откат/потеря SQLite replay DB/WAL, PostgreSQL replay state/WAL либо Redis AOF блокируют защищённый тракт. Неизвестная свежесть восстановленной копии трактуется как потеря; epoch в том же файле сама по себе не доказывает отсутствие rollback. Установка/restore помечаются явной процедурой, а для verifier после каждого старта до ready действует окно не менее TTL+2*skew (120s) с отказом от signed created до начала окна; это исключает доверие незаметно устаревшей backup. Повторный старт перезапускает окно. Выполнять приложение во время восстановления/копирования БД запрещено. Восстановление выполняется оператором; для сброшенного replay namespace действует общий barrier не менее TTL+2*skew (120s) и минимальный created после момента восстановления. Barrier публикуется в устойчивом control state и применяется всеми verifier, прежде чем тракт станет ready. Потеря данных об отзыве не лечится одним ожиданием: они восстанавливаются из control state, иначе доступ остаётся закрыт.
- Snapshot/delta отзывов выдаётся после устойчивой записи в control state; потерянный cursor/разрыв журнала требует полного snapshot, а не пропуска событий. До начальной синхронизации SDK не принимает защищённые запросы. При устаревании credential-снимка более 5s соответствующие операции запрещаются и потоки закрываются; для user-отзывов предел 30s. Сроки п. 5.5.1 сохраняются; local cache не разрешает бессрочную работу offline. Доставка отзывов и replay backend независимы: Redis pub/sub не является источником истины.
- При недоступном control/replay/revocation state readiness=false; новые защищённые операции получают `503`, открытые защищённые потоки закрываются в пределах срока проверки отзывов. Обычный локальный healthz остаётся диагностическим. Выполняются резервное копирование control state, проверка восстановления и мониторинг записи/свободного места; старая backup не вводится в эксплуатацию без восстановления отзывов и replay barrier.

#### 5.5.3. Безопасная публикация маршрутов и внутренних операций

- В production регистрация лишь резервирует допустимые пути и добавляет экземпляр/версию. Новые префиксы имеют состояние pending и не меняют longest-prefix match, даже если экземпляр заявил stable version. Отдельная административная активация требует разрешённого deployment grant и покрытия нового пути активными экземплярами всех положительно взвешенных версий сервиса; кандидат с 0% не может отнять трафик у stable.
- Уже активированный маршрут сохраняется устойчиво и при отсутствии экземпляров даёт `503`. Retire/release и tombstones регулируются п. 3.26, не автоматическим TTL. Приём новых регистраций не удаляет/не заменяет его. Удаление/смена владельца выполняется только через авторизованную транзакцию с revision и аудитом; для shared path сохраняются явные владельцы.
- Корневой frontend также активируется административно; само подключение кандидата не включает override. После активации рестарт не возвращает старый SPA-upstream: до восстановления допущенного frontend возвращается `503`. Возврат к upstream — явная устойчивая операция администратора; не fallback по ответу/ошибке сервиса.
- Для internal-only endpoint задаётся политика шлюза `internal_only` с target, paths, methods и непустым allowlist callers. До вызова сервиса она требует mTLS и корректный outgatecall; браузерный запрос без Outgate-полей не получает доступ через внешний режим. Сам API дополнительно проверяет CallerServiceFromContext для внутренних операций. Обычные public/private пользовательские endpoints по-прежнему определяет API, а не шлюз.
- SDK подписывает ограниченный X-Outgate-Hop-Limit; максимум 8. Для первого внутреннего вызова — 8, каждый следующий из проверенного контекста обязан уменьшить значение на 1, значение 0 отклоняется с `508` до доставки. Это ограничивает случайные циклы; скомпрометированный сервис способен начать новую цепочку, поэтому hop limit не заменяет квоты.

#### 5.5.4. Проверяемый пользовательский контекст и отзыв долгоживущих сессий

- В production WithUserContext устанавливает только локальный контекст API. Для его межсервисной передачи дополнительно обязателен WithUserAssertion с JWT от настроенного доверенного issuer. Самостоятельно созданные API-сервисом X-User-ID/Roles, даже с корректным outgatecall, не принимаются как доказательство пользователя. Background-вызов без пользователя остаётся возможен при отдельном разрешении.
- Issuer — отдельная доверенная зависимость, выбранная владельцем системы, а не новый сервер паролей внутри gateway. Он проверяет пользовательскую сессию и полномочия делегирующего сервиса; для target-specific делегирования поддерживается OAuth Token Exchange по RFC 8693. Ключ подписи issuer не выдаётся обычным API-сервисам, gateway и получателям. Если API само является issuer, это явно привилегированный компонент с ограниченной областью claims, а не любой владелец tunnel token.
- Gateway и библиотека получателя независимо проверяют signature, exact iss, единственную aud=target service_id, sub, exp, iat/nbf, jti, sid и act.sub=непосредственный caller; lifetime JWT не более 300s, skew не более 30s. Claims user ID/roles/attributes выводятся из JWT по явной карте и должны совпасть с переданными заголовками. Для B → C требуется утверждение для C и actor B; простое наследование токена с aud B запрещено. Роли/tenant/scopes получатель проверяет согласно собственной авторизации; утверждение для одного target не даёт прав на другой.
- Разрешённые JWT algorithms задаются фиксированным allowlist (пример — RS256); none, HS256/подмена типа ключа и выбор алгоритма из непроверенного header запрещены. JWKS загружается только с настроенного HTTPS URL; jku/x5u токена игнорируются. Неизвестный kid вызывает не более одного контролируемого refresh за 30s; известные ключи кешируются максимум 5 минут. При отсутствии пригодного ключа проверка закрыта, фонового fail-open нет. Профиль утверждения отделён от browser access token по typ=outgate-delegation+jwt и проверяется отдельно.
- X-Outgate-User-Assertion, X-Outgate-Hop-Limit и X-Outgate-Deployment-Grant-ID резервируются и включаются в outgatecall/outgategateway signature base. Assertions не логируются и не попадают в ответы. Утверждение не подписывает тело: это отдельная доказанная идентичность, а тело по-прежнему защищается TLS на каждом участке. Пароли, Cookie и произвольные Authorization автоматически не копируются между сервисами.
- Для защищённых внешних WebSocket/SSE API после собственной аутентификации вызывает BindUserSession с проверенными sid и expiresAt. SDK связывает transport request/соединение с этой сессией даже после Hijack/возврата handler. Без истечения user assertion допустим максимум 15 минут непрерывной пользовательской авторизации от Bind; затем клиент выполняет новое подключение и проверку. Для delegated assertion срок потока дополнительно ограничен его exp; истечение HMAC handshake при этом не является сроком пользователя.
- Logout/блокировка пользователя/отзыв sid или jti публикуются уполномоченным identity-компонентом в защищённый revocation API. В control state сохраняется issuer+sid/jti и срок, событие получает монотонный cursor; только principal с правом на этот issuer может его создать. Gateway предоставляет `GET /outgate/revocations` на service mTLS listener: snapshot/delta по cursor с watermark, сроком актуальности и признаками gap/epoch. Это служебный endpoint, не SPA/service route; SDK получает только относящиеся к нему credential и issuer/session отзывы. Поток событий по туннелю служит ускорением, не единственным источником. SDK синхронизирует credential-отзывы не реже 2s, user-отзывы не реже 15s, сохраняет snapshot/cursor в локальном store и проверяет статус; активный защищённый поток закрывается не позднее 30s после отзыва, по истечении expiresAt — не позднее 5s. При недоступном revocation state поток закрывается не позднее 30s, а не остаётся бессрочно авторизованным.
- API проверяет права на чувствительные WebSocket-команды, размер сообщения (по умолчанию не более 1 MiB, без полной буферизации больших фрагментов), частоту сообщений и Origin allowlist. Браузерные cookie-handshakes с чужим/отсутствующим Origin отклоняются; исключения для небраузерных клиентов требуют явного режима service-auth. Logout обязан закрывать связи, а не только удалить cookie у браузера. Нагрузочные/негативные тесты выполняются с безопасными прикладными лимитами, не с CheckOrigin=true.

#### 5.5.5. Ограничение ресурсов, парсинг и защита сети

- До дорогих TLS/application операций используются сетевые connection/handshake limits; после определения principal — отдельные token buckets. Минимальная production-конфигурация задаёт публичный HTTP rate, per-IP, регистрацию, caller/target, Admin API, WebSocket handshakes, сообщения и общие активные соединения. Доверенные proxy CIDR задаются явно; иначе IP берётся только из socket peer, не X-Forwarded-For.
- Начальные пределы профиля: HTTP 1000 RPS/burst 2000 глобально, 20 RPS/burst 40 на IP; signed calls 1000 RPS/burst 2000 глобально и 100 RPS/burst 200 на caller; регистрации 30/min на service и 10/min на IP; WebSocket handshake 5/s на IP. Превышение — `429` с Retry-After. Администратор может изменять эти пределы после измерений и совместного пересчёта replay/memory budgets; 50 000 RPS не включаются одним отключением лимитов.
- По умолчанию не более 5000 внешних TCP-соединений глобально, 50 на IP, 1000 открытых WebSocket/SSE глобально и 10 защищённых потоков на user sid. Есть отдельные квоты service/target и предел туннелей на service (16), не только общий max_tunnels. Масштабирование лимитов требует расчёта RAM/FD/CPU; все уровни действуют одновременно.
- Общий бюджет буферов gateway — 512 MiB, одного service — 64 MiB, одного туннеля — 16 MiB. Новый stream/кредит резервирует бюджет до выдачи окна; переполнение не приводит к скрытому выделению памяти или бесконечной очереди. Для QUIC также ограничиваются соединения, streams и receive windows. Медленный stream не держит общую блокировку; при перегрузке корректно завершается только его операция. Итоговый concurrency — минимум лимитов SDK, туннеля, сервиса и глобального бюджета.
- ReadHeaderTimeout 5s, TLS/Upgrade handshake timeout 10s, max header bytes 32 KiB, максимум 100 header fields, максимальная request line 8 KiB. Для ненулевых HTTP request bodies после 10s прогрева требуется средняя скорость не ниже 1 KiB/s за окно 30s, иначе соединение/stream завершается; SSE/idle WebSocket не оцениваются как HTTP upload. Длительные легитимные операции ограничиваются своими квотами/сессионными сроками, а не отключением глобальных защит.
- Публичный Host/:authority должен точно соответствовать настроенному allowlist доменов с разрешёнными портами; неожиданный Host получает `421`. Не допускаются duplicate Host, неоднозначные Content-Length, конфликт Transfer-Encoding+Content-Length, obs-fold, управляющие символы и неоднозначная Outgate/identity metadata. Стандартный parser не заменяется ручным split строк; HTTP/1 framing не переносится в HTTP/2/3 headers. CONNECT на публичном слушателе запрещён, внутренний CONNECT ограничен фиксированным byte-channel endpoint аутентифицированной сессии без произвольного host/port.
- Корректность Path/RawPath, escaped slash/backslash, dot segments, duplicate headers и порядок signature verification → mount strip проверяются единым набором тестов для HTTP/1.1, HTTP/2, HTTP/3 и WSS, включая встроенный HTTP/1.1 WebSocket bridge. Fuzzing decoder/multiplexer/HTTP bridge обязателен. Направление HTTP proxy не выбирается из клиентского URL/Host/metadata; upstream, JWKS и служебные адреса фиксируются администратором.
- Межсервисный mTLS endpoint, service CA, Admin API, выбранный PostgreSQL endpoint и опциональный Redis доступны только из разрешённой сети/через firewall; browser HTTP и необходимые tunnel ports — единственные публичные поверхности. Для публичного QUIC используется штатная anti-amplification/address validation библиотеки. Внешний L4/L7 DDoS-фильтр должен поддерживать UDP либо закрывать его, оставляя WSS; приложение не обещает отражать объёмный DDoS самостоятельно.

#### 5.5.6. Единый browser origin и административная плоскость

- Один origin разрешается только для компонентов одного уровня доверия. Недоверенные сервисы, пользовательские HTML/JS и загружаемые файлы выносятся на отдельные origins без общих session cookies. Смена origin для таких данных — требование эксплуатации, а не опциональная компенсация HMAC; пути и cookie Path не являются изоляцией браузера.
- Для `/api` по умолчанию разрешены JSON и явно настроенные безопасные MIME-типы; HTML/JS в API-ответе не публикуются inline. Загрузки возвращаются как attachment либо с отдельного download origin. Gateway добавляет X-Content-Type-Options:nosniff и HSTS max-age=31536000 (без preload/includeSubDomains до отдельной проверки владельцем домена). SPA задаёт CSP с явным script-src без unsafe-eval/unsafe-inline, frame-ancestors и ограниченным connect-src. Конкретный CSP подтверждается тестами реальной сборки, не заменяется шаблонным разрешением всех источников.
- Service worker по умолчанию отключён: запросы загрузки с Service-Worker:script отклоняются, Service-Worker-Allowed из API удаляется. Включение допускается только для назначенного frontend с явным перечнем скриптов/максимальным scope. Обычный сервис не может расширить SW scope до `/`.
- Set-Cookie фильтруется по service allowlist имён и допустимым Domain/Path после mount rewrite. По умолчанию session cookie — Secure, HttpOnly, SameSite=Lax, без Domain; cross-site режимы требуют явного обоснования и CSRF-тестов. Общие cookie, включая __Host-, может устанавливать только назначенный владелец session/identity; обычный API не может перезаписать cookie другого сервиса. SameSite не заменяет CSRF-токены/Origin-проверку для изменяющих состояние cookie-запросов. CORS по умолчанию не включён; wildcard origin с credentials запрещён.
- Admin API и метрики не проксируются через service routes/root override. Production Admin API требует выделенного admin CA и mTLS: для CLI — индивидуальный admin principal/секрет, для веб-консоли — разрешённый BFF certificate вместе с проверяемым access JWT пользователя по п. 3.19 и 6.2. Роль viewer/deployer/security_admin определяется сервером; service CA и service tokens административных прав не дают. Сетевой доступ — VPN/изолированная management network; доступ людей к ней защищён MFA. Loopback сам по себе не считается достаточной аутентификацией.
- Viewer читает состояние, deployer создаёт grant/активирует маршруты, меняет rollout и вручную переключает готовый active-passive экземпляр, security_admin отзывает credentials и управляет политиками/импортом/root override. Все изменения содержат actor, revision, время, request ID и безопасную разницу; секрет/полная подпись/JWT никогда не записываются. Аудит отправляется во внешнее защищённое хранилище; ошибка его устойчивой локальной очереди запрещает mutating Admin API. Метрики не включают user/sid/raw URL и защищены от внешнего чтения.
- Production API дополняется: `POST /admin/deployment-grants`, `POST /admin/revocations`, `DELETE /admin/tunnels/{instance_id}` (немедленно), `POST /admin/routes/activate`, `POST /admin/config/import`, `PUT /admin/frontend-override`. Mutating операции требуют revision и соответствующей роли, выдача grant возвращает секрет только один раз. Импорт, изменяющий interservice ACL/internal_only, дополнительно требует свежего MFA пользователя, reason и одноразового preview по п. 3.20: сервер извлекает из импорта candidate access snapshot и проверяет его hash и базовую revision, чтобы импорт не обходил редактор прав. Отдельный `/outgate/session-revocations` на service mTLS listener принимает отзывы user sid/jti только от principal с правом соответствующего issuer. Интерфейсы/HTTP ошибки/идемпотентность административных команд документируются до реализации и тестируются; service listener не маршрутизирует свои служебные пути в SPA.
- Источники ключей и сертификатов монтируются отдельно; поддерживается атомарное обновление keyring/certificates через явный аутентифицированный reload секретов на обеих ОС либо SIGHUP только на Linux без полного reset control state. Невалидный новый keyring не заменяет рабочий, событие аудируется; отозванный ключ не восстанавливается из старого файла. Секреты issuer/admin/gateway недоступны контейнерам обычных API и frontend.

#### 5.5.7. Сборка, эксплуатация и границы гарантий

- Go toolchain, Outgate revision, прямые/транзитивные зависимости и container base фиксируются; CI запускает go test/race/vet, govulncheck, сканирование образа/секретов и выпуск SBOM. Релиз блокируется при достижимой Critical/High уязвимости без исправления или подписанного ответственным временного исключения с compensating controls и сроком. Проводится повторная проверка зависимостей перед каждым публичным релизом.
- Production image и нативные Linux/Windows release archives публикуются по digest с подписью доверенного CI; deployment сверяет подпись/digest до выдачи grant. Для Windows выдаются SHA-256 manifest и проверяемая подпись артефакта (Authenticode для exe — дополнительный механизм); PowerShell-процедура проверяет manifest до установки. Для внешних непроверенных образов/бинарников grant автоматически не выдаётся. Администратор может допустить конкретный проверенный digest, но version label не заменяет проверку артефакта.
- Должны быть runbooks: отзыв сервиса/ключа/пользователя, компрометация frontend/issuer, переполнение ресурсов/replay, потеря локального control/replay диска, отказ/restore PostgreSQL либо опционального Redis, восстановление backup без replay, обновление сертификатов, безопасный root switch и откат. Алерты: credential failures, неизвестный kid, replay/квоты, рост buffer/FD, состояние storage, отказы маршрутов и изменения admin policies.
- Для неидемпотентных операций API реализует и тестирует собственные idempotency keys/уникальные operation IDs; nonce защищает передачу, но не повтор бизнес-операции с новым nonce. Объектные/tenant-права и SQL/XSS/SSRF-защита внутри handler остаются обязанностью API и входят в security-приёмку демонстрационных операций.
- Единственный gateway и его хранилище (локальная SQLite либо внешний PostgreSQL, при выборе Redis — также replay backend) остаются точками отказа: профиль требует отказа в доступе при потере доверенного state, а не обещания непрерывной работы. SLA 99.9% и 50 000 RPS подтверждаются отдельным эксплуатационным/нагрузочным проектом. При повышении производительности защитные меры не отключаются.

#### 5.5.8. Равноправные SQL backend: SQLite и PostgreSQL

- Оба SQL backend входят в первую версию, включая production на Linux amd64 и нативной Windows amd64. Выбор независим для gateway control, gateway replay, каждого SDK replay и BFF sessions. Поддерживаются однородные и смешанные профили; gateway PostgreSQL не обязывает SDK отказываться от локальной SQLite. Redis остаётся опциональным только для replay. Транспорты, права, revisions, nonce retention/recovery и результаты Admin API не зависят от SQL backend.
- SQLite — встроенный вариант без DB-сервера; PostgreSQL — отдельный локальный либо удалённый сервер, настраиваемый оператором. PostgreSQL не встраивается в `.exe` и не становится обязательным для Windows. Поддерживаемые major/minor версии сервера и Go-драйвер фиксируются в матрице релиза; обещание совместимости с любой версией не допускается. Клиентский драйвер включён в бинарник, отдельные psql/libpq/компилятор оператору не требуются.
- PostgreSQL использует обычные WAL-logged таблицы, `fsync=on`, `full_page_writes=on`, `synchronous_commit=on` либо более строгий режим. TEMP/UNLOGGED, async commit, чтение решений безопасности с lagging replicas запрещены. Транзакции control/replay/session выполняются на writable primary; подтверждённый commit предшествует успешному ответу Admin API и передаче защищённого запроса. Timeout/обрыв соединения во время commit имеет неопределённый результат: запрос не отправляется и не повторяется автоматически; оператор/API читает итоговую revision при восстановлении.
- Single primary PostgreSQL не гарантирует сохранения подтверждённых nonce при продвижении асинхронной реплики. Если настроен failover, topology обязана сохранять все подтверждённые security записи посредством синхронной репликации и fencing старого primary. Иначе после failover/restore применяется fail-closed recovery с восстановлением отзывов и barrier; бесшовный автоматический failover с возможной потерей nonce не заявляется. PostgreSQL не добавляет кластерную HA шлюзу: остаётся один активный gateway/control writer.
- Gateway владеет именованной блокировкой одного control state (идентификатор стабилен и задаётся installation/database/schema, не случайным ID процесса): SQLite — OS lock, PostgreSQL — session advisory lock на выделенном прямом соединении. Control-транзакции исполняются на этом же соединении с сериализацией; второй gateway с тем же control schema получает ошибку. Потеря owner connection/lock запрещает новые назначения/изменения, снимает readiness и требует повторного получения lock и синхронизации state до возобновления. Transaction pooling proxy для этого соединения не допускается. Это защита от случайного двойного запуска, не распределённый кластерный протокол.
- Для PostgreSQL обязательны TLS с проверкой CA/hostname (`verify-full`), ограниченный пул/очередь, connect/query/lock timeouts и параметризованный SQL. URL/DSN, пароль и client key не возвращаются в UI/логи/метрики. Production подключается к закрытому DB endpoint, не публикует PostgreSQL в интернет. Серверный TLS минимум 1.3 согласно общему профилю проекта. ACL service/management сетей допускает только необходимые соединения с выбранным DB endpoint.
- Gateway control, gateway replay, каждый SDK verifier и BFF используют разные схемы и DB principals. Runtime principals не имеют superuser/CREATEDB/CREATEROLE/BYPASSRLS, DDL или доступа к чужим схемам; runtime не владеет схемой и не может изменять объекты другого участника; search_path фиксируется только на доверенные схемы без public/untrusted write. SQL обращается к schema-qualified объектам. Каждый SDK получает доступ только к собственной replay схеме; service identity не даёт доступа к gateway control либо session tokens. Изоляция схем не заменяется только фильтром namespace из клиентского запроса.
- Bootstrap и versioned migrations выполняются отдельной ограниченной migration-role/командой под migration lock, не автоматически каждой replica при startup. Runtime проверяет schema version; несовместимая схема блокирует запуск. UI не запускает произвольный SQL и не меняет DB credentials. Backup/restore, PITR, cleanup индексов/expired nonce, vacuum/bloat и диск/WAL мониторятся; restore security state сохраняет общую процедуру восстановления п. 5.5.2. Переключение SQLite ↔ PostgreSQL — явная offline migration с проверкой целостности, сохранением ревизий/отзывов/epoch и recovery barrier, не fallback при отказе.

### 5.6. Единая модель таймаутов, readiness и повторов

| Этап | Default | Правило истечения |
| :--- | :--- | :--- |
| TCP/QUIC connect и TLS handshake | 5s каждый, вместе не более 10s | Ошибка соединения, ещё без передачи бизнес-запроса |
| Registration | 10s после защищённого connect | Сессия не активируется, cleanup и reconnect по классификации ошибки |
| External request headers | 5s | HTTP parser закрывает/отклоняет медленный запрос; до routing |
| Ожидание response headers | 60s | 504, если ещё не отправлены внешние headers; иначе abort |
| Body idle HTTP/SSE | 60s | Отмена только запроса; после headers abort, до headers 408 для upload/504 для downstream |
| Общий deadline HTTP/SSE | 0s — отключён | Если задан/передан context deadline — min всех общих deadlines |
| WebSocket handshake | 10s | 504 до внешнего 101; нет автоматического retry |
| WebSocket application idle | 0s — отключён | При настройке закрывается только app stream, не весь tunnel |
| Заблокированная запись WebSocket | 10s | Закрытие app stream; не общий срок жизни соединения |
| QUIC keepalive/connection idle | 15s / 45s | Потерянная сессия исключается, её in-flight запросы abort |
| WSS ping / pong / missed pongs | 15s / 10s / 2 | Два последовательных неполученных pong закрывают tunnel; активный body не заменяет pong |
| WSS frame write / cancel ack | 10s / 10s | Неисправная session закрывается, без доставки её запросов заново |
| Readiness callback | 2s | unavailable, без неограниченного callback accumulation |
| Credential callback | 5s | Сохранение ещё действующей пары, retry только получения credentials |
| DB connect / query / lock | 5s / 5s / 2s | Bounded failure, при неопределённом commit — п. 3.23, без fail-open |
| Graceful drain | 30s | Принудительное завершение остатка, Close сообщает deadline |
| Production startup/replay barrier | минимум 120s | До окончания signed ingress не готов, bypass не допускается |

- Конкретные YAML поля существующих routing/tunnel/websocket/storage sections соответствуют таблице; новые connect/TLS значения входят в transport schema, callback/drain — в SDK security configuration. Register timeout не включает startup barrier: соединение/ack допустимы в registered, но instance ready=false до завершения защиты. Healthz остаётся диагностическим; readyz возвращает 503 до готовности всех обязательных stores/identity/listeners. Admin read/status доступен в recovery, mutating недоступен до восстановления целостности state. Текущие готовые экземпляры не останавливаются из-за startup barrier другой реплики.
- Обещание reconnect `2 * MaxDelay` относится к восстановлению соединения/регистрации после обнаруженного разрыва, а не к окончанию barrier или готовности приложения. Метрики отдельно измеряют connect/register/ready, и UI показывает причину ожидания. Запуск с готовым store всё равно соблюдает установленный п. 5.5.2 startup cutoff; health probe/startup grace в deployment по умолчанию не менее 180s.
- Header timeout начинается после отправки headers запроса в выбранный upstream/tunnel; body idle контролируется отдельно по направлениям, пока каждое открыто. Idle сбрасывается только при передаче полезных bytes downstream: накопление в очереди, tunnel ping и HTTP headers не считаются прогрессом тела. SSE producer отправляет heartbeat чаще idle timeout либо администратор явно задаёт иной idle policy. Полный deadline WebSocket после 101 заменяется его собственным idle/session expiry/revocation limits, не обычным HTTP timeout.
- Операции делят оставшийся parent deadline: новый этап не получает дополнительные 60s поверх истёкшего родительского времени. На deadline отменяется соответствующий stream/context, освобождаются credit/nonce transient counters/DB pool wait; уже committed nonce не удаляется. Истечение после headers не заменяет ответ JSON-ошибкой. Статус/событие диагностики содержит timeout stage без секретов. Panic readiness/credential callback перехватывается как callback_failed, не завершает процесс и не заменяет рабочие credentials; readiness становится false при отсутствии пригодного результата.
- Нулём можно отключать только явно помеченные overall/application idle значения; отрицательные интервалы, отключение security expiry/registration/DB write/callback limits запрещены. Config validation проверяет соотношения heartbeat/pong/idle, timeout/drain и operational startup grace. Security expiry/revoke всегда имеют приоритет над drain и app idle.
- Политика «не повторять после начала передачи» обязательна на всех слоях: frontend reverse proxy, SDK HTTPS RoundTripper, QUIC/WSS adapters и DB-result handling. Transport нельзя считать безопасным только потому, что приложение не содержит retry-loop: стандартные HTTP библиотеки могут повторять GET/HEAD и запросы с Idempotency-Key/GetBody. Реализация должна исключать повтор по мере начала отправки данного бизнес-запроса; попытка нового соединения до передачи любых bytes допустима. Admin API повтор по тому же operation key — отдельный явный механизм, не скрытый retry произвольного запроса.

## 6. Конфигурация шлюза

Пример локального development-стенда смешанного режима; он не удовлетворяет production-профилю без обязательных дополнений п. 6.1. Отключение одного адаптера не меняет маршруты и политики другого:

```yaml
deployment:
  mode: development

server:
  https_addr: "127.0.0.1:8443"
  tls:
    cert_file: "./certs/server.pem"
    key_file: "./certs/server-key.pem"

upstream:
  url: "http://127.0.0.1:8080"     # SPA по умолчанию, сохраняется при override

frontend_override:
  enabled: true                   # default: false
  service_id: "frontend-service"  # только этот сервис может регистрировать /

tunnel:
  quic:
    enabled: true
    addr: "127.0.0.1:7171"                 # UDP
    keepalive_interval: 15s
    idle_timeout: 45s
  wss:
    enabled: true
    addr: "127.0.0.1:7172"                 # TCP
    path: "/tunnel"
    ping_interval: 15s
    pong_timeout: 10s
    missed_pongs: 2

    initial_window_bytes: 65536
  tls:
    cert_file: "./certs/server.pem"
    key_file: "./certs/server-key.pem"
  register_timeout: 10s
  max_control_message_bytes: 65536
  max_paths_per_instance: 32
  max_versions_per_service: 100
  max_inflight_per_tunnel: 1000
  max_tunnels: 1000
  shared_paths: ["/health", "/metrics"]

  mode: bearer
  bearer_tokens:
    - token: "replace-with-service-secret"
      service_id: "my-service"
    - token: "replace-with-reports-tunnel-secret"
      service_id: "reports-service"
    - token: "${OUTGATE_FRONTEND_TUNNEL_TOKEN}"
      service_id: "frontend-service"

  frontend-service:
    allowed_paths: ["/"]          # точное право на корневой override, не на поддеревья
    rollout:
      stable_version: "2026.11.21"
      canary_version: null
      canary_percent: 0

    allowed_paths: ["/api/v1", "/health", "/metrics"]

      stable_version: "1.4.2"

  signature_ttl: 60s
  clock_skew: 30s
  replay_cache_max_entries: 100000
  trusted_attributes:
    tenant_id: "X-User-Tenant-ID"
  context_limits:
    user_id_bytes: 128
    roles: 32
    role_bytes: 64
    attributes: 16
    attribute_value_bytes: 1024

  callers:
    my-service:
      keys:
        - key_id: "my-call-1"

      active_key_id: "gateway-reports-1"

        - key_id: "gateway-reports-1"

    - caller: "my-service"
      target: "reports-service"

      allow_background: true

  strategy: round_robin           # default; сервис может выбрать active_passive

  body_idle_timeout: 60s

  addr: "127.0.0.1:9090"           # /healthz, /readyz, /metrics

```

`services` задаёт разрешения и начальные политики, но само по себе не регистрирует маршруты. Для сервисов в credential должен существовать раздел services; стабильная версия и upstream URL обязательны. WSS путь должен быть абсолютным HTTP-путём без query/fragment. Значения `enabled` по умолчанию: QUIC `true`, WSS `false`; для смешанного режима WSS включается явно, как в примере.

Env-переменные имеют приоритет над YAML; префикс `OUTGATE_`, вложенные имена разделяются `_`, например `OUTGATE_TUNNEL_WSS_ENABLED=true`. В строковых полях токенов допускается ссылка `${VAR}` на переменную окружения: она разрешается после разбора YAML и не интерпретируется повторно как YAML. Неопределённая или пустая переменная токена — ошибка запуска, значение никогда не выводится в логи. Env-переопределение структурных карт/списков в прототипе не требуется. Все лимиты, интервалы и проценты валидируются при запуске; неизвестные поля отклоняются. В development политики Admin API действуют до перезапуска; в production начальная политика YAML используется только для первичного создания control state. Дальнейшие изменения API сохраняются устойчиво; повторная загрузка YAML не сбрасывает их. Изменение YAML-политик production выполняется явной импорт-операцией администратора с проверкой ревизии состояния. Hot reload YAML не входит в прототип. `interservice` настраивает только межсервисные полномочия; пользовательские public/private маршруты здесь не задаются. Политики по умолчанию пусты, резерв API по умолчанию `["/api"]`. Каждый caller/target ссылается на известный service_id; для разрешённых target обязателен набор recipient keys и единственный active key ID, для caller — принимаемые ключи. Одно совпавшее правило должно разрешать одновременно путь, метод и вид контекста; частичные разрешения из разных правил не суммируются. На стороне сервисов загружаются соответствующие независимые ключи с теми же лимитами и replay-настройками. Профиль времени 60s/30s общий для участников, несовместимые значения отклоняются при запуске.

Для reports-service пример включает active-passive. Запускаются три одинаковые сборки с разными WithInstanceID: reports-main, reports-backup-1, reports-backup-2 и одинаковым WithVersion("1.0.0"). Для production каждый ID имеет собственные certificate/grant и WithReadinessCheck; порядок не извлекается из порядка регистрации. Canary-версия получает отдельный instance_order перед назначением доли. Неподдерживаемая стратегия, пустые/повторяющиеся IDs, отсутствующий order положительной версии, timeout>=interval, status_timeout<2*interval и отрицательная recovery_hold_down отклоняют конфигурацию.

### 6.1. Конфигурация production и обязательные зависимости

Ниже — фрагмент конечного production YAML, дополняющий общую схему п. 6. Поля демонстрационного deployment.mode/auth/admin заменяются целиком, development bearer tokens удаляются; неявного merge с демонстрационными секретами нет. Адреса, cert/CA/secret files, issuer и служебные принципы заменяются реальными значениями до запуска. Фрагмент не заменяет выпуск сертификатов, настройку постоянных локальных каталогов/ACL и выдачу grants: запуск с отсутствующими/некорректными источниками обязан завершиться ошибкой.

Для остальных principals роли задаются отдельно, а не общим токеном. Grant и service certificate формируют identity по шаблону `spiffe://<trust_domain>/service/<service_id>/instance/<instance_id>`; IDs ограничены ASCII буквами/цифрами, `.`, `_`, `-`, длиной 1–128, service_id — до 64. Разделители URI, percent encoding и управляющие символы в ID запрещены. Admin CA — отдельный trust anchor. Server certificates public/tunnel/interservice могут быть общими для домена, но CA клиентских identities и secrets ролей не объединяются.

В конечном YAML дополнительно обязательны: tunnel listeners/TLS, services с initial rollout и grants permissions, callers/recipients HMAC keyrings и policies, upstream TLS trust, cookie/Origin/CSP policies реального frontend/API, разрешённые issuers для session revocations и внешняя очередь audit. Туннельные grant credentials и клиентские сертификаты подаются сервисам отдельно, не в SPA assets. SDK получает такой же профиль issuer/replay/revocation, собственную постоянную SQLite replay DB/каталог либо изолированную PostgreSQL schema/роль и mTLS-доступ к revocation API; для опционального Redis — отдельный ACL principal только своего namespace; настройка этих зависимостей входит в поставку библиотеки и примеры production bootstrap.

Production startup проверяет presence/формат обязательных полей, выбранные control/replay stores: для SQLite — файлы/epoch/WAL/FULL/блокировки/место, для PostgreSQL — TLS/primary/schema version/права/durable settings/owner lock; для обоих — recovery barrier, источники ключей/сертификатов, allowlists, active key IDs и расчёт replay capacity. Первый bootstrap создаёт SQLite БД либо PostgreSQL schema только явной операцией инициализации, не после неожиданной потери файла/таблиц. SDK дополнительно проверяет актуальный revocation snapshot. Для опционального Redis его persistence/ACL/TLS подтверждаются отдельным health principal/deployment probe без выдачи приложению CONFIG/FLUSHALL; результат проверки должен быть актуален не более 30s и привязан к backend/epoch. Отдельный Linux sidecar или `/run/outgate/redis-health.json` не требуются для SQL backend и нативной Windows-поставки. Потеря зависимости не переключает production на development.

В production межсервисный gatewayURL/WithTLS использует mTLS endpoint `https://gateway.example.com:9443` и client certificate, а не браузерный origin :8443. Браузерный listener отклоняет предъявленные Outgate-service credentials с `403`; внутренние вызовы, управление grants и отзывы не доступны через SPA fallback. Изменение security limits, internal-only правил, root override и credentials применяется только валидированной транзакцией control state/импортом с revision; reload секретов не перезагружает маршруты из старого YAML.

### 6.2. Конфигурация административной веб-консоли

Фрагмент описывает отдельный процесс outgate-admin-web и дополнительные поля Admin API. Поля `admin` объединяются в конечной конфигурации с TLS/principals из п. 6.1 без дублирования YAML-ключа; BFF-конфигурация развёртывается отдельно от конфигурации публичного gateway. Все домены/subjects/файлы задаются оператором. Admin IdP может быть тем же программным продуктом, что user issuer, но имеет отдельные client/audience, role mapping и assurance policy.

```yaml
admin_web:
  enabled: true
  addr: "10.0.0.11:9444"
  public_origin: "https://outgate-admin.example.net:9444"
  tls:
    cert_file: "/run/secrets/admin-web-server.pem"
    key_file: "/run/secrets/admin-web-server-key.pem"
  oidc:
    issuer: "https://admin-identity.example.net/"
    client_id: "outgate-admin-web"
    client_secret_file: "/run/secrets/admin-web-oidc-client"
    redirect_uri: "https://outgate-admin.example.net:9444/auth/callback"
    api_audience: "outgate-admin-api"
    required_acr_values: ["urn:outgate:mfa"]
  session:
    store: sqlite
    path: "/var/lib/outgate-admin-web/sessions.db"
    journal_mode: WAL
    synchronous: FULL
    encryption_key_file: "/run/secrets/admin-web-session-key"
    idle_timeout: 15m
    absolute_timeout: 8h
    privileged_auth_max_age: 5m
  admin_api:
    url: "https://outgate-management.internal:9091"
    ca_file: "/run/secrets/admin-server-ca.pem"
    client_cert_file: "/run/secrets/admin-web-client.pem"
    client_key_file: "/run/secrets/admin-web-client-key.pem"
admin:
  web_delegation:
    certificate_uri: "spiffe://outgate.example/admin-web"
    issuer: "https://admin-identity.example.net/"
    jwks_url: "https://admin-identity.example.net/.well-known/jwks.json"
    algorithms: ["RS256"]
    audience: "outgate-admin-api"
    required_acr_values: ["urn:outgate:mfa"]
    privileged_auth_max_age: 5m
    role_bindings:
      - subject: "admin-operator-subject"
        role: viewer
        service_ids: ["*"]
      - subject: "admin-operator-subject"

        service_ids: ["*"]
      - subject: "release-operator-subject"
        role: viewer

      - subject: "release-operator-subject"

        role: viewer
        service_ids: ["my-service"]
```

BFF выбирает собственную SQLite DB с отдельным OS account/ACL или PostgreSQL session schema с отдельной ограниченной ролью; не получает доступ к control/replay данным. Несколько BFF-реплик требуют отдельного проекта HA даже при общей PostgreSQL; в первой версии один BFF. Записи с tokens шифруются серверным session key, browser cookie не содержит JWT. Ключи и OIDC secret не доступны в frontend build/static files. После каждого старта BFF прежние сессии инвалидируются до обслуживания браузера, чтобы восстановленная старая DB не возобновляла logout-сессии; требуется новый OIDC-вход. Потеря session store разлогинивает/блокирует консоль, но не меняет политики шлюза и не включает анонимный вход. CSP/Origin/Host и exact callback URI валидируются при запуске; произвольный admin_api.url/return URL из браузера не принимается, BFF не является универсальным HTTP-прокси.

Admin API принимает user JWT web-ветки только в сочетании с разрешённым mTLS BFF certificate; CLI user assertion принимается отдельно только для явно bound certificate principal по п. 3.24. Он не принимает ID token вместо access token или обычный API user assertion. Admin IdP должен включать проверяемые auth_time и acr/amr в access token для этой audience. Нет явного role binding — нет административного доступа. Изменение role bindings/trust roots выполняется защищённой эксплуатационной конфигурацией, не редактором межсервисных прав. Role changes инвалидируют соответствующие admin sessions/кеши в пределах 5s.

Для старых CLI/headless principals остаются сертификат и индивидуальный token по п. 6.1. Применение security policy через PUT и config import, меняющий те же ACL/internal_only, требует такого же подтверждённого user principal со свежим MFA и preview diff; машинный deployer не обходит это импортом. Автоматизация выпуска grant/rollout остаётся в своей роли без получения policy_write. Режим «без IdP, общий admin secret в JavaScript» в production запрещён.

### 6.3. Нативная конфигурация Windows и профиль без Redis

Схема YAML общая для обеих ОС. Ниже — заменяемые storage/TLS поля конфигурации шлюза; это фрагмент, а не второй YAML поверх работающего процесса. Все остальные secret/cert/CA, audit и BFF paths из п. 6.1–6.2 также задаются Windows-путями в полном поставляемом примере `gateway.windows.yaml`/`admin-web.windows.yaml`. Использование `/` в Windows paths допустимо; backslash в double-quoted YAML требует экранирования.

```yaml
storage:
  control:
    driver: sqlite
    path: "C:/ProgramData/Outgate/gateway/control.db"
    journal_mode: WAL
    synchronous: FULL
  replay:
    driver: sqlite
    path: "C:/ProgramData/Outgate/gateway/replay.db"
    journal_mode: WAL
    synchronous: FULL
    namespace: "outgate:gateway"
    recovery_barrier: 120s
server:
  tls:
    cert_file: "C:/ProgramData/Outgate/secrets/gateway.pem"
    key_file: "C:/ProgramData/Outgate/secrets/gateway-key.pem"
```

- Gateway, BFF и каждый service instance имеют разные каталоги и service accounts. BFF session path: `C:/ProgramData/Outgate/admin-web/sessions.db`; SDK verifier path, например: `C:/ProgramData/MyService/instance-1/replay.db`. Секреты SDK принадлежат только соответствующему сервису. Оператор создаёт каталоги/ACL до bootstrap; служба не использует текущий каталог `System32` и не требует записи рядом с exe.
- Для SQLite SDK `storage.replay` использует те же driver/path/journal_mode/synchronous/namespace/recovery_barrier поля; PostgreSQL-настройки определены в п. 6.4; namespace уникален для service_id/instance_id. Revocation endpoint — mTLS gateway URL, identity credentials берутся из текущего service certificate/grant. Размеры capacity и caller-квоты задаются профилем SDK, а не безусловно копируются с gateway. SDK не получает административный доступ к control DB.
- Обязательный однопроцессный production-профиль стартует без установленного Redis и без попыток соединения с ним: control/replay/session — встроенная SQLite, отзывы доставляются собственным mTLS API. OIDC/identity issuer, DNS/TLS и инфраструктура аудита остаются настроенными эксплуатационными зависимостями; «без Redis» не означает автономную пользовательскую аутентификацию.
- Для опционального Redis replay adapter схема задаёт `driver: redis`, `url: rediss://...`, `username`, `password_env`, `ca_file`, `namespace`, `require_aof: true`, `require_appendfsync: always`, `require_noeviction: true`, `recovery_barrier: 120s`. Конкретная поддерживаемая версия фиксируется в релизе. SQLite path-поля вместе с Redis-полями отклоняются. Перенос nonce между backend выполняется offline по runbook с recovery barrier, не hot fallback; Windows-профиль не требует локального запуска Redis.
- CLI-команда bootstrap, примеры PowerShell и Windows Service wrapper входят в реализацию. Приёмка проверяет команды на чистой ОС, а не только правильность YAML. Создание службы не выдаёт права локального администратора её runtime account.

### 6.4. Конфигурация PostgreSQL и независимый выбор backend

SQLite-примеры п. 6.1–6.3 остаются действующими и используются по умолчанию. Для PostgreSQL соответствующий раздел заменяется целиком; скрытого merge SQLite path/WAL настроек с PostgreSQL-параметрами нет. Пример показывает разные principals/schema для одного DB server; BFF запускается отдельным процессом со своим поднабором конфигурации и credentials.

```yaml
storage:
  control:
    driver: postgres
    host: "postgres.internal"
    port: 5432
    database: "outgate"
    schema: "outgate_control"
    user: "outgate_control_runtime"
    password_env: "OUTGATE_CONTROL_PG_PASSWORD"
    sslmode: verify-full
    ca_file: "./certs/postgres-ca.pem"
    max_connections: 4
    connect_timeout: 5s
    query_timeout: 5s
    lock_timeout: 2s
  replay:
    driver: postgres
    host: "postgres.internal"
    port: 5432
    database: "outgate"
    schema: "outgate_gateway_replay"
    user: "outgate_replay_runtime"
    password_env: "OUTGATE_REPLAY_PG_PASSWORD"
    sslmode: verify-full
    ca_file: "./certs/postgres-ca.pem"
    max_connections: 8
    connect_timeout: 5s
    query_timeout: 5s
    lock_timeout: 2s
    namespace: "outgate:gateway"
    recovery_barrier: 120s
admin_web:
  session:
    store: postgres
    host: "postgres.internal"
    port: 5432
    database: "outgate"
    schema: "outgate_admin_sessions"
    user: "outgate_admin_sessions_runtime"
    password_env: "OUTGATE_ADMIN_SESSIONS_PG_PASSWORD"
    sslmode: verify-full
    ca_file: "./certs/postgres-ca.pem"
    max_connections: 4
    connect_timeout: 5s
    query_timeout: 5s
    lock_timeout: 2s
    encryption_key_file: "./secrets/admin-session-key"
    idle_timeout: 15m
    absolute_timeout: 8h
    privileged_auth_max_age: 5m
```

- Допустимые обязательные SQL selectors — `sqlite` и `postgres`: `storage.control.driver`, `storage.replay.driver`, `admin_web.session.store`. У SDK используется `storage.replay.driver` с той же схемой; backend SDK не наследуется автоматически от gateway. `postgresql`/неизвестный alias не принимаются молча. `redis` допустим только для replay при поставке опционального адаптера.
- PostgreSQL-поля host/port/database/schema/user/password_env/sslmode/ca_file и timeouts валидируются до соединения; отсутствующий secret — ошибка без вывода значения. Пароль можно альтернативно задавать `password_file`; одновременно password_env/password_file запрещены. Для client-certificate authentication допускаются `client_cert_file`/`client_key_file` вместо пароля, с обязательной проверкой серверного сертификата. Режим аутентификации выбирается явно наличием одного из этих комплектов; небезопасный trust не является альтернативой. Идентификатор schema допускает только заранее разрешённые простые SQL identifiers, а не пользовательский SQL.
- SQLite требует path/journal_mode/synchronous; PostgreSQL не принимает эти поля. Namespace/recovery_barrier относятся к replay, параметры encryption/session lifetimes — к BFF session store; драйвер не позволяет менять эти общие security требования. Redis-only поля в SQL backend отклоняются. Секреты берутся из окружения процесса/защищённых файлов; CLI arguments/UI их не содержат.
- У SDK для PostgreSQL задаются собственные user/schema/namespace, например `reports_1_replay_runtime` / `reports_1_replay` / `outgate:reports-service:reports-1`. Административные migration credentials и credentials других SDK ему не передаются. Получатель продолжает независимо проверять nonce, подписанный контекст и revocations; PostgreSQL не заменяет service certificate/HMAC.
- Startup проверяет schema version, durable server/session settings, writable primary и доступные privileges; при невозможности подтвердить обязательный профиль readiness=false. PostgreSQL endpoint доступен обоим нативным бинарникам по TCP/TLS, расположение сервера БД не меняет Windows/Linux модель запуска. Контрольный owner connection входит в max_connections control pool и не проходит через transaction pooling. Ожидание свободного соединения имеет deadline и ограниченную очередь; суммарный лимит DB connections рассчитывается по gateway/BFF/всем service instances.
- Конфигурации смешанных профилей входят в поставку: PostgreSQL control + SQLite gateway/SDK replay + SQLite sessions, а также полный PostgreSQL профиль с изолированными schemas. Offline migration-tool переносит данные выбранного store, сравнивает контрольные суммы/число записей/revisions и сохраняет source read-only до завершения проверки. Незавершённая migration не публикует target как рабочее состояние; работающий процесс не переключается между backend автоматически.

### 6.5. Профиль разработчика, bindings и артефакты контрактов

- Все конфигурационные поля документируются в config.schema.json: type/unit/default/range, mode-specific requirements, secret classification, reload policy и зависимости. Unknown/duplicate YAML keys запрещены; duration значения разбираются явно в указанных единицах, implicit boolean/date conversions не меняют тип поля. Есть две команды без сетевого трафика: `config validate` (с разрешением обязательных secret references без вывода значений) и `config explain` (эффективная конфигурация с полным redaction secrets/token/DSN). Их поддерживает gateway/BFF; bootstrap/migrate/recover — обязательные локальные maintenance subcommands, даже если отдельный Admin CLI не поставляется.
- Production instance_id и mounts задаются deployment-конфигурацией приложения и передаются SDK; библиотека не угадывает их из hostname. Grant binding включает mounts и generation-пару сертификата, но mount_id не даёт самостоятельного разрешения на prefix. Схема grants и credential-provider exchange документируется без реальных secrets.
- OIDC role_bindings содержат subject, role, service_ids; issuer берётся из фиксированной web delegation config, не поля браузера. CLI principal содержит список bindings {role, service_ids}, а не неявную глобальную роль. Пример ниже заменяет список role_bindings п. 6.2 целиком; admin-operator явно имеет global viewer/security_admin для bootstrap-оператора, release-operator — только release service scope. Grant release service scope не включает управление trust roots.

```yaml
role_bindings:
  - subject: "admin-operator-subject"
    role: viewer
    service_ids: ["*"]
  - subject: "admin-operator-subject"
    role: security_admin
    service_ids: ["*"]
  - subject: "release-operator-subject"
    role: viewer
    service_ids: ["my-service", "reports-service"]
  - subject: "release-operator-subject"
    role: deployer
    service_ids: ["my-service", "reports-service"]
  - subject: "observer-subject"
    role: viewer
    service_ids: ["my-service"]
```

- Каждый dev example запускается по одной документированной команде в Linux и PowerShell; production credentials/CA/IdP не имитируются development secret. Тестовый issuer/mock OIDC и fake clock входят в test harness, не в публичную default-конфигурацию. SDK examples включают WaitReady, независимый mount, graceful Close, background/user call, credential renewal и разбор typed error без string matching.
- Gateway repository содержит docs/protocol.md, docs/admin-openapi.yaml, docs/config.schema.json, docs/compatibility.md, docs/runbook.md, docs/upstream.md; test fixtures — tests/fixtures/protocol/v1, OpenAPI examples и migration manifests. Эти файлы создаются как результаты соответствующих этапов реализации; ТЗ не объявляет их существующими до фактической поставки. Каждое обязательное требование связывается с test case/этапом в acceptance matrix, изменение контракта без обновления артефактов и теста не принимается.

## 8. Критерии приёмки

### 8.1. Общая функциональность и транспорты

Единый параметризованный набор интеграционных сценариев запускается для QUIC-only, WSS-only и смешанного режима. Production setup предварительно создаёт допуск/grants и активирует маршруты; development setup использует тестовые bearer credentials. Эти setup не смешиваются:

1. `GET /api/v1/foo` попадает в зарегистрированный `http.Handler`: в preserve путь `/api/v1/foo`, в strip — `/foo`. Метод, Host, query, многозначные заголовки, статус и бинарное тело сохранены.
2. Незарегистрированный путь вне `/api` обслуживается frontend-upstream, включая его `404`; неизвестный `/api`-путь даёт `404` без HTML SPA, в том числе после перезапуска. Недоступный известный маршрут даёт `503`/`Retry-After: 1` без fallback или более короткого префикса.
3. Границы сегментов, вложенные префиксы, trailing slash, некорректный escaping, traversal и закодированные разделители проверены; неоднозначный путь отклоняется.
4. В round-robin реплики одного сервиса балансируются; mixed mode использует экземпляры обоих транспортов. В active-passive проверяется отдельный набор п. 8.9. Shared path доступен нескольким авторизованным сервисам; чужой исключительный путь отклоняется.
5. Ошибка одного пути не публикует остальные; токен чужого сервиса, отсутствие разрешений, duplicate instance ID, несовместимая версия и превышение лимитов дают ожидаемые причины.
6. Разрыв туннеля убирает экземпляр из выбора; реконнект и перезапуск шлюза восстанавливают регистрацию. Запрос, уже отправленный в туннель, не воспроизводится повторно, включая POST с побочным эффектом.
7. Проверены параллельные запросы, `429`, пустые тела, ранний ответ до окончания загрузки, отмена внешним клиентом, timeout, лимиты размера и очистка всех ресурсов.
8. Большая загрузка/выгрузка передаётся с ограниченной памятью. Первый SSE event приходит до закрытия потока; живой SSE продолжается дольше response header timeout без общего deadline.
9. Медленный получатель WSS исчерпывает своё окно, но не блокирует управление и другие готовые потоки; проверены переполнение кредита, неверная последовательность, закрытие в середине чанка и отмена с данными в пути.
10. Проверены оба отключённых адаптера (ошибка запуска), отключённый выбранный транспорт, недоступный UDP, неверный WSS path и недоверенный сертификат. Автоматического fallback нет.
11. `X-Request-ID`, forwarded headers и `traceparent` проверены для туннеля и fallback. Токены/тела не появляются в логах.
12. Graceful shutdown клиента и шлюза перестаёт направлять новые запросы в дренируемую сессию, завершает текущие либо отменяет их по deadline; новые подключения не дублируют instance ID.

13. Неизменённые WebSocket handlers `gorilla/websocket` и `coder/websocket` принимают внешнее WSS-подключение через каждый транспорт и fallback: работают `http.Hijacker`, deadlines и буферизованные после handshake байты. Проверены text/binary, большой фрагментированный обмен, Ping/Pong и Close с кодом/причиной.
14. Проверены subprotocol, Cookie/Authorization/Origin, отказ Origin-политики и пользовательской аутентификации, ответ без Upgrade, `permessage-deflate` и некорректный handshake. Внешний `101` не выдаётся до успешного ответа handler; tunnel credential не появляется в сервисе.
15. Несколько WebSocket работают параллельно с HTTP/SSE; медленный WebSocket имеет ограниченные буферы и не блокирует управляющий канал. Исчерпание concurrency возвращает `429` до Upgrade, слот удерживается после Hijack и освобождается после закрытия.
16. WebSocket остаётся открытым при длительном отсутствии сообщений с idle timeout 0 в пределах срока авторизации своей сессии, не обрывается HTTP body timeout/лимитом суммарного тела. Проверены явный idle timeout, заблокированная запись, разрыв транспорта, закрытие браузера и drain с принудительным завершением по deadline. Действующий туннель и соседние соединения при закрытии одного канала сохраняются.

### 8.2. Версии и канарейка

1. Успешная регистрация новой version создаёт одну запись обнаружения с временами и счётчиком экземпляров; повторная регистрация не дублирует версию, отказ не создаёт её. После отключения версия видна с нулём active.
2. YAML stable получает 100%; новый кандидат получает 0% и не становится stable автоматически. Пустая version отклоняется.
3. PUT устанавливает canary 10%, stable получает 90%. Выбор версии не зависит от числа её реплик и транспорта. В unit-тесте используется управляемый источник случайности; статистическая проверка большой выборки имеет заранее заданный допуск и не требует точной доли на нескольких запросах.
4. Проверены границы 0%/100%, неверные проценты, совпадающие stable/canary, неизвестная версия и отсутствие покрытия маршрутов. Неуспешное изменение не меняет предыдущую политику.
5. Promote переводит canary в stable и сохраняет previous stable; rollback во время канарейки и после promote работают по п. 3.5. Недоступная цель отката отклоняется без изменения политики.
6. Сбой canary после включения её доли даёт `503` для выбранных canary-запросов без скрытого перераспределения. Ручной rollback восстанавливает 100% stable; автоматического отката нет.
7. Изменение политики не обрывает уже начатые запросы, SSE и WebSocket. Открытый WebSocket остаётся на исходной версии/экземпляре после promote/rollback; новые подключения используют новую политику. Параллельные административные обновления применяются целиком, а не смешивают поля.
8. Admin API закрыт для внешнего клиента без admin token и для service token. Изменения отражаются в аудит-логе/метриках; в development после перезапуска действует YAML, в production сохраняются подтверждённые rollout и история, а активные сессии восстанавливаются только после новой проверки credentials.

### 8.3. Качество и поставка прототипа

- `go test ./...`, `go test -race ./...`, `go vet ./...` проходят во всех Go-модулях проекта. Проверки охватывают реестр, конкурентные регистрации/rollout, flow control и завершение фоновых задач.
- Клиентская библиотека имеет unit coverage ≥ 70% и интеграционные тесты обоих транспортов; coverage не заменяет проверку поведения.
- Docker Compose запускает шлюз, отдельный SPA-upstream, frontend-service с корневым туннелем, stable-экземпляры QUIC/WSS и canary-экземпляр, а также reports-service для межсервисных вызовов. Тестовый CA доверен клиентам; UDP и TCP порты опубликованы явно, секреты демонстрационные.
- Health/readiness/metrics доступны на служебном адресе. Серии содержат правильные service/version/transport и не включают request ID или произвольные URL.
- README содержит одну команду запуска и воспроизводимые запросы регистрации, API public/private, подписанного межсервисного вызова, SPA fallback, распределения 90/10, promote и rollback. Публичный API документирован godoc. Стенд содержит WebSocket echo-обработчики на `gorilla/websocket` и `coder/websocket` для проверки совместимости без изменений их прикладного кода.

Runbook объясняет отключение UDP, диагностику WSS, retained routes, 503 выбранной версии и потерю runtime-политик при рестарте только в development; production сохраняет политики.

### 8.4. Отдельная нагрузочная приёмка

Нагрузочный отчёт должен измерить цели п. 5.1 отдельно для каждого транспорта и mixed mode, включая 90/10 rollout, большие тела и медленных потребителей. Если цель не достигнута, фиксируются реальные показатели и ограничения; функциональная готовность прототипа не выдаётся за production SLA или подтверждение 50 000 RPS.

### 8.5. API-аутентификация, SPA и межсервисный доступ

1. Один API-префикс содержит публичный и защищённый endpoint: публичный работает без пользователя, защищённый возвращает отказ по решению API. Шлюз не запрашивает auth endpoint и не требует знания public/private маршрутов.
2. Внешние поддельные `X-User-ID`, `X-User-Roles`, дополнительные allowlist-атрибуты удаляются. Пользовательские Cookie/Authorization сохраняются; Outgate-маркер без подписи, неправильная подпись или предъявление `outgategateway` на публичном входе дают `401`, а не downgrade к внешнему режиму.
3. Проверенный API-контекст передаётся разрешённым A → B и B → C с ID, ролями и дополнительным атрибутом. Caller меняется на непосредственный сервис; неизвестный target, чужой origin и отсутствие signing key не отправляют запрос. Данные исходного request/context не мутируются.
4. Запрос с межсервисным Outgate-маркером без подписи и запрещённый подписанный вызов не достигают handler. Проверены запрет делегирования, background-доступ без пользовательских заголовков, путь/метод, shared path с указанным target и чужой вложенный префикс; fallback в SPA/другой сервис отсутствует. Обычный запрос без Outgate-полей остаётся внешним и проверяется API по его пользовательским правилам.
5. Изменение каждого обязательного подписанного компонента (метод, authority, path/query, caller, target, user/roles/атрибуты/manifest), просрочка, будущая дата, повтор nonce, неверный/чужой key ID и подпись получателю от ключа другого сервиса отклоняются. Тесты времени используют управляемые часы; параллельные одинаковые nonce не допускают двойную доставку.
6. Ротация старого/нового ключей проходит в обоих направлениях. Replay-кеш ограничен, живые записи не вытесняются; переполнение даёт `503`. Проверяется привязка recipient подписи к instance/version, отсутствие секретов в логах/Admin API и в production сохранение replay-состояния при рестарте и fail-closed при его потере; упрощённая потеря состояния проверяется отдельно только для development.
7. Большое/потоковое тело не читается для подписи, не буферизуется и не отправляется повторно после ошибки/redirect. Применение context через QUIC/WSS даёт одинаковые результаты. Canary цели выбирается обычным способом после проверки caller/target.
8. SSE и WebSocket получают проверенный контекст до handler/handshake; истечение HMAC-подписи handshake не закрывает соединение; в production истечение/отзыв пользовательской сессии или assertion отдельно прекращает защищённый поток по п. 5.5.4. Новое подключение проверяется заново; long-lived canary binding сохраняется. Для исходящего WebSocket выполняется профиль п. 10.4.
9. Frontend-upstream обслуживает `/` и клиентский SPA-маршрут, отсутствующий asset возвращает `404`; `/api`, `/api/v3/unknown` без регистрации не возвращают HTML. Обновление frontend без рестарта шлюза сохраняет API/туннели и обеспечивает согласованные HTML/assets с cache validators.

### 8.6. Проверка монтирования

1. Один и тот же бинарник с handler `/hello` разворачивается под `/api/v1` и `/api/v2` сменой конфигурации WithPaths, без изменений кода. Preserve сохраняет прежний полный путь, strip удаляет ровно выбранный префикс.
2. Проверены точный mount, завершающий `/`, несколько алиасов, вложенные маршруты, граница сегментов, query/escaping и согласованность Path/RawPath/RequestURI. Внешний X-Forwarded-Prefix не влияет на выбор, невалидная metadata отклоняется, в SPA fallback заголовок отсутствует.
3. Signed межсервисные запросы проверяются по публичному path и mount-префиксу до strip; подмена любого из них отклоняется. User context сохраняется, local handler принимает локальный путь, gateway policies проверяют публичный. Наследование context при B → C не переносит префикс B на C.
4. Для обоих транспортов проверены SSE и неизменённые WebSocket handlers под разными mount points, отказ handshake, subprotocol и Set-Cookie в `101`. Подписи и canary не зависят от локального переписывания пути.
5. Проверены root-relative и относительный Location, query/fragment, точный mount без trailing slash, сохранение абсолютных/external URL; отключение response rewriting не меняет заголовки. Cookie Path переписывается с сохранением остальных атрибутов, нескольких Set-Cookie, удаления cookie и исключения __Host-. Проверяется cookie path-match точного mount, дочерних путей и соседнего `/api/v10`.
6. Никакой URL в response body или WebSocket-сообщении не меняется автоматически; примеры показывают использование MountInfo и конфигурации base URL. Несогласованные режимы реплик одной версии отклоняются, режим доступен в Admin API.

### 8.7. Корневой frontend override

1. При выключенном override root-регистрация запрещена. При включённом зарегистрировать `/` может только назначенный service_id с собственным credential и allowed `/`; чужой токен со скопированным service_id не проходит. Нельзя атомарно получить root через набор с другими допустимыми путями, wildcard или shared_paths.
2. До первой активации запросы идут в upstream; после неё `/`, SPA client routes, assets и WebSocket идут в frontend-туннель. В development активация совмещена с первой регистрацией, в production выполняется явно. API и другие конкретные маршруты сохраняют приоритет; неизвестный `/api/...` возвращает `404` без HTML. Проверено отдельно для QUIC, WSS и смешанных frontend-реплик.
3. Отключение последнего frontend-экземпляра, неизвестная/недоступная stable или выбор недоступной canary возвращают `503` без скрытого fallback. Ответ frontend `404` не ищет ресурс в старом upstream. Уже начатые upstream/WebSocket-соединения не мигрируют при активации override.
4. Реплики и canary frontend балансируются внутри единственного service_id; upstream не участвует в процентном распределении. Root в preserve/strip не повреждает Path/RawPath, cookie Path, Location и не создаёт `//`.
5. После отключения override в development YAML с перезапуском либо production Admin API используется upstream, старая root-регистрация отклоняется. В development после рестарта upstream работает до повторной регистрации; в production ранее активированный override сохраняется и даёт `503` до восстановления туннеля. API, аудит и диагностика отражают configured/awaiting/active/unavailable состояния без секретов.
6. Пустой/неизвестный назначенный ID при enabled=true, root в shared_paths, отсутствие allowed `/` или выдача root другому сервису отклоняют конфигурацию. Фронтенд не получает автоматически interservice-доступ или право регистрации произвольных поддеревьев.

### 8.8. Обязательная security-приёмка публичного production-релиза

Проверки выполняются для QUIC, WSS и mixed mode с production-настройками; результаты, версии, лимиты и наблюдаемые статусы сохраняются в отчёте. Development-успех не заменяет этот gate.

1. **Fail-closed запуск.** Production не стартует/не становится ready без mTLS, deployment-grant verifier, устойчивого control/replay state, issuer/JWKS, quotas и admin isolation. Публичный development запрещён конфигурацией/сетевым deployment-тестом. Недоступность выбранного SQL/replay backend либо JWKS без пригодного identity-кеша не включает упрощённую проверку.
2. **Допуск экземпляров.** Токен другого сервиса, неверный/просроченный сертификат, неправильный service/instance SAN, сертификат с другим SPKI, подмена version/paths/mount и отсутствие grant отклоняются. Украденный общий development token не позволяет добавить production stable-реплику; один grant не открывает две активные сессии. Проверены обновление grant/cert и закрытие по сроку.
3. **Отзыв.** Revoke service/certificate/grant/HMAC key прекращает новые операции и активные затронутые потоки не позднее 5s. Состояние остаётся отозванным после рестарта и после reload старого key file. Security-admin может немедленно отключить туннель без ожидания graceful deadline; непривилегированный caller не может отозвать чужой credential.
4. **Пользовательские утверждения.** Корректный HMAC с произвольными admin roles без issuer assertion не проходит. Проверены неверные iss/aud/act/typ, изменение sub/roles/tenant, exp/nbf, неизвестный kid, alg none, HS/RS confusion, навязанный jku и несовпадение JWT/header context. B → C не использует audience B. Получатель повторно проверяет утверждение независимо от доверия к gateway.
5. **Internal-only.** Запрос к внутреннему endpoint с публичного listener, без Outgate-полей, с обычной пользовательской cookie, с service certificate без HMAC или без caller ACL не достигает handler. Обычный public endpoint остаётся доступен; private user endpoint проверяется API. Подписанный hop limit убывает, исчерпание возвращает `508` без дальнейшей доставки.
6. **Replay.** Два параллельных запроса с одним nonce дают не более одной доставки; проверяется также конкуренция разных соединений/caller-квот. После restart gateway/recipient с сохранённым SQL store (SQLite DB/WAL либо PostgreSQL) принятая подпись остаётся replay либо отклоняется recovery cutoff. Испытаны process kill, перезагрузка ОС, отказ commit/диска, потеря epoch/DB/WAL, удаление файлов и незаметно старая backup: до восстановления отзывов и окончания startup/recovery barrier запросы не проходят; старые подписи не становятся действительными. Handler не вызывается до durable commit; при сбое после commit доставка может не состояться, автоматического повтора нет. Production не очищает namespace при старте. Для Redis-адаптера при его поставке те же проверки включают потерю AOF/недоступность Redis; обязательные SQLite/PostgreSQL профили проходят на обеих ОС без Redis.
7. **Ёмкость и квоты.** Непрерывная нагрузка на допущенном signed RPS длится не менее 10 максимальных окон хранения nonce (не менее 20 минут при 120s) без штатного переполнения replay. Несовместимо маленькая capacity отклоняется при запуске. Один caller на 2x своей квоты получает `429`, не вытесняет чужие nonce и не блокирует разрешённые вызовы других principals. При глобальном отказе хранилища — предсказуемые `503`, не fail-open.
8. **Slow clients и DoS.** TLS/Upgrade floods, slow headers/body, множество idle WebSocket, oversized/fragmented messages, credit overflow и быстрые registration reconnects не превышают настроенные FD/buffer/stream бюджеты. При атаке в 2x квоты одного service/IP p95 разрешённых запросов другого service не превышает 2x его baseline при прочих равных; сессии/буферы после остановки возвращаются к baseline с заданным допуском. Rate limit действует до дорогостоящих crypto/issuer-refresh операций.
9. **Публикация маршрутов.** Кандидат с 0% регистрирует `/api/v1/orders` внутри работающего stable `/api/v1`: stable продолжает обслуживать путь. Pending не участвует в longest match. Активация без покрытия положительных версий, grant или роли отклоняется; корректная активация/смена owner атомарна и сохраняется после restart.
10. **Устойчивые политики.** Rollout/revocations/root state и revision сохраняются после аварийного restart. Старый YAML не возвращает прошлую canary или SPA. Повреждённая БД даёт not ready/`503`, не пустой реестр. Явный root switch доступен только разрешённому principal и не переигрывает уже отправленный запрос.
11. **Сессии WebSocket/SSE.** Logout/revoke sid/jti закрывает защищённые соединения в пределах 30s, expiry — 5s; возврат handler после Hijack не мешает закрытию. Потеря revocation dependency также закрывает поток. API проверяет права каждой защищённой команды; проверены чужой Origin, отсутствующий Origin браузерной сессии, CSRF, message flood и лимит фрагментированного сообщения. Истечение только HMAC handshake не подменяется пользовательским expiry.
12. **Парсинг и подписи.** Негативный corpus включает CL/TE ambiguity, duplicate Host/Signature/Outgate/user headers, CR/LF, obs-fold, unknown authority, escaped separators/dot segments и разные Path/RawPath/RequestURI. Нельзя получить другую авторизацию/маршрут изменением HTTP-версии/адаптера; подпись проверяется до strip. CONNECT к произвольному host/port, metadata endpoint и Admin API недоступен. Fuzz targets выполняются в CI ограниченным временем и дополнительно не менее 24h суммарно перед первым релизом без crash/hang/unbounded memory.
13. **Browser boundary.** API не может выдать inline HTML/JS, поставить чужую session cookie, расширить Service-Worker-Allowed до `/` или включить CORS wildcard+credentials. Проверены CSP реальной SPA, nosniff, HSTS, CSRF и cookie Domain/Path/HttpOnly/SameSite/Secure. Нельзя использовать API asset как SW root script. Недоверенные downloads обслуживаются на отдельном origin; доверие к frontend явно принято владельцем системы.
14. **Control plane.** Viewer не меняет состояние, deployer не отзывает чужие credentials/не импортирует security policy, service certificate/token/HMAC не дают admin прав. Админ-порт недоступен из публичной/service сети по сетевым правилам. Проверены admin mTLS, индивидуальные principals, revision conflict и аудит без secrets/JWT/сырых user fields; потеря устойчивой audit-очереди блокирует изменения.
15. **Supply chain и эксплуатация.** Релиз содержит dependency/image scan, SBOM, проверенный digest/подпись, fuzz/integration/race отчёты и runbooks. Выполнена учебная процедура отзыва сервиса и восстановления state без replay/отмены отзывов. До выдачи разрешения на production нет неустранённых достижимых Critical/High без оформленного ограниченного исключения. Бизнес-тесты подтверждают tenant/object permissions и idempotency важных операций.

Публичный выпуск допускается только после прохождения всех применимых проверок. Исключение для необязательной функции означает, что она явно выключена и недоступна, а не что её защиту можно пропустить. Эталонная production-интеграция включает настоящий настроенный issuer (тестовый issuer допустим только в приёмочном стенде), сервисные CA, устойчивые control/replay/session stores SQLite либо PostgreSQL, revocation API и изолированный Admin API; Redis необязателен. Полноценная HA и заявленные 50 000 RPS могут иметь отдельный срок приёмки, но не достигаются снятием этого security gate.

### 8.9. Проверка основного и резервных экземпляров

1. При подключённых reports-main/backup-1/backup-2 одной версии и готовом main серия запросов идёт только main. При его отключении новые запросы идут backup-1, после отказа backup-1 — backup-2; все unavailable дают 503/Retry-After:1. Round-robin других сервисов не меняется.
2. Прикладной not_ready, зависшая/отказавшая readiness callback, пропуск instance_status, drain и production revoke корректно исключают primary. Проверены пороги/timeout на управляемых часах; после обнаружения переключение <=1s. Быстрые 5xx/429 не вызывают неявного failover/retry, зависшие проверки не создают неограниченных goroutine.
3. preempt=false оставляет восстановившийся main резервным; preempt=true возвращает его только после 30s непрерывной готовности. Flapping обнуляет выдержку. Проверены подключение backup раньше main и новый выбор после рестарта без использования старого socket.
4. Нет маршрутизации на instance вне order, с другой version/path set, без grant или обязательной readiness. Клиентские заголовки/metadata не меняют приоритет. Кандидат/standby не публикует новые маршруты; активация/rollout требуют готового экземпляра и полного покрытия своей версии.
5. Canary выбирает stable/canary по обычным долям, затем primary внутри выбранной версии; резерв stable не обслуживает запрос выбранной canary. Проверены QUIC-only, WSS-only, mixed failover, межсервисные подписи окончательного instance и root frontend без возврата к upstream.
6. Во время сбоя POST с побочным эффектом не воспроизводится на резерве, старые HTTP/SSE/WebSocket не мигрируют; исправные уже принятые соединения могут завершиться на старом экземпляре при переключении новых. Тест приложения с fencing не допускает двойную singleton-операцию; без него gateway не заявляет single-writer гарантию.
7. Ручное переключение доступно только deployer, соблюдает revision/order/readiness; выбранный primary и причины видны в Admin API/метриках/аудите. Graceful drain и немедленный отзыв имеют разные сроки, общий buffer/concurrency budget включает standby-туннели.

### 8.10. Приёмка Admin Web и редактора межсервисных прав

1. Консоль доступна только на отдельном management HTTPS origin, не через public /admin, service tunnel или frontend override. Cookie/token публичной SPA не открывает консоль. Service certificate/token и BFF certificate без admin user JWT не получают права управления.
2. OIDC Code+PKCE/state/nonce и exact callback проверяются на позитивных/негативных сценариях; MFA и свежесть привилегированного действия проверяются API. JWT неправильных iss/aud/subject/alg, ID token вместо access token и подставленная роль в JS/header не дают доступ. При role revoke/session logout доступ исчезает <=5s; idle 15m/absolute 8h выполняются на управляемых часах.
3. В browser storage, JS bundle, HTML, URL и network responses отсутствуют access/refresh tokens, admin/service/HMAC private secrets и mTLS keys. Session cookie Secure/HttpOnly/Strict, transient callback-cookie Lax и короткоживущая; server session tokens зашифрованы. CSRF/Origin/CSP/frame-ancestors/no-store/XSS escaping проверены, чужой сайт не выполняет mutating BFF запрос.
4. Viewer просматривает сервисы/версии/primary/standby/политики и evaluate, но не меняет состояние даже прямым HTTP вызовом. Deployer управляет своим rollout/route activation/primary switch, но не policy editor; security_admin меняет права/root/revocations в своей области. UI controls не считаются механизмом авторизации.
5. Security_admin создаёт правило A → B с конкретными paths/methods и user/background flags, видит нормализованный diff, подтверждает reason и получает новую revision без рестарта. Разрешённый вызов начинает работать; перезапуск не сбрасывает изменения к старому YAML. Неизвестный сервис, wildcard/root path, попытка изменить issuer verification/admin role/secret отклоняются.
6. Черновик, validate и evaluate не меняют трафик и не вызывают бизнес-handler. Неверный/подменённый/чужой/просроченный preview, stale revision и две параллельные формы не вызывают silent overwrite; PUT без security_admin/свежего MFA не проходит. Config import не обходит тот же контроль для ACL/internal-only.
7. Удаление/сужение правила немедленно блокирует новые запросы и закрывает переставшие быть разрешёнными межсервисные WebSocket/SSE <=5s; перевод в internal-only также закрывает старые внешние потоки. Уже выполненная POST-операция не повторяется/не объявляется откаченной; неподходящие внешние user-соединения не затрагиваются случайно.
8. При отказе control state/outbox до commit не публикуется частичная политика, UI показывает ошибку и старую revision; при потере ответа после commit UI проверяет operation result и не обещает rollback. Каждое успешное изменение имеет actor, reason, old/new revision и безопасный diff; JWT/секретов/сырых пользовательских данных нет в UI/аудите. Возврат прежних правил создаёт новую revision с повторной проверкой и не восстанавливает отозванные credentials.
9. Экраны показывают статусы transport/версий, primary/standby, canary, frontend override и состояние зависимостей с временем обновления. Потеря API/session store не отображается как нормальное состояние и не разрешает анонимный доступ. В deploy-стенде демонстрируются promote/rollback, switch primary и редактирование access rules через браузер.

UI является обязательным проверенным компонентом поставки; его временное отключение оператором не отменяет серверные RBAC/preview/audit требования. Приложение не должно менять security policy в обход Admin API ни из формы, ни из отдельного импорта YAML. Полный набор контролей проверяется даже если конкретная эксплуатация предпочитает API/автоматизацию.

### 8.11. Приёмка платформ и встроенного хранилища

1. На чистых Linux amd64 и Windows Server 2022/2025 amd64 запускаются gateway, Admin Web и сервисы обоих транспортов. Windows не содержит WSL/WSL2, Docker, Linux VM, Go toolchain или Redis; работают штатные `.exe` и встроенная SQLite. Windows 11 проходит development smoke suite. Установочные/эксплуатационные зависимости перечислены явно.
2. На обеих production-платформах проходит общий integration/security suite: QUIC, WSS, mixed mode, routing/strip, canary, active-passive, SSE/WebSocket, подписанные вызовы, отзывы и Admin UI. Дополнительно gateway Windows обслуживает Linux-сервис и наоборот. Кросс-компиляция без исполнения не считается проверкой платформы.
3. Windows Service install/start/stop/restart/uninstall, восстановление после сбоя и Ctrl+C консольного запуска проверяются с ограниченным service account; SCM Stop выполняет bounded drain. Linux SIGTERM и переносимый admin reload проверены отдельно. Подписанные release manifests проверяются до установки.
4. Пути с пробелами/Unicode, произвольный working directory службы, PEM reload, NTFS ACL для DB/WAL/SHM/secrets/backup, firewall TCP/UDP и ротация логов проверены. Второй gateway с тем же control store отклоняется; сетевые/синхронизируемые каталоги не выдаются за поддерживаемый durable storage. При force kill/сбое диска не теряются уже подтверждённые security записи в рамках заявленных гарантий диска/ОС; состояние проверяется после перезапуска.
5. SQLite replay транзакции выдерживают конкурентные nonce/квоты, ошибки commit, checkpoint/cleanup и заполнение диска без доставки до commit или удаления живых nonce. При каждом старте соблюдается 120s cutoff/barrier, при restore восстанавливаются отзывы; потеря revocation канала закрывает credential/user потоки в пределах 5s/30s соответственно. BFF SQLite sessions сохраняют logout/revocation и fail-closed требования.
6. Выпускается сравнительный нагрузочный отчёт по ОС/транспорту/backend: hardware, filesystem/disk, durability settings, signed RPS, p99, commit latency, WAL/disk/RAM и очередь записи. Начальные 1000 signed RPS — admission ceiling примера, не гарантированная пропускная способность; допустимый профиль снижается при необходимости. 50 000 RPS остаются отдельной целью; FULL/проверки безопасности ради результата не отключаются.
7. При поставке Redis adapter он проходит тот же security/restart/recovery suite отдельно; его отсутствие не блокирует обязательную приёмку SQLite/PostgreSQL. Неподдерживаемый/недоступный driver приводит к явной ошибке, не к скрытому in-memory fallback.

### 8.12. Приёмка SQLite и PostgreSQL

1. Оба обязательных SQL driver проходят один контрактный набор control/replay/session: атомарный commit, expected_revision/409, сохранение rollout/прав/отзывов после restart, namespace isolation, session logout и recovery barrier. Уникальный nonce с конкурентных соединений доставляется не более одного раза; caller/global квоты не превышаются из-за гонки. Для PostgreSQL нагрузка включает конкурентные cleanup и quota updates, deadlock/lock timeout и обрыв connection/commit.
2. На Linux amd64 и нативной Windows amd64 общий integration/security suite выполняется для SQLite и PostgreSQL; QUIC/WSS/mixed mode и Admin UI не меняют поведение. Проверяются минимум три профиля: полный SQLite без DB-сервера/Redis, PostgreSQL control с локальными SQLite replay/session, полный PostgreSQL. Gateway PostgreSQL + SDK SQLite и обратное сочетание не требуют изменения прикладного handler.
3. PostgreSQL без verify-full, с неверным CA/hostname, недостаточными правами/несовместимой schema version, fsync/synchronous_commit выключенными либо UNLOGGED security tables не допускается. Обращение к read-only replica не обслуживает security транзакции. Ошибка DB/пула/query/lock не переводит процесс на SQLite/память и не вызывает replay отправленного HTTP-запроса. Секреты/DSN не появляются в UI/логах/ошибках.
4. BFF и SDK не читают/не изменяют чужие схемы и gateway policies; migration-role не нужна runtime. Прямой SQL, подставленные schema identifiers и чужой namespace не расширяют права. Два gateway с одним PostgreSQL control schema не становятся активными одновременно; потеря owner lock останавливает назначения до resync. Transaction pooling proxy для owner connection явно отклоняется/исключён deployment-проверкой.
5. Проверены migration lock, bootstrap, upgrade schema и несовместимая версия, backup/restore/PITR, stale backup и смена primary. Подтверждённые nonce/отзывы не теряются незаметно: непроверенный failover/restore остаётся fail-closed до восстановления отзывов и barrier. Допуск бесшовного PostgreSQL failover требует отчёта о синхронной репликации/fencing и отсутствии потери подтверждённых записей; cluster HA шлюза не заявляется.
6. Offline SQLite → PostgreSQL и PostgreSQL → SQLite migration сохраняют service IDs, версии, paths, policy snapshot/revision, grants/revocations и живые nonce/epoch; BFF sessions при переходе инвалидируются. Проверены cancel/crash migration, контроль целостности и безопасный возврат без запуска устаревшей security state. Нет автоматического online fallback.
7. Нагрузочный отчёт отдельно показывает SQLite и PostgreSQL с одинаковой durability/security, включая DB RTT, pool wait, commit latency, signed RPS/p99, cleanup/vacuum, WAL/диск и число соединений. PostgreSQL не получает заявленное преимущество без измерений; доступность внешней DB учитывается как дополнительная зависимость. Один backend не считается проверенным результатами другого.

### 8.13. Приёмка контрактов для разработчиков

1. Независимость реализации по п. 2.3 проверена module graph/imports/vendor/SBOM и review; build/test не требует reverst, перенос его кода запрещён. До реализации адаптеров доступны полные protocol.md/schemas/fixtures по п. 4.7, admin-openapi.yaml/config.schema.json и compatibility matrix. CI проверяет валидность спецификаций, соответствие OpenAPI реальным endpoints и выполнение golden corpus независимо каждым codec/verifier. Невыбранный QUIC carrier/ALPN или placeholder вместо схемы блокируют этап 1/2. Fuzz corpus покрывает framing/escaping/signature canonicalization, а не только happy path.
2. SDK проходит table-driven state/concurrency suite: Run дважды/одновременно, Close до Run/параллельно/с ранним deadline, WaitReady cancel/terminal error/reconnect, callback timeout/panic и handler panic. Run cancellation допускает завершение уже принятых запросов до drain; disconnect/revoke отменяют их в свой срок. Race detector не выявляет гонок, после теста нет лишних goroutine/handles; persistent stores не очищаются Close.
3. A вызывает логический B:api:/reports при разных deployment prefixes без изменения приложения. Проверены root/multiple mounts, strip/preserve, escaped Unicode/query, отсутствие discovery grant/policy, чужой вложенный route/shared path, stale route_revision и отрицательный cache. 409 не вызывает автоматического business retry; после явного refresh новый Request использует актуальный mount. Canary mismatch опубликованного mount отклоняется до применения.
4. Единые Problem Details/typed errors, API version, pagination cursors/filters/scope проверены в Admin API/BFF и HTTP gateway errors. Прикладной 4xx/5xx с произвольным Content-Type проходит без изменения. HEAD не получает тело, ошибка после headers не превращается во второй HTTP response; secrets/SQL/JWT отсутствуют.
5. Fault injection до commit, после commit/до publish, после publish/до response и при отказе внешнего audit проверяет отсутствие частичного state. Operation/outbox/revision записываются одной транзакцией на SQLite и PostgreSQL. Повтор UUIDv7 key возвращает тот же result без нового события/ревизии, чужой/изменённый payload конфликтует, expired key не исполняется. Повторное получение grant не раскрывает secret; сценарий revoke+reissue работает. Outbox доставляет event с дедупликацией; локальное переполнение блокирует только ещё не committed изменения.
6. Viewer/deployer/security_admin без scope, с одним/несколькими bindings и с revoked role не обходят cross-service ограничения через прямой API/import/retry/cursor/evaluate. Правило caller A → target B требует scope обоих; scoped PUT сохраняет скрытые чужие правила. Проверены empty bootstrap, повторная инициализация, recovery при недоступном IdP и отсутствие online MFA bypass; recovery оставляет проверяемый manifest/audit и инвалидирует сессии.
7. Static и rotating credentials: production без instance_id, несовпадение SAN/SPKI/grant/path/mount, stale generation, callback timeout, краткое перекрытие срока, истечение и revoke проверены. Новый сертификат и старый grant не допускаются; при плановом switch нет двух active sessions instance, старый WebSocket не переносится и не живёт сверх срока. Service replica с другим ID продолжает принимать новые запросы.
8. Таймауты п. 5.6 проверяются управляемыми часами, отдельно header/body directions/WS/DB/drain/barrier. SSE heartbeat сохраняет поток, tunnel ping не заменяет прогресс body; expiry/revoke приоритетнее idle/drain. Startup readiness и обещание reconnect не смешиваются; 180s startup grace допускает штатный barrier.
9. Retire/release/version retire/delete/purge проходят RBAC/preview/revision/idempotency и не освобождают владение автоматически. Retired недоступный path даёт 503, released API — 404, released non-API может перейти в SPA только после явно подтверждённого release. Live grants/streams/references блокируют удаление; purge не удаляет live nonce/revocations/неотправленный outbox. ID tombstone не переиспользуется.
10. Чистый downstream service из отдельного boilerplate repository собирается с released pinned SDK и GOWORK=off без исходников gateway/локального replace; проходит приёмка [service-development.md](service-development.md). Gateway N с SDK N/предыдущим опубликованным minor одного major проходит QUIC/WSS contracts; unsupported major/required capability отвергаются до routing. Проверены supported DB schema upgrade, невозможный binary rollback и safe restore. HTTP retry fault suite закрывает reused HTTP/1 connection, HTTP/2 reset/GOAWAY и QUIC reset на разных этапах отправки: handler не получает повтор ни для GET/HEAD/OPTIONS, ни для body/GetBody/Idempotency-Key. Механизм Admin API dedup тестируется отдельно от business retry.

## 9. Риски и допущения

| Риск | Меры |
| :--- | :--- |
| UDP заблокирован сетью сервиса | Явный выбор WSS и включение соответствующего слушателя; без скрытого fallback |
| WSS TCP head-of-line blocking | Ограниченные окна и очереди, справедливый writer; сравнение под потерями в нагрузочных тестах |
| Различие поведения адаптеров | Единые контракты и одинаковые сценарии приёмки |
| Захват пути или вложенного префикса | Привязка credential к сервису, allowed paths и атомарная регистрация |
| Неисправная новая версия | По умолчанию 0%, ручной rollout, метрики по версиям и явный rollback |
| Недостаточно stable/canary экземпляров | 503 без скрытого изменения долей; проверка покрытия при изменении политики |
| Рост памяти/кардинальности | Лимиты запросов, тел, кредитов, путей, версий и туннелей; очистка завершённых сессий |
| Потеря runtime-политик при рестарте | Явное восстановление YAML, инструкция оператору; постоянное хранение в production, development только для изолированного стенда |
| Рассогласование при нескольких шлюзах | Первая production-версия — один writer/gateway, SQLite либо PostgreSQL control/replay stores; Redis опционален; общая PostgreSQL сама по себе не добавляет HA, кластерный реестр и HA требуют отдельного проекта |
| Подмена пользовательского контекста | Удаление внешних trusted headers, разрешение делегирования только доверенным API и подписи обоих участков |
| Replay и рассинхронизация часов | Устойчивый nonce store, квоты, синхронизация часов и fail-closed recovery; потеря кеша при рестарте допустима только в development |
| Несогласованное обновление SPA | Атомарная публикация, cache validators и сохранение ресурсов предыдущей сборки |

Допущения: DNS настроен внешней инфраструктурой; сервис имеет исходящий TCP/TLS для WSS либо UDP для QUIC к соответствующему слушателю. Шлюз не выполняет оркестрацию контейнеров и бизнес-проверку готовности версии: регистрация означает транспортную готовность, а администратор отвечает за запуск, проверку и остановку версий. Для других языков SDK не входит в прототип. Автоматическая доставка уведомлений во внешние системы не требуется: обнаружение доступно через API, метрики и события логов.

Дополнительно: YAML задаёт начальные межсервисные политики, UI/Admin API изменяют постоянный policy snapshot с revision; шлюз и сервисы синхронизируют часы; in-memory replay допустим только в development. Production использует устойчивое состояние п. 5.5. Автоматические цепочки auth-проверок и полноценное обнаружение циклов вызовов не входят в первую версию; постоянное replay-хранилище обязательно в production. Бюджет hop count обязателен независимо от отсутствия полного детектора циклов. Наличие исходящего туннеля не заменяет доступ вызывающего сервиса по HTTPS к слушателю межсервисных вызовов шлюза (в development — публичному, в production — отдельному mTLS endpoint).

Нормативные источники по транспортам: [HTTP/3 — RFC 9114](https://www.rfc-editor.org/rfc/rfc9114.html), [QUIC — RFC 9000](https://www.rfc-editor.org/rfc/rfc9000.html), [WebSocket — RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html). Конкретный протокол Outgate является расширением проекта и документируется отдельно.

## 10. Приложения

### 10.1. Пример клиента

Иллюстрация development-использования будущего Go-пакета; module path `github.com/solodyagin/outgate-sdk` соответствует отдельному опубликованному [SDK repository](https://github.com/solodyagin/outgate-sdk). Прикладной `outgateclient` и SDK release ещё не реализованы/не выпущены. Для публичного production дополнительно обязательны bootstrap и зависимости п. 10.8. Тестовый сертификат шлюза должен быть выпущен доверенным для клиента CA. Ниже используется переносимый Ctrl+C для консольного примера; production host wrapper добавляет Linux SIGTERM или Windows SCM Stop по п. 5.4.1.

```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "os/signal"
    "strings"

    "github.com/solodyagin/outgate-sdk/outgateclient"
)

func main() {
    ctx, stop := signal.NotifyContext(context.Background(), os.Interrupt)
    defer stop()

    mux := http.NewServeMux()
    mux.HandleFunc("/hello", func(w http.ResponseWriter, r *http.Request) {
        _, _ = w.Write([]byte("hello from 1.4.2"))
    })
    mux.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        w.WriteHeader(http.StatusOK)
    })

    c, err := outgateclient.New(
        "gateway.example.com:7171",
        outgateclient.WithTransport("quic"),
        outgateclient.WithSecurityMode("development"),
        outgateclient.WithServiceID("my-service"),
        outgateclient.WithVersion("1.4.2"),
        outgateclient.WithPaths(strings.Split(os.Getenv("OUTGATE_SERVICE_PATHS"), ",")...),
        outgateclient.WithStripPrefix(true),
        outgateclient.WithHandler(mux),
        outgateclient.WithBearerToken(os.Getenv("OUTGATE_SERVICE_TOKEN")),
        outgateclient.WithMaxConcurrentRequests(100),
    )
    if err != nil {
        log.Fatal(err)
    }
    // При отмене ctx Run выполняет ограниченный graceful shutdown.
    if err := c.Run(ctx); err != nil {
        log.Printf("outgate client stopped: %v", err)
    }
}
```

В конфигурации развёртывания задаётся `OUTGATE_SERVICE_PATHS=/api/v1`; тогда внешние пути `/api/v1/hello` и `/api/v1/health` соответствуют локальным `/hello` и `/health`. Пустое значение не имеет неявного default и отклоняется New. Несколько значений через запятую — алиасы того же локального корня; отдельный публичный `/health` в этом примере не регистрируется. Для WSS используются `gateway.example.com:7172`, `WithTransport("wss")` и при необходимости `WithWSSPath("/tunnel")`. Для канарейки запускается отдельный процесс с новым instance ID и `WithVersion("1.5.0")`, затем администратор назначает долю. Изменения прикладного `http.Handler` для выбора транспорта не требуются.

### 10.2. Последовательность

```text
Microservice               Gateway                    Admin / External client
    │── QUIC или WSS ────────►│
    │── auth + register ─────►│── обнаружение version, публикация путей
    │◄── register_ack ────────│
    │                         │◄── PUT rollout: stable 90%, canary 10%
    │                         │◄── HTTPS GET /api/v1/hello
    │                         │── path → service → version → instance
    │◄── HTTP/3 request ──────│  либо WSS request_start + binary chunks
    │── потоковый ответ ─────►│── HTTP response ─────────────►
    │                         │◄── POST promote / rollback
    │                         │── атомарная политика новых запросов
```

### 10.3. Отдельные репозитории шлюза, SDK и шаблона сервиса

Поставка разделена на **три самостоятельных репозитория** и три Go modules. Разработчику прикладного сервиса выдаётся boilerplate и доступ к released SDK, а не исходники шлюза. Репозитории gateway и SDK опубликованы: [solodyagin/outgate](https://github.com/solodyagin/outgate) и [solodyagin/outgate-sdk](https://github.com/solodyagin/outgate-sdk). SDK вынесен в самостоятельный module `github.com/solodyagin/outgate-sdk`. Для шаблона создан отдельный repository [solodyagin/outgate-service-template](https://github.com/solodyagin/outgate-service-template), локальный checkout — `../outgate-service-template/`. Repository пока пуст: исходники boilerplate, его Go module, CI и versioned releases ещё отсутствуют. Ниже показана целевая структура поставки; наличие repository не означает готовности всех перечисленных компонентов. Нормативные protocol/schema и golden corpus хранятся в gateway repository. SDK содержит локальный snapshot schema/fixtures для автономных offline-тестов; изменения контракта синхронно переносятся в SDK с побайтовой сверкой.

- SDK импортируется как `github.com/solodyagin/outgate-sdk/outgateclient`; service go.mod фиксирует опубликованную SemVer-версию SDK. Шлюз не импортируется в прикладное приложение, не копируется в его repository и не нужен на машине разработчика для local mode. Go SDK статически входит в обычный service binary; отдельный SDK daemon/sidecar не требуется.
- Однонаправленные зависимости: service → SDK/outgateclient; SDK → свой protocol/v1 и независимые библиотеки; gateway → при необходимости только SDK/protocol/v1 с pinned версией. SDK никогда не импортирует gateway, его internal packages, Admin API server, control DB/outbox или administrative UI. Public protocol/v1 содержит только wire types/serialization/чистые protocol helpers, не transport sockets/SQL/RBAC runtime; SDK public API не раскрывает quic-go connection types. Общие wire определения не копируются вручную между репозиториями.
- Нормативные protocol/schema/golden artifacts версионируются согласованно с релизом; SDK release содержит snapshot совместимого контракта. Gateway использует pinned snapshot/SDK protocol package; кодовые зависимости не образуют цикл. CI проверяет import graph, соответствие golden corpus и совместимость gateway N с SDK N/предыдущим поддерживаемым minor. Старое размещение pkg/outgateclient внутри gateway repository не используется.
- Каждый repository имеет собственные go.mod/go.sum, tags, changelog и CI. Gateway может обновляться без обязательного rebuild сервисов в пределах compatibility matrix. SDK major v2 использует обычный Go module suffix /v2; wire protocol major/version сервиса не меняются автоматически вместе с ним. Web build dependencies существуют только в gateway web/admin.
- go.work допустим только как локальное удобство при соседних checkout; published template/release не содержит обязательных replace на ../outgate-sdk или ../outgate-gateway, file paths разработчика либо обязательного workspace. Чистый checkout с GOWORK=off и доступом к module registry/VCS обязан собираться. Для приватного SDK документируются доступ к VCS и точечный GOPRIVATE, без отключения TLS/checksum для всех dependencies и без tokens в go.mod/URL.
- Исходный код Outgate самостоятельный; vendored/adapted reverst directory не создаётся. upstream.md хранит только историю архитектурного референса; реальные dependencies/licenses/SBOM ведутся отдельно. Helm и отдельный Admin CLI остаются последующим расширением; обязательные maintenance subcommands предусмотрены в п. 6.5.

Подробный контракт выдаваемого boilerplate и onboarding разработчика — [service-development.md](service-development.md); готовый шаблон сервиса обязателен в первой поставке, а не необязательный пример рядом с gateway.

### 10.4. Пример прикладной аутентификации и межсервисного вызова

Development-фрагмент для сервиса `my-service` с публичным префиксом из deployment-конфигурации (в стенде `/api/v1`) и `WithStripPrefix(true)`: функция `authenticate` предоставляется самим приложением и проверяет его пользовательскую сессию/токен. Middleware устанавливает контекст только после успешной проверки. Клиент создаётся с корневым `http.ServeMux` через `WithHandler` и ключом `my-call-1` через `WithServiceSigningKey`; затем результат `APIHandler` устанавливается в корневой mux до вызова `Run`. Соответствующий секрет передаётся из `OUTGATE_MY_SERVICE_CALL_KEY`. У `reports-service` настраивается `WithGatewayVerificationKeys` с ключом `gateway-reports-1`. Секреты предварительно декодируются из base64; значение tunnel bearer используется отдельно.

```go
package example

import (
    "io"
    "net/http"

    "github.com/solodyagin/outgate-sdk/outgateclient"
)

func APIHandler(
    c *outgateclient.Client,
    authenticate func(*http.Request) (outgateclient.UserContext, error),
    gatewayOrigin string, // из конфигурации: https://gateway.example.com:8443
    reportsURL string,    // из конфигурации: https://gateway.example.com:8443/api/v2/reports
) (http.Handler, error) {
    serviceHTTP, err := c.ServiceHTTPClient(gatewayOrigin)
    if err != nil {
        return nil, err
    }
    mux := http.NewServeMux()
    mux.HandleFunc("GET /public", func(w http.ResponseWriter, r *http.Request) {
        _, _ = w.Write([]byte("public"))
    })
    mux.HandleFunc("GET /reports", func(w http.ResponseWriter, r *http.Request) {
        user, err := authenticate(r)
        if err != nil {
            http.Error(w, "unauthorized", http.StatusUnauthorized)
            return
        }
        // Здесь же API проверяет прикладные права пользователя на reports.
        ctx := outgateclient.WithUserContext(r.Context(), user)
        ctx = outgateclient.WithTargetService(ctx, "reports-service")
        req, err := http.NewRequestWithContext(
            ctx, http.MethodGet, reportsURL, nil,
        )
        if err != nil {
            http.Error(w, "request creation failed", http.StatusInternalServerError)
            return
        }
        resp, err := serviceHTTP.Do(req)
        if err != nil {
            http.Error(w, "service call failed", http.StatusBadGateway)
            return
        }
        defer resp.Body.Close()
        if value := resp.Header.Get("Content-Type"); value != "" {
            w.Header().Set("Content-Type", value)
        }
        w.WriteHeader(resp.StatusCode)
        _, _ = io.Copy(w, resp.Body)
    })
    return mux, nil
}
```

На стороне `reports-service` библиотека сначала проверяет подпись шлюза и устанавливает context, затем handler вызывает `UserContextFromContext(r.Context())` и `CallerServiceFromContext(r.Context())` и проверяет собственные права. Он не должен доверять user headers без этой проверки. Для разрешённого фонового вызова применяется context без `WithUserContext`; получатель видит caller `my-service` и отсутствие пользователя. Для B → C можно использовать контекст проверенного входящего запроса с новым `WithTargetService`, но B обязан иметь собственный исходящий signing key и соответствующее разрешение.

`ServiceHTTPClient` сохраняет потоковую семантику ответов и, при Upgrade, двунаправленный интерфейс response body. Для исходящего межсервисного WebSocket используется `coder/websocket.Dial` с этим клиентом в `DialOptions.HTTPClient` и context с `WithTargetService`/`WithUserContext`; подпись добавляется к фактическому handshake. Origin/subprotocol и пользовательские credentials задаются приложением явно. Это не требует изменений WebSocket-handler получателя, включая handler на `gorilla/websocket`. Автоматический reconnect WebSocket не выполняется библиотекой шлюза; каждая новая попытка получает новую подпись/nonce.

### 10.5. Конфигурация SPA-сервера

Пример ожидаемого поведения frontend-upstream: `/` и `/app/orders/42` возвращают текущий `index.html`; `/assets/app.<hash>.js` возвращает ресурс; отсутствующий `/assets/missing.js` возвращает `404`. API-префиксы не обслуживаются этим сервером через шлюз. Сборка размещается отдельным релизом и переключается атомарно; предыдущие хешированные ресурсы сохраняются для открытых вкладок.

Изменения SPA не требуют изменения регистрации API, rollout-политик, ключей или конфигурации шлюза. При недоступном SPA-upstream его запросы получают `502`/`504`; при недоступном ранее зарегистрированном корневом frontend — `503`. Работа уже подключённых API-туннелей продолжается.

### 10.6. Настройки монтирования сервиса

Настройки из этого примера принадлежат deployment сервиса и передаются его кодом в outgateclient; это не новые поля YAML шлюза:

```yaml
deployment:
  mode: development
outgate:
  gateway_addr: "gateway.example.com:7171"
  transport: quic
  service_id: "my-service"
  version: "1.4.2"
  paths: ["/api/v1"]
  strip_prefix: true
  rewrite_mount_headers: true
outbound:
  gateway_origin: "https://gateway.example.com:8443"
  reports_url: "https://gateway.example.com:8443/api/v2/reports"
```

В разработке тот же локальный mux обслуживает `/hello`, `/public`, `/reports`, `/health` или `/ws`. В production вызываются публичные `/api/v1/hello`, `/api/v1/public` и т. д.; код маршрутов менять не нужно. Чтобы локальный `/health` был доступен через mount, используется `/api/v1/health`, а не отдельный strip-алиас `/health` (который соответствовал бы локальному `/`). Для endpoint вне общего префикса выбирается отдельная регистрация/сессия или preserve-обработчик.

Локальный redirect `/login` и cookie `Path=/session` становятся `/api/v1/login` и `/api/v1/session`. Для ссылок в HTML/JSON и URL WebSocket, отдаваемых приложением, используется `MountInfoFromContext` или явно настроенный публичный base URL: автоматического переписывания содержимого нет. Межсервисный исходящий URL также задаётся конфигурацией целевого сервиса и не выводится из входящего mount текущего запроса.

### 10.7. Подключение назначенного frontend-сервиса

Администратор включает frontend_override и выдаёт frontend-service только его credential и разрешение `/`, как в конфигурации шлюза выше. Frontend-разработчик запускает HTTP-handler SPA через ту же библиотеку; отдельный доступный шлюзу HTTP-порт не нужен:

```go
package example

import (
    "net/http"
    "os"

    "github.com/solodyagin/outgate-sdk/outgateclient"
)

// spaHandler предоставляет index.html fallback и корректные asset 404/cache headers.
func FrontendClient(spaHandler http.Handler) (*outgateclient.Client, error) {
    return outgateclient.New(
        "gateway.example.com:7171",
        outgateclient.WithTransport("quic"),
        outgateclient.WithSecurityMode("development"),
        outgateclient.WithServiceID("frontend-service"),
        outgateclient.WithVersion("2026.11.21"),
        outgateclient.WithPaths("/"),
        outgateclient.WithHandler(spaHandler),
        outgateclient.WithBearerToken(os.Getenv("OUTGATE_FRONTEND_TUNNEL_TOKEN")),
    )
}
```

Это фрагмент настройки: обработка err и запуск/остановка Run аналогичны п. 10.1. WSS использует соответствующий порт и WithTransport("wss"). Фронтенд не может самостоятельно назначить себе право root: его service_id и токен проверяются шлюзом, а enabled и allowed_paths задаёт только администратор. Режим preserve для корня подходит без удаления `/`.

Чтобы вернуть SPA-upstream, администратор в development отключает frontend_override и применяет конфигурацию перезапуском, а в production выполняет PUT /admin/frontend-override с revision; простое отключение туннеля возвращает `503`, а не переключает пользователей на другую сборку незаметно.

### 10.8. Обязательный production bootstrap и процедура допуска

Development-примеры выше показывают transport/handler API, а не рецепт публичного запуска. Для production выполняется следующий воспроизводимый порядок:

1. Оператор создаёт отдельные service/admin CA и server certificates, постоянные локальные SQLite control/replay/session каталоги с WAL/FULL/ACL либо PostgreSQL schemas/roles с проверенными durability/TLS по п. 6.4, секреты HMAC и защищённую очередь аудита. Identity issuer настраивается на выдачу target-specific `outgate-delegation+jwt` с actor, sid/jti и ограниченными claims; проверяется доставка отзывов.
2. Gateway запускается в production с конфигурацией п. 6.1 и остаётся not ready, пока зависимости не проверены. CI фиксирует digest образа либо нативного release-артефакта, проверяет SBOM/подпись и получает от deployer grant под конкретные instance/service/version/paths/SPKI. Клиент загружает production-профиль через WithSecurityConfigFile (mode, issuer/JWKS, выбранный replay driver и его path/namespace либо PostgreSQL schema/credentials, revocation endpoint и лимиты); certificate через WithTLS, grant через WithDeploymentGrant/Provider, отдельные HMAC и issuer/replay/revocation настройки. WithBearerToken вместо grant отклоняется.
3. Экземпляр регистрируется с pending-путями; после проверки handler и покрытия stable-версии deployer выполняет `/admin/routes/activate` с revision. Для корневого frontend такая активация отдельно включает durable override. Подключение новой canary-версии само по себе не активирует новые префиксы.
4. Для пользовательского A → B приложение A после своей аутентификации получает от issuer утверждение для audience B/actor A; помещает его через WithUserAssertion, указывает WithTargetService и вызывает production ServiceHTTPClient на :9443 с client certificate. Локальный WithUserContext не заменяет assertion. SDK формирует/сверяет user headers по claims, gateway и B независимо проверяют их. Для фонового вызова assertion отсутствует, действует allow_background и caller identity.
5. API с защищённым WebSocket/SSE после собственной проверки cookie/token вызывает BindUserSession с проверенным sid и сроком, передаёт новый context handler. При logout уполномоченный identity-компонент отзывает sid/jti; SDK закрывает соединение в срок. Для delegated stream binding создаётся из проверенного assertion автоматически. Это требует интеграции lifecycle в auth middleware, но не переписывания WebSocket handshake/обмена существующего handler.
6. Проводятся проверки п. 8.8 с отчётом, учебный отзыв credentials и восстановление state. Только после этого firewall/LB публикует browser/tunnel endpoints. Admin и опциональный Redis не становятся публичными. Production acceptance не достигается установкой mode=development или отключением проверок ради прохождения load test.

При чистом HTTPS/QUIC перенаправлении в handler сохраняется совместимость прикладных маршрутов. Новые обязанности разработчика API в production — корректная пользовательская авторизация, session lifecycle, internal-only проверка и получение issuer assertion при делегировании; библиотека обеспечивает transport, signature/replay verification и принудительное завершение привязанных потоков. В комплекте поставляются production Compose для Linux и нативные PowerShell/Windows Service инструкции с конфигурациями firewall/ACL, тестовый issuer и CA для приёмки; реальные ключи/IdP администратора в репозиторий не включаются.

Источники для конкретных механизмов: [JWT Best Current Practices — RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html), [делегирование Token Exchange — RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html), [OWASP WebSocket Security](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html), [SQLite WAL](https://www.sqlite.org/wal.html), [SQLite synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous), [Go signals на Windows](https://pkg.go.dev/os/signal), [PostgreSQL WAL/durability](https://www.postgresql.org/docs/current/runtime-config-wal.html), [PostgreSQL locking](https://www.postgresql.org/docs/current/explicit-locking.html), [PostgreSQL TLS verify-full](https://www.postgresql.org/docs/current/libpq-ssl.html), [Redis persistence — для опционального адаптера](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/). Собственные сроки, квоты, роли и критерии этого ТЗ являются требованиями проекта и проверяются приёмкой, а не выдаются за параметры, гарантируемые стандартами.

### 10.9. Развёртывание active-passive сервиса

Одна сборка reports-service развёртывается в трёх процессах/контейнерах. Конфигурация приложения передаёт OUTGATE_INSTANCE_ID в WithInstanceID, одну version 1.0.0, одни paths /api/v2 и общую реализацию handler. Только OUTGATE_INSTANCE_ID, certificate/grant и при необходимости транспорт различаются. Настройка порядка и режима остаётся у администратора gateway, а не у приложения.

WithReadinessCheck получает локальную функцию, проверяющую обязательные зависимости с context deadline; readiness не проверяет роль primary и не становится ложной только потому, что экземпляр standby. В production отсутствие callback — ошибка регистрации active-passive экземпляра. Пример interval/timeout/порогов приведён в конфигурации reports-service п. 6.

По умолчанию автоматического возврата на восстановившийся main нет: он готов к следующему отказу как резерв. Для возврата оператор выполняет active-instance switch или заранее включает preempt с hold-down. Развёртывание не обещает перенос WebSocket/локальных сессий; состояние приложения выносится в общее хранилище. Background workers используют отдельный database lease/fencing, не самостоятельно интерпретируют сетевую роль как право записи.

### 10.10. Рабочий сценарий администратора в веб-консоли

1. Оператор открывает management origin, проходит OIDC/MFA, видит свою серверную роль и текущую revision. Viewer может исследовать состояние, но не включить кнопки изменения через JS и не применить API-запрос напрямую.
2. Security_admin открывает «Межсервисный доступ», выбирает caller my-service, target reports-service, path /api/v2/reports, методы GET/POST и отдельно отмечает user delegation/background. Эти флаги не отключают JWT/mTLS и не выдают роли пользователя.
3. Сервер validate показывает diff и последствия; evaluate позволяет проверить гипотетический вызов без обращения к reports-service. До применения действующая политика не меняется.
4. Оператор проверяет изменения, указывает причину и подтверждает. При устаревшем MFA сначала выполняет step-up; при конфликте revision получает актуальный snapshot и повторяет проверку. После успешного PUT новые вызовы используют новую политику, без перезапуска сервиса или gateway.
5. При удалении права соответствующие новые вызовы получают 403, старые больше не разрешённые WebSocket/SSE закрываются <=5s. При необходимости вернуть старое правило оно загружается как новый черновик из истории и заново проходит валидацию, подтверждение и аудит.

Тестовый development-стенд включает отдельную административную консоль и mock OIDC с тестовыми ролями. Реальный admin IdP/MFA, BFF cert/secret/session key и management network задаёт оператор; они не встраиваются в frontend assets и не поступают в публичную SPA. Конкретный frontend framework выбирается при реализации; требования к security flow, API и ролям не зависят от него.

Основание для browser-защит: [OWASP CSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html), [OWASP OAuth2](https://cheatsheetseries.owasp.org/cheatsheets/OAuth2_Cheat_Sheet.html). Разделение BFF/Admin API, сроки сессий и preview workflow являются требованиями этого проекта, а не обещаниями конкретного IdP.

Нормативные механизмы контрактов разработчика: [HTTP Problem Details — RFC 9457](https://www.rfc-editor.org/rfc/rfc9457.html), [UUIDv7 — RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html), [Go HTTP Transport и автоматические retries](https://pkg.go.dev/net/http#Transport). Состояния SDK, WSS layout, mount discovery, сроки retention и API workflow выше являются собственным контрактом Outgate.
